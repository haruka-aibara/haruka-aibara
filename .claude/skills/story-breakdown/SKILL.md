# ストーリーをサブタスクと基準線に分解する

## このスキルが解こうとしている問題

複雑なストーリーを進めているとき、**「いま計画を変えるべきか」は本人にもチームにも判定できない**。学習は少しずつ進むのに、判断に足る差分になるまでラグがあるし、何が分かっていないかが分かるのは最後だったりする。デイリースクラムで「どうですか」と聞いても「順調です」しか出てこないのは、本人が嘘をついているからではなく、判定する基準が存在しないから。

だから作るのは**予定表ではなく基準線**。着手前に「これがうまくいけば◯日目に××が動いているはず」を外に出しておくと、判定が「変えるべきか？」（答えられない）から「見込みとズレたか？」（答えられる）に変わる。

この目的から外れる出力は価値がない。**精度を上げようとしないこと。** 詳細な工数見積もりや網羅的な WBS に寄せると、更新コストのほうが勝って誰も見なくなる。ざっくりでいい。

## いつ使うか（リファインメントの前が効く）

もっとも効くのは、PO がストーリーを書いたあと、**リファインメントに入る前**。ただし配る順番を間違えると逆効果になるので、そこだけ注意する。

**回すのは PO ではなく、担当しそうな開発者かスクラムマスター。** PO が回すと「PO の計画」になり、開発側が受け取るだけの構図が固定される。作りたいのは PO のストーリーに対するチーム側の読み。

**会議に最初に持ち込むのは「未知」と「置いた仮定」だけ。** サブタスク分解と基準線は伏せておき、チームが自分で分解したあとに突き合わせる。分解案を先に見せると、それが基準になってチームから別案が出なくなる（特に経験の浅いメンバー）。会議が分解案の承認作業に変わると、検査も適応も起きない。

**「置いた仮定」は PO への質問リストとして使う。** ここは AI がもっともらしく埋めた箇所、つまりストーリーの曖昧な部分そのもの。無視すると「曖昧さが埋められて見えなくなった状態」で会議に入ることになり、これがこの使い方の最大の失敗パターン。

見積もりの精度が上がるとすれば、それは AI が正しく見積もるからではなく、**未知の認識が揃うから**。見積もりが割れる原因はたいてい計算力の差ではなく、見えている未知が人によって違うこと。だから出力の数字や個数を答えとして扱わない。チームの分解が一つも変わらずに通ったリファインメントは、合意ではなく素通りだと考えたほうがいい。

## 進め方

### 1. 足りない情報を確認する（最大3つまで）

判断に効くのはこのあたり。**全部聞かない。効きそうなものを最大3つ、聞かなければ答えが大きく変わるものだけ。**

- 期間の枠（スプリント終了日、締め切り、残り日数）
- 何をもって完了とするか（受け入れ条件、誰が受け入れるか）
- 触る範囲（既存のどこを変えるか、初めて触る領域か）
- 外部依存（他チーム・外部サービス・データ提供の有無）

質問が3つを超えるなら、**仮定を置いて出力に明記する**。止めるより、たたき台を出して直してもらうほうが早い。

### 2. 未知を先に洗い出す

サブタスクより先にこれをやる。順番が逆だと、未知が実装タスクの中に埋もれて見えなくなる。

未知は種類で打ち手が違うので、必ず種類を書く。

| 種類 | 具体例 | 打ち手 |
|---|---|---|
| 技術が未知 | このライブラリで実現できるか分からない | 時間を区切って試す（スパイク） |
| 要件が未知 | 何を作れば受け入れられるか曖昧 | 早く薄く動かして見せる |
| 依存が未知 | 他チームの返答・外部の仕様待ち | 先に投げて、待つ間の代替作業を用意 |

**未知ゼロと書かない。** 複雑なストーリーには必ずある。見つからないなら分解が粗いか、そもそも単純な作業でこのスキルの出番ではない。

### 3. サブタスクに割る（5〜8個）

**薄くても end-to-end で通る1本目を必ず先頭に置く。** 縦に1本通ると、学習が主観ではなく事実の形で出てくる。ここが一番効く。

避けたいのは工程で切ること（設計 → 実装 → テスト）。分業には都合がいいが、動くものが終盤まで出ないので、学習が全部後ろに寄る。「変えるべきだった」と分かるのが手遅れになってから、という失敗はほぼこれが原因。

- 各サブタスクに「終わったと言える条件」を1行だけ添える（長い DoD は要らない）
- 8個を超えたら粒度が細かすぎる。まとめる
- 3個未満なら、たぶん未知を見落としている

### 4. 止まりどころを予告する（2〜3個）

詰まった人が申告できないのは、それが異常なのか普通なのかを判定できないから。3日溶かしても「こういうものかもしれない」と思えてしまう。「たぶんここで止まる」が事前に共有されていれば、止まった人は「予告どおり止まりました」と言えるし、予告そのものが「止まるのは想定内」というメッセージになる。経験の浅いメンバーほどここで救われる。

- **そのストーリーの言葉で具体的に書く。** 「外部連携に注意」は一般論なので流される。「サンドボックスの返り値が本番と違って半日溶けるかも」まで書く
- 各予告に「そうなったらどうするか」を1行添える（誰に相談する／代替案／何時間で切り上げる）
- **外れてよい。** 予告と違う場所で止まったなら、それ自体が有用な情報

### 4. 基準線を2〜3点だけ置く

**全サブタスクに日付を振らない。** 振ると管理表になり、更新されなくなって死ぬ。

置くのはこの2〜3点だけ：

- **1本目が縦に通っている日**（いちばん重要）
- **未知が解消されている期限**（スパイクのタイムボックス、依存先の返答期限）
- 必要なら、残りが見通せているはずの中間点

日付が分からなければ「スプリント◯日目」のような相対表現でよい。**絶対日付を作るために推測を重ねない。**

### 5. ズレの検出条件を書く

基準線とセットで、「何が起きたら見直すか」を書く。ここが曖昧だと、結局「なんとなく不安」に戻る。

良い例：「3日目に画面から1件も登録できていなければ、方式を変える相談をする」
悪い例：「進捗が芳しくなければ見直す」（判定できない）

## 出力の形

チケットにそのまま貼れる長さで。この構成で出す。

```markdown
## 未知（先に潰すもの）
- [種類] 内容 → 打ち手（◯日目まで）

## サブタスク
1. **1本目（縦に通す）**：内容 — 終わったと言える条件
2. …

## 止まりどころ（予告）
- 内容 → そうなったら◯◯する

## 基準線
- ◯日目：××が動いている
- ◯日目：△△の見通しが立っている

## ズレたと判断する条件
- ◯日目に××が動いていなければ、□□を相談する

## 置いた仮定
- （聞かずに埋めた前提。違っていたら直してもらう）
```

最後に必ず、**これはたたき台であり、チームが5分で直す前提**だと添える。ここを省くと「AI が言ったから」で疑われなくなり、判断を外注する道具になってしまう。それはこのスキルが解こうとしている問題を悪化させる。順序も粒度も、実際に手を動かす人が一番よく知っている。

## 途中で呼ばれたとき

「着手したが見通しが立たない」「基準線からズレた」という相談で呼ばれることもある。そのときは最初からやり直さない。

- 何が分かったか・分からなくなったかを聞く（進捗率は聞かない。判断に使えない）
- **残りだけ**を引き直す。終わった部分の再分解は無駄
- ズレの原因が未知の見落としなら、そこを明示してから割り直す
- 「まだ判断できない」が答えとして正当なことを伝える。ただし**いつ判断するかは決める**。ここを空にしたまま次の日に送ると、同じ会話が毎日繰り返される
