# ハッシュテーブル

`if item in huge_list:` をループの中で書いたら地獄のように遅くなった。`huge_list` を `set` に変えた瞬間、数分が数秒になった——この魔法の正体がハッシュテーブル。Python で最も重要なデータ構造で、`dict` と `set` の中身がこれ。

## 仕組み：キーから保管場所を直接計算する

ハッシュテーブルは「キーをハッシュ関数に通して、格納すべき位置（バケツ番号）を直接算出する」方式。探すときも同じ計算をするだけなので、**データ量に関係なくほぼ一定時間 O(1)** で出し入れできる。

```python
seen = set()
for record in records:          # 100万件でも
    if record.id in seen:       # この判定は O(1)
        continue
    seen.add(record.id)
```

list の `in` は先頭から総当たり O(n) なので、ループ内で使うと全体が O(n²) になる。**「in を使うなら set/dict」**はPython の性能問題の半分を解決する経験則。

## ハッシュ衝突と「hashable」

異なるキーが同じバケツに割り当たる（衝突）ことはあり、その場合は同じバケツ内で追加の照合をする。衝突が増えると性能が劣化するため、テーブルは自動で拡張される——利用者は意識しなくてよいが、「O(1) は平均であって保証ではない」程度は知っておく。

実務で先に効いてくるのはキーの制約のほう。**キーにできるのはハッシュ値が不変なもの（hashable）だけ**：

```python
d = {}
d[("api", 443)] = "ok"     # タプルはOK（不変）
d[["api", 443]] = "ok"     # TypeError: unhashable type: 'list'
```

リストや dict をキーにしたければタプルや frozenset に変換する。「なぜ list はキーにできないのか」の答えは「中身が変わるとハッシュ値が変わり、格納場所を見失うから」。

## セキュリティの余談：ハッシュは攻撃対象になった

ハッシュ衝突は攻撃にも使われた。攻撃者が**意図的に衝突するキーを大量に送る**と、O(1) のはずのテーブルが O(n) に劣化し、少ないリクエストで CPU を食い潰せる（hash flooding DoS、2011年に主要言語が軒並み影響を受けた）。この対策として Python の `hash()` は**プロセスごとにランダム化**されている——`python -c "print(hash('a'))"` の結果が実行のたびに変わるのはこのため。「dict の順序や hash 値に依存したコードを書くな」という規範には、こういう背景もある。
