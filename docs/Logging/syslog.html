syslog と rsyslog / syslog-ng

ログが各サーバの中にしか無いと、調べたいときには消えている。それを一箇所に集めるのが syslog の仕事。

「あのとき何が起きたか」を後から調べられるか

サーバが 1 台なら /var/log を見れば済む。台数が増えると事情が変わる。障害の切り分けで何台も SSH して回ることになるし、ログはローテーションで消える。さらに厄介なのは、侵入されたサーバのログは、侵入者に消されること。手元にしか無い記録は証拠にならない。

syslog は「ログを書いたホストの外へ転送し、別のホストに保存する」ための仕組み。1980 年代から使われている枠組みで、いまも Linux・ネットワーク機器・アプライアンスがほぼ共通して喋れる数少ない共通語になっている。

アプリは「どこに書くか」を知らない

syslog の設計で一番効いているのはここ。ログを出す側は、出力先のファイル名も転送先の IP も指定しない。ファシリティ（どの種類のログか）とプライオリティ（どれくらい重大か）のラベルを付けて投げるだけで、行き先の判断は受け取る側（rsyslog / syslog-ng）の設定に任せる。だから「認証ログだけ別ファイルに」「err 以上だけ集約先へ」といった変更を、アプリに手を入れずに設定だけで実現できる。

ファシリティとプライオリティ

ファシリティは auth / authpriv / cron / daemon / kern / mail / syslog / user など。自作アプリには local0〜local7 が空けてあるので、そこを割り当てて使う。

プライオリティ（＝severity）は 8 段階。設定で .warning と書くと「warning 以上」、つまり数値の小さい側すべてが対象になる。

値名前だいたいの意味
0emergシステムが使用不能
1alert即座に対応が必要
2crit致命的
3errエラー
4warning警告
5notice正常だが注意すべき事象
6info通常の情報
7debugデバッグ用

いまのメッセージの通り道

systemd のディストリビューションでは、アプリの出力をまず systemd-journald が受け取る。journalctl で読めるのはこれ。rsyslog はそこから取り出して、テキストファイルへの書き出しと外部への転送を担当する、という分担になっている。

rsyslog の設定

本体は /etc/rsyslog.conf、追加分は /etc/rsyslog.d/*.conf。ファイル名の数字順に読まれるので、自分の設定は /etc/rsyslog.d/ に置く。本体を直接編集するとパッケージ更新で衝突する。

どこに書くかを決める（送る側）

# /etc/rsyslog.conf（抜粋）
# 「ファシリティ.プライオリティ  出力先」の 1 行が 1 ルール

# info 以上を messages へ。ただし mail/authpriv/cron は除く（none ＝ 対象外）
*.info;mail.none;authpriv.none;cron.none    /var/log/messages

# 認証系だけ別ファイルに
authpriv.*                                  /var/log/secure

# 自作アプリを local0 に割り当てた場合
local0.*                                    /var/log/myapp.log

集約サーバへ転送する

# /etc/rsyslog.d/60-forward.conf
*.* action(type="omfwd"
           target="10.0.0.5" port="514" protocol="tcp"
           # 送信先が落ちている間はディスクに退避して、復旧後に送り直す
           queue.type="linkedList"
           queue.filename="fwd-central"
           queue.maxDiskSpace="1g"
           queue.saveOnShutdown="on"
           action.resumeRetryCount="-1")

古い書き方の *.* @@10.0.0.5:514（@@ ＝ TCP、@ ＝ UDP）も動くが、キューが付かないので送信先が落ちた瞬間からログが落ちる。新規に書くなら action() 形式にする。

受け取る側

# /etc/rsyslog.d/10-receive.conf
module(load="imtcp")
input(type="imtcp" port="514")

# ホスト名／プログラム名ごとにファイルを分ける
template(name="PerHost" type="string"
         string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log")

if $fromhost-ip != "127.0.0.1" then {
    action(type="omfile" dynaFile="PerHost" createDirs="on")
    stop   # ここで打ち切らないとローカルの messages にも混ざる
}

構文チェックは rsyslogd -N1。反映は systemctl restart rsyslog。

syslog-ng の設定

やることは同じで、書き方の思想が違う。rsyslog が「1 行 1 ルール」なのに対し、syslog-ng は入口（source）・条件（filter）・出口（destination）を別々に定義して、log 文で組み合わせる。部品を使い回せるので、経路が増えるほど読みやすくなる。設定は /etc/syslog-ng/syslog-ng.conf と /etc/syslog-ng/conf.d/*.conf。

@version: 4.5

source s_local  { system(); internal(); };          # ローカルのログを受ける
filter f_auth   { facility(auth, authpriv); };
filter f_err    { level(err..emerg); };             # err 以上

destination d_auth    { file("/var/log/auth.log"); };
destination d_central { syslog("10.0.0.5" transport("tcp") port(514)); };

log { source(s_local); filter(f_auth); destination(d_auth); };
log { source(s_local); filter(f_err);  destination(d_central); };
# 受け取る側
source s_net { syslog(transport("tcp") port(514)); };
destination d_perhost {
    file("/var/log/remote/${HOST}/${PROGRAM}.log" create-dirs(yes));
};
log { source(s_net); destination(d_perhost); };

構文チェックは syslog-ng --syntax-only。

rsyslogsyslog-ng
既定採用RHEL 系・Ubuntu の多くSUSE 系ほか。他は追加インストール
設定の形1 行 1 ルール（＋action() 形式）source / filter / destination の組み合わせ
向いている場面既定のまま少し足す経路や加工が多く、構造化して管理したい

どちらも UDP/TCP/TLS 転送・ディスクキュー・ファイル分割はできる。入っているほうを使えばよく、乗り換える理由になるほどの機能差は普通の用途では出ない。

UDP のままにしない。 514/UDP は再送も到達確認もなく、送信元 IP の詐称も容易。「攻撃者が偽のログを流し込んで本物を埋める」が成立する。集約は TCP を既定にし、拠点をまたぐ・監査に使うなら TLS（6514）にする。

動作確認

# 任意のファシリティ・プライオリティでテストログを流す
logger -p local0.err "test message from $(hostname)"

# 受け取れているか集約サーバ側で確認
tail -f /var/log/remote/web01/root.log

集約先に届かないときの確認順は、ss -lntup | grep 514（受信側が待ち受けているか）→ ファイアウォール／セキュリティグループ → SELinux（semanage port -l | grep syslog）。設定ミスより経路で止まっていることのほうが多い。
