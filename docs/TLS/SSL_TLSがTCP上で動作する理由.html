SSL/TLS が TCP 上で動作する理由

「UDP ではだめなのか」に答えられると、DTLS も QUIC も繋がって理解できる。

何が問題なのか

TLS は「トランスポート層セキュリティ」という名前のとおり、トランスポート層の上に乗る。実際に使われるのはほぼ TCP の上で、UDP の上に直接乗せることはできない。なぜか。「TCP のほうが信頼性が高いから」で終わらせると、では DTLS は何をして UDP 上で成立させたのか、QUIC はなぜ TCP をやめられたのかが説明できなくなる。

答えは、TLS 自身が「順序どおり・欠けなく届くこと」を前提に作られていて、その前提を自分では回復できないから。

1 バイト欠けると、そのレコードは復号できない

TLS は、アプリから受け取ったデータをレコードという単位に区切り、暗号化して MAC（改ざん検知用の値）を付けて送り出す。受信側はレコードを丸ごと揃えてから復号し、MAC を検証する。

ここで、パケットが 1 つ失われたり順番が入れ替わったりすると何が起きるか。レコードのバイト列が欠けるので復号できない。無理に復号しても MAC が合わない。そして TLS には、MAC が合わなかったときの選択肢が「接続を切る」しかない。改ざんされたのか単に届いていないのかを、TLS からは区別できないからだ。

UDP でやるなら、TCP の仕事を自分で持つことになる

音声や映像、DNS のように「多少落ちてもいいから速く」という通信では、TCP の再送はむしろ邪魔になる。それでも暗号化はしたい。そこで作られたのが DTLS で、やったことはTLS が TCP に任せていた部分を、TLS 側に作り直すことだった。各レコードに明示的なシーケンス番号を持たせて 1 つずつ独立に復号できるようにし、ハンドシェイクだけは順序と完全性が必須なので専用の再送とフラグメント処理を用意した。

同じ発想をさらに進めたのが QUIC で、こちらは TCP をやめて UDP の上に再送・順序制御・暗号化をまとめて実装した。TCP と TLS で別々だったハンドシェイクを 1 つに統合できたので、接続確立の往復が減っている（HTTP/3 と QUIC）。

TCP を挟むことの代償

TCP が順序を保証するということは、1 つのパケットが失われると、その後ろに届いているデータも渡してもらえないということでもある（ヘッドオブラインブロッキング）。TLS レコードは複数の TCP セグメントにまたがるので、影響はさらに大きくなる。「信頼できる下位層に任せる」という設計は単純さと引き換えに、この待ちを受け入れている。
