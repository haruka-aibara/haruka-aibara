TLS ハンドシェイクと証明書検証をゼロから理解する

鍵マークの裏で、実際に何が確認されているのか。ハンドシェイクから証明書検証・失効確認までを1本につなぐ。

https でつながっているとき、何が確認されているのか

「鍵マーク＝暗号化されている」とだけ理解していると、TLS の半分を見落とす。TLS がやっているのは3つある。相手が名乗ったホスト本人か（認証）／経路で読まれないか（機密性）／途中で書き換えられていないか（完全性）。

そして順番が肝心で、認証が先、鍵の共有が後。逆にすると、中間者と仲良く暗号通信を確立して終わる。暗号化は「誰と」が確定していて初めて意味を持つ。

その前に、なぜ TCP の上なのか

TLS は下位層が「欠けず・重複せず・順番どおり」届けることを前提に作られている。レコードのバイトが1つでも欠ければ復号も改ざん検知も通らないので、欠落と順序の面倒は TCP に任せている。詳しくはSSL/TLS が TCP 上で動作する理由。

ハンドシェイクの流れ

段取りは4つ。暗号スイートの合意 → 証明書の提示 → 鍵の共有 → 暗号化通信の開始。

押さえるのは、①〜④が平文で流れること。暗号スイートの合意そのものを改ざんして弱い暗号に落とすのがダウングレード攻撃で、これを防いでいるのが最後の Finished ——ここまでの全メッセージのハッシュを鍵付きで送り合うので、途中で1バイトでも書き換えられていれば一致せず接続が切れる。

プレマスタシークレット → マスタシークレット → セッション鍵

共有した秘密（プレマスタシークレット）はそのまま暗号鍵にしない。①②で交換した双方の乱数を混ぜてマスタシークレットを作り、そこから用途別・方向別のセッション鍵（暗号化用と MAC 用、送信方向と受信方向で別）を導出する。

乱数を混ぜるのは、同じ鍵が二度と再現されないようにするため。毎回同じ鍵になるなら、記録しておいた過去の通信をそのまま投げ返す再生攻撃が成立する。鍵の作り方2通りはプレマスタシークレットにある。

Record プロトコルが実データにしていること

以降のデータを扱うのが Record プロトコル。扱える大きさに分割し、改ざん検知用の MAC を付け、セッション鍵で暗号化し、ヘッダを付けて TCP に渡す。

MAC がないとどうなるか。暗号文は読めなくても、ビットを反転させて中身を狂わせることはできる。「読めない」と「変えられない」は別物で、後者を担うのが MAC（現在の AEAD 暗号は両方を一体で行う）。詳細は Record プロトコル。

受け取った証明書を検証する

サーバが証明書を出してきた時点では、まだ何も証明されていない。証明書は誰でも自分で作れるからだ。クライアントは4点を確認する。

4点のどれを省いても穴になる。連鎖を見なければ攻撃者の自作証明書が通るし、名前を照合しなければ攻撃者が自分のドメインで正規に取得した証明書で他サイトになりすませる。ホスト名の照合は、かつての CN ではなく SAN（Subject Alternative Name）で行うのが現在の仕様。

失効確認：CRL と OCSP

秘密鍵が漏れた証明書は、放っておけば期限まで有効なまま使える。だから「この証明書はまだ生きているか」を発行元に問い合わせる仕組みが要る。

失効確認を一切しないと、秘密鍵が漏れて取り消し済みの証明書が、期限が来るまで使われ続ける。OCSP の負荷とプライバシーを緩和する OCSP ステープリングは、サーバが自分の分の応答をあらかじめ取得してハンドシェイクに同梱する方式。詳しくはCRL と OCSP。

登場人物：CA / RA / IA / VA

ここまでの「発行元」は、実務では役割が分かれている。

役割担当
CA認証局全体。ポリシを定め、証明書を発行する主体
RA申請の受付と本人・ドメイン所有の確認（登録局）
IA実際に鍵と証明書を生成する（発行局）
VA失効情報を提供する。CRL や OCSP レスポンダの側（検証局）

分けている理由はCA・RA・IA・VA にある。

鍵マークが出ていても安全とは限らない

DV 証明書が証明しているのは「申請者がそのドメインを操作できた」ことだけ

運営者が誰かも、サイトの中身が安全かも証明していない。フィッシングサイトでも、自分で取得したドメインなら数分で鍵マークが付く。example-bank-login.com で正規の鍵マークが出ている状況は普通に起こる。鍵マークが保証するのは「暗号化されている」「アドレスバーのホスト名と証明書が一致している」までで、その先は利用者がホスト名を読むしかない。→ DV・OV・EV

もう一つは企業内の TLS 復号プロキシ。端末にプロキシのルート証明書が配布されていれば検証は正常に通り鍵マークも出るが、通信はプロキシで一度復号されている。中間者攻撃と技術的には同じ構造で、違いは端末の管理者が意図して信頼させたかどうかだけ。

症状原因切り分けの観点
ブラウザでは正常、curl や古い端末・アプリだけエラー中間 CA 証明書がサーバから配信されていないブラウザは過去に見た中間 CA をキャッシュしたり自力で取得したりして繋がってしまう。サーバが返す証明書チェーンを直接確認する
名前が一致しないというエラーSAN に接続先ホスト名がないwww 有無、ワイルドカードの階層（*.example.com は a.b.example.com に一致しない）、IP アドレス直打ちでのアクセス

UDP の上でやるなら

TLS は TCP の順序保証に寄りかかっているので、UDP の上ではそのまま動かない。欠落と順序入れ替えを自前で吸収して TLS 相当を実現するのが DTLSで、VPN や WebRTC で使われている。
