DTLS — UDP の上で TLS 相当の保護を成立させる

パケットが落ちる・順番が入れ替わる前提で、暗号化とハンドシェイクをやり切る。

何が問題なのか

音声通話、映像配信、オンラインゲーム、IoT の小さなセンサー。これらが UDP を使うのは、再送を待つより落ちたぶんを捨てて先へ進むほうがよいから。0.5 秒遅れて届く音声は、届かないのと変わらない。

ところが TLS は TCP を前提に作られている。「前のバイトが確実に届いている」ことに依存しているので、そのまま UDP には載らない。かといって暗号化を諦めるわけにもいかない——ここを埋めるのが DTLS（Datagram TLS）。

TLS からの変更点

  • 順序番号を明示的に送る：TLS では両者が数えているだけだった番号を、DTLS ではパケットに書いて送る。順番が入れ替わって届いても正しく復号できる。
  • ハンドシェイクに再送タイマを持つ：ハンドシェイクのメッセージが落ちると先へ進めないので、ここだけは自前で再送する。
  • ハンドシェイクを分割できる：証明書はデータグラムの大きさに収まらないことがあるため、分割して送り、受信側で組み立てる。
  • リプレイ検知の窓を持つ：過去に受け取った番号を記録し、同じパケットの再投入を弾く。

UDP ならではの危険：増幅攻撃

UDP は送信元アドレスを簡単に偽れる。攻撃者が被害者のアドレスを名乗ってハンドシェイクを始めると、サーバは証明書を含む大きな応答を被害者へ送りつける。小さなリクエストで大きな応答を撃たせる——DNS を使った反射増幅攻撃とまったく同じ構図になる。

どこで動いているか

  • WebRTC：ブラウザの音声・映像通話。DTLS で鍵を交換し、実際のメディアは SRTP で暗号化する。
  • IoT：CoAP という軽量プロトコルの標準的な保護手段。
  • VPN 製品：TCP の上に TCP を通すと効率が落ちるため、UDP＋DTLS を主経路にして、通らない環境だけ TCP に落とす構成が多い。

なお QUIC は DTLS を使っていない。同じく UDP の上で暗号化するが、TLS 1.3 のハンドシェイクを直接組み込んだ別の設計になっている。
