# Slack ワークフローの作り方

「毎朝の勤怠報告を自動化したい」「問い合わせをフォームで受け付けて担当チャンネルに流したい」——Slack で手作業を自動化しようと調べ始めると、最初にぶつかるのがこれ。

**ワークフロービルダーはフリープランでは使えない。**

管理画面をいくら探しても「ワークフロー」のメニューが出てこないのは、設定が悪いのでも権限が足りないのでもなく、プランの問題。ここを知らずに数十分溶かす人が多いので、まずそこから。

---

## 前提：プランの話

| プラン | ワークフロービルダー | 料金の目安（2026年時点・年払い/ユーザー/月） |
|---|---|---|
| フリー | **使えない** | 0 円 |
| Pro | 使える | 925 円 |
| Business+ | 使える | 1,920 円 |
| Enterprise Grid | 使える | 個別見積もり |

月払いにすると年払いより 1〜2 割高くなる。金額は改定されるので、稟議を書く前に必ず[公式の料金ページ](https://slack.com/intl/ja-jp/pricing)で確認すること。

### 「ワークフローのためだけに有料化」は通るのか

社内で通しやすいのは、ワークフロー単体ではなく**フリープランの制約とセットで説明する**やり方。

| 技術的な言い方 | 予算を握っている人に刺さる言い方 |
|---|---|
| ワークフロービルダーが使えない | 定例の報告・申請・依頼受付を人手でやり続けている。1人月あたり数時間が固定で消えている |
| メッセージ履歴が 90 日で見えなくなる | 「あの障害のときどう判断したか」が半年後には残っていない。引き継ぎも監査対応もできない |
| アプリ連携が 10 個まで | 通知の集約先を Slack に寄せられず、監視・CI の結果を各ツールに見に行く運用が残る |

有料化は「便利機能が増える」ではなく「いまお金と時間を払って埋めている穴が塞がる」という話にすると、判断する側が比較できるようになる。

### まず試したいなら

いきなり課金しなくても、**有料プランの無料トライアル**でワークフロービルダーを触れる。作りたいワークフローが 1〜2 個決まっているなら、トライアル中に実際に組んで「これが毎日動く」状態を見せたほうが、機能一覧を説明するより早く話が進む。

> 注意：トライアル終了やダウングレードでフリープランに戻ると、ワークフローは動かなくなる。「一度作ったから残る」ものではない。

## 誰が作れるかを先に決める

有料プランにすると、**デフォルトでは全メンバーがワークフローを作れる**。触れる状態にしてから設計を考えるのではなく、逆にしたほうがいい。

放置すると起きること：

- 同じ通知が複数のワークフローから二重に飛ぶ
- 作った本人が退職・異動して、誰も中身を知らないワークフローが動き続ける
- 外部サービスに書き込むワークフローが、レビューなしで本番データを触る

`設定と権限` → `権限` → `ワークフロービルダー` で、作成できる人を絞れる。2024年10月以降、標準ワークフローとプレミアムワークフロー（コネクタステップやカスタムステップを含むもの）を分けていた権限は**「プレミアムを含むすべてのワークフローを公開する」という単一の権限に統合**されている。細かく分けるのではなく「誰に許すか」だけを決める形。

小さいチームなら全員許可でいい。ただし**運用ルールは先に決める**：命名規則、置き場所（どのチャンネルに紐づけるか）、そして「作った人が異動したらどうするか」。

管理者は `管理` → `ワークフロー` から、ワークスペース内の全ワークフローを一覧できる。誰が何を作ったか・実行できる人は誰かがここで見えるので、権限を絞る前後で必ず確認しておくといい。

## 作り方の基本構造

ワークフローは **トリガー（いつ動くか） + ステップ（何をするか）** の 2 つだけ。ここを押さえれば UI は迷わない。

```
トリガー：毎週月曜 10:00
   ↓
ステップ1：#team-dev にメッセージを送る
   ↓
ステップ2：フォームを表示して今週の予定を入力させる
   ↓
ステップ3：入力内容を #team-dev に投稿する
```

### 主なトリガー

| トリガー | こういうときに使う |
|---|---|
| リンク・ボタンから | 「申請はこのボタンから」と固定して運用する |
| スケジュール | 定例のリマインド、週次の報告依頼 |
| チャンネルに参加したとき | 新メンバーへのオンボーディング案内 |
| 絵文字リアクション | 特定の絵文字を付けたら別チャンネルにエスカレーション |
| Webhook | 外部システム（監視、CI、業務システム）から叩いて起動 |

トリガーの種類は増え続けているので、作る前に一度 UI の一覧を眺めておくといい。

### 主なステップ

- メッセージを送る（チャンネル / DM）
- フォームを表示して入力を受け取る
- 前のステップの入力内容を後続で使う（変数として差し込める）
- 承認待ちにする（誰かの返答で分岐）
- コネクタで外部サービスを操作する（スプレッドシートに追記、チケット作成 など）

### 実際の作成手順

1. サイドバーの `その他` → `オートメーション` → `ワークフロー` → `新規ワークフロー`
2. トリガーを選ぶ
3. ステップを順に足す
4. 右上の `公開する` を押す

実際にキャプチャを取りながら作った記録は [Slack ワークフローを実際に作ってみる](./Slackワークフローを実際に作ってみる.md) を参照。

**公開するまでは動かない。** 保存しただけで動くと思って「なんで通知が来ないんだ」となるのは定番のハマりどころ。

## 外部サービスと繋ぐとき（コネクタ）

Google スプレッドシート、Jira、Salesforce などに書き込むステップは「コネクタ」と呼ばれる。ここで詰まりやすいのは 2 点。

**1. 管理者の事前設定が要るコネクタがある**

メンバーが自分で繋げるものと、ワークスペース管理者が先に接続を許可しておく必要があるものがある。Workflow Builder 上から管理者に設定をリクエストできるので、権限がなくて詰まったらそこから依頼する。

**2. 料金は気にしなくてよくなった**

以前はコネクタステップを 2 つ以上使うワークフロー（プレミアムワークフロー）に実行回数ベースの従量課金があった。**2024年9月25日にこの従量課金は廃止**され、有料プランなら実行回数で追加請求されることはない。ネット上には従量課金前提の古い記事が残っているので、コスト試算のときは注意。

## Webhook トリガーを使うときの注意

外部から Slack ワークフローを起動できる Webhook トリガーは強力だが、**発行される URL は「知っていれば誰でも叩ける」認証情報そのもの**として扱う必要がある。

- URL を GitHub のコードや設定ファイルに直書きしない。Secrets / パラメータストアに置く
- 誤って公開したら、ワークフローを作り直して URL を再発行する（URL 単体のローテーション手段はない前提で設計する）
- Webhook で起動するワークフローに「承認」「本番操作」を含めない。起動できる＝実行できる、になる

CI から Slack に通知を送るだけなら、Webhook トリガーより GitHub の Slack アプリや `slackapi/slack-github-action` を使ったほうが管理が楽なことも多い。ワークフロービルダーは「Slack の中で人が動く業務」を自動化するもの、と割り切ると設計がぶれない。

---

## まとめ

- ワークフロービルダーは有料プラン（Pro 以上）専用。フリープランではメニュー自体が出ない
- 有料化の説明は「機能が増える」ではなく「いま人手で埋めている穴」の話にする
- 作れる人を先に絞り、命名と引き継ぎのルールを決めてから解放する
- 構造は「トリガー + ステップ」。公開するまで動かない
- コネクタの従量課金は 2024年9月に廃止済み。古い記事の情報に注意
- Webhook の URL は認証情報として扱う
