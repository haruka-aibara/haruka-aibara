# ADR の要否を AI に判断させるリポジトリ設計

AI がコードを書く割合が増えると、意思決定の文脈が急速に消えていく。「なぜこの構成にしたか」は AI とのチャットログ、Slack のスレッド、担当者の頭の中に散らばり、どれもリポジトリには残らない。半年後に別の人（または別の AI セッション）が同じ議論をゼロからやり直し、下手をすると過去に捨てた選択肢を採用し直す。

ADR（Architecture Decision Record）はこの問題への古典的な回答だが、「重要な決定をしたら ADR を書きましょう」という運用ルールは、人間の記憶と意識に依存している時点でだいたい形骸化する。シニアは面倒がって書かず、ジュニアは何が「重要な決定」なのか判断できない。

発想を変える。**「ADR を書くべきかどうか」の判断自体を、PR を作る AI にやらせる。** Claude Code は `CLAUDE.md` を毎セッション読むので、そこに判断基準を書いておけば、リポジトリで作業する全員が——ジュニアでもシニアでも、ルールの存在を知らなくても——同じ基準で判断された状態になる。人間向けの運用ルール文書は読まれないが、CLAUDE.md は PR を作る AI が毎回読む。これが効く理由のすべてで、ここに書く仕組みに CI もフックも登場しない（「毎回読む」が保証でないことへの向き合い方は、末尾の運用ポイントで扱う）。

目指す状態はこう：

- 意思決定はすべて MADR ベースの形式で `docs/decisions/` にあり、AI は作業前にそこを読んで既存の決定と矛盾しない変更をする
- ADR に値する変更を含む PR を作ろうとすると、AI が「これは ADR として残すべき決定を含んでいます」と言い、ADR 案を作って PR に含める
- ADR に値しない変更なら、AI は会話では ADR に言及せず黙って PR を進める（「不要と判断しました」という報告すらしない。PR 本文のチェック欄だけが判断の痕跡として残る）

以下、AWS アカウントのセキュリティ機能（CloudTrail・GuardDuty・Security Hub・AWS Config 等）を Terraform で管理するリポジトリを題材に、この状態を作るためのファイル一式を示す。**そのままコピーして固有名詞を差し替えれば使える**ことを目的に、仕組みを構成する 5 ファイルの全文を載せる（`terraform/` 配下とルートの README.md は各自の実装・説明なので範囲外）。

## リポジトリ構造

```
.
├── CLAUDE.md                      # AI への常時指示。ADR の判断基準はここ
├── README.md
├── docs/
│   ├── decisions/                 # 意思決定の記録（MADR ベース）
│   │   ├── README.md              # 人間向けの運用説明
│   │   ├── template.md            # ADR の雛形
│   │   └── 0001-guardduty-findings-は自動修復せず通知に留める.md
│   └── runbooks/                  # 運用手順書
│       └── guardduty-finding-triage.md
├── terraform/
│   ├── modules/
│   │   ├── cloudtrail/
│   │   ├── guardduty/
│   │   ├── security-hub/
│   │   └── config-rules/
│   ├── main.tf
│   ├── variables.tf
│   └── backend.tf
├── scripts/                       # 棚卸し・監査用スクリプト等
└── .github/
    └── PULL_REQUEST_TEMPLATE.md   # ADR 判断の可視化
```

ポイントは 2 つ。

- **文脈になりうるものをすべてリポジトリ内に置く。** Terraform コードだけでなく、runbook・スクリプト・意思決定を同居させる。MCP 等で Slack や Confluence に接続することもできるが、権限・検索精度・再現性を考えると、AI が恒常的に頼れる文脈はリポジトリの中身だけ。リポジトリ外にしかない合意は「無いもの」として扱われる前提で設計する
- **`docs/decisions/` のファイル名自体を情報にする。** `0001-guardduty-findings-は自動修復せず通知に留める.md` のように、ファイル名だけで決定内容がわかるタイトルにする。AI も人間も、全文を読まず一覧を見るだけで関係する決定を拾える。だからインデックスファイルも作らない（更新漏れで腐るだけ）

## CLAUDE.md（全文）

仕組みの本体。判断基準は抽象論ではなく、このリポジトリで実際に起きる例つきで書く。例がないと AI の判断がブレる。

```markdown
# リポジトリ概要

AWS アカウントのセキュリティ機能（CloudTrail・GuardDuty・Security Hub・AWS Config 等）を
Terraform で管理するリポジトリ。運用手順書（docs/runbooks/）と運用スクリプト（scripts/）も
ここに置く。

- 単一アカウント前提
- AI は AWS に接続しない。terraform plan / apply は人間が実行する。AI の作業は PR 作成まで

# 意思決定の記録（ADR）

このリポジトリに関する意思決定は docs/decisions/ に MADR ベースの形式で置いてある。
**このリポジトリの「なぜ」はすべてここにある。** ここに書かれていない合意
（Slack・口頭など）は、このリポジトリの文脈として存在しないものとして扱う。

## 作業を始める前に

docs/decisions/ の一覧を確認し、変更対象に関係する ADR を読む。ファイル名が決定内容に
なっているので、一覧を見れば関係の有無は判断できる。

- 既存の決定に沿う変更なら、そのまま進める
- 既存の決定と矛盾する変更を求められたら、作業を始める前にその ADR を挙げて指摘する。
  それでも進めることになったら、新しい ADR で置き換え、古い ADR のステータスを
  「失効（NNNN に置き換え）」に更新する（両方を同じ PR に含める）

## PR を作る前に：ADR の要否を毎回判断する

PR を作成する前に、その変更が「記録すべき意思決定」を含むかを判断する。

**ADR を書くべき変更**（1 つでも当てはまれば該当）：

- 複数の妥当な選択肢から 1 つを選んだ
  （例：Findings の通知経路を EventBridge → SNS 直結にするか Security Hub 集約にするか）
- セキュリティと運用負荷・コストのトレードオフを取った
  （例：あえて有効化しない Security Hub コントロール、CloudTrail ログの保持期間）
- 後から元に戻すコストが高い
  （例：ログアーカイブ用 S3 バケットの構成、KMS キーの構成、ステート管理方式）
- モジュールを横断する規約・方針を決めた
  （例：タグ付け規約、命名規則、モジュール分割の方針）
- 例外を許容した
  （例：特定リソースだけ Config ルールの評価対象から外す）

**ADR が不要な変更**（黙って PR を進めてよい）：

- 既存 ADR で決まった方針の実装・展開
- プロバイダ・モジュールのバージョン追随
- バグ修正、typo 修正、外部から見た構成が変わらないリファクタリング
- 既存パターンの単純な繰り返し（例：既存の書き方に沿って Config ルールを 1 つ足す）
- 理由が diff から自明なパラメータ調整

両方のリストに当てはまりそうな場合（例：ログ保持期間の変更は「パラメータ調整」だが
コストと調査可能性のトレードオフを含む）は、**「書くべき」側を優先する**。

## 判断した後の動き

- **必要**：docs/decisions/template.md から ADR を作成し、同じ PR に含める（ファイル名・番号・
  ステータスの規約は docs/decisions/README.md に従う）。選択肢と採用理由は会話の文脈から
  書き起こし、埋められない部分（検討したが会話に出ていない選択肢など）は
  ユーザーに確認する。ユーザーに聞けない実行形態（CI 上の自動実行など）では、埋められない欄を
  {要確認} のまま残して PR レビューで人間が埋める
- **不要**：会話では ADR に言及せず PR を進める。「ADR は不要と判断した」という報告もしない
- **迷う**：「この決定は ADR に残しますか」と 1 回だけ聞く。ユーザーが不要と言ったら従う。
  ユーザーに聞けない実行形態では、ADR 案を PR に含めて要否ごとレビューに委ねる

いずれの場合も、**PR 本文の「ADR」セクションには該当する行を残す**。これはテンプレートの
記入であって報告ではないので、「不要なら言及しない」の対象外。
```

## docs/decisions/README.md（全文）

AI 向けの指示は CLAUDE.md にあるので、こちらは人間（特に初見の人）向け。同じ内容を二重管理すると必ずズレるので、置き場所はそれぞれ 1 つに決めて互いに参照する：**判断基準は AI が毎回使うから CLAUDE.md に、ファイル名・番号・ステータスの規約は書くときだけ必要だから README に**。この分担は CLAUDE.md を小さく保つことにも効く。

ステータスは MADR 標準の accepted / deprecated / superseded ではなく「有効／失効」の 2 値にしている。日本語話者しか触らない前提のリポジトリで英単語のステータスを使っても、読み手に翻訳を 1 段強いるだけで得るものがない。実際に必要な区別は「今も効いているか」だけで、置き換え先は失効の注記で示せば足りる。「無効」ではなく「失効」なのは、かつて有効だった決定が効力を失った、という実態に合う語だから。

```markdown
# 意思決定の記録（ADR）

このディレクトリには、このリポジトリに関する意思決定を
[MADR](https://adr.github.io/madr/) ベースの形式で記録している。

## なぜあるか

「なぜこの構成なのか」を、人と AI の両方が参照できる場所に残すため。ここに書かれていない
合意（Slack・会議・チャットログ）は、時間が経つと存在しないのと同じになる。
変更を提案する前に、関係する ADR を読むこと。

## いつ書くか

目安：**半年後に来た人（または AI）が、diff とコミットログだけでは理由を復元できない決定**を
したとき。具体的な判断基準はリポジトリルートの CLAUDE.md にあり、Claude Code で PR を作る
場合は AI が要否を判断して必要なら起案する。手で書く場合も同じ基準に従う。

実装の詳細・バグ修正・バージョン追随には書かない。ADR が多すぎると誰も読まなくなり、
少なすぎると意味がない。「決定」だけを残す。

## 書き方

1. `template.md` をコピーして `NNNN-タイトル.md` を作る（NNNN は 4 桁連番、既存の最大値 + 1。
   並行する PR で番号が衝突したら、後からマージされる側が振り直す。番号に意味は持たせない）
2. タイトルは「何を決めたか」がファイル名だけでわかる形にする
   （例：`0001-guardduty-findings-は自動修復せず通知に留める.md`）
3. 決定を実装する PR と同じ PR に含める
4. インデックスファイルは作らない。`ls` の結果が一覧になる

## ステータスの扱い

- `有効`：現在も効いている決定
- `失効`：もう効いていない決定。置き換え先があれば `失効（NNNN に置き換え）` と書く

一度有効になった ADR の本文は書き換えない。決定が変わったら新しい ADR を書き、
古い方はステータス行だけを更新する。履歴を改変しないことで「当時なぜそう決めたか」が残る。
```

## docs/decisions/template.md（全文）

MADR をベースに、埋まらない項目が形骸化しない程度まで削ったもの。決定者の欄はあえて置かない。決定の主体は個人とは限らない——チームの合意のこともあれば、組織側の方針や監査・外部要件で決まってくることもあり、個人名の欄はそのどれにも合わない。誰がいつ承認したかは PR の履歴に残るので、文書側で二重管理もしない。決定が組織方針・外部要件由来なら、そのことは「文脈と課題」に書く。

```markdown
# {決定内容がわかるタイトル}

- ステータス: 有効
- 日付: {YYYY-MM-DD}

## 文脈と課題

{どういう場面で、何を決める必要があったか。2〜5 行}

## 検討した選択肢

- {選択肢 1}
- {選択肢 2}
- {選択肢 3}

## 決定

{選択肢 X} を採用する。

{理由。決め手になったトレードオフを書く}

## 影響

- {この決定によって今後どうなるか}
- {受け入れたリスク・負債があれば明記する}
- {再検討の条件・時期があれば書く}
```

## サンプル ADR（全文）

最初の 1 本は書き方の見本を兼ねるので、リポジトリの実際の決定で 1 本入れておく。AI はテンプレートより既存 ADR の実物に強く倣うため、ここの品質が以後の全 ADR の品質を決める。

```markdown
# GuardDuty Findings は自動修復せず通知に留める

- ステータス: 有効
- 日付: 2026-08-01

## 文脈と課題

GuardDuty を有効化するにあたり、Findings 検知後の対応をどこまで自動化するかを決める
必要があった。検知して放置では意味がなく、かといって自動修復（IAM アクセスキーの無効化、
セキュリティグループの自動閉塞など）は誤検知時に業務を止めるリスクがある。

## 検討した選択肢

- EventBridge + Lambda で重要度 High 以上の Findings を自動修復する
- 通知（Slack）のみとし、対応は runbook に従って人間が行う
- 通知のみで開始し、誤検知率の実績を見てから自動修復を段階導入する

## 決定

「通知のみで開始し、実績を見てから段階導入」を採用する。

運用実績がない段階で自動修復を入れると、誤検知で業務を止めたときの説明責任を負えない。
まず 3 か月間通知運用し、Finding タイプごとの誤検知率を記録した上で、誤検知ゼロの
タイプに限って自動化を検討する。

## 影響

- docs/runbooks/guardduty-finding-triage.md に沿って人間がトリアージする（対応工数を受け入れる）
- 夜間の検知に即時対応はできない。このリスクは受容する
- 2026-11 に自動化の再判断を行う
```

## .github/PULL_REQUEST_TEMPLATE.md（全文）

判断の結果を PR 上で可視化する。CLAUDE.md 側で「不要と判断した場合でも該当行は残す」ところまで指示してあるのがポイントで、これがないと「不要なら沈黙しろ」という指示に従った AI はテンプレートも埋めず、可視化の仕組みが AI 経由の PR でこそ機能しなくなる。チャットでは沈黙しても PR には判断結果が残り、レビュアーは異議があればレビューで返せる。逆にこのセクションが空の PR は「判断そのものがされていない」サインとして読める。

強制ではなく可視化に留めるのも意図的で、CI で機械的に強制し始めると「typo 修正にダミー ADR」のような回避行動を生む。

```markdown
## 変更内容

## ADR

<!-- 該当する 1 行だけ残してチェックする -->
- [ ] この PR で ADR を追加した（docs/decisions/NNNN）
- [ ] 既存 ADR（NNNN）の範囲内の変更
- [ ] 記録すべき意思決定を含まない
```

## 運用してみるとわかるポイント

**確率的にしか効かないことを前提に置く。** CLAUDE.md は AI が従う確率を上げる仕組みであって、保証ではない。長いセッションの終盤や文脈の圧縮で指示が抜けることはあるし、Claude Code を通さず手で作られた PR はそもそもこの仕組みを素通りする。だから本体（AI への指示）と検知（PR テンプレートの ADR セクション）の二段構えにする。セクションが空の PR は「判断がされていない」ことがレビュアーに機械的に見える。それでも漏れは出る、という期待値で導入し、漏れに気づいたら、理由を覚えている人がいるうちに後追いで書く。誰も理由を覚えていないなら推測で埋めて書かないこと——後述の通り、間違った理由が書かれた ADR は無い ADR より悪い。

**「不要なら黙る」を明文化しないと壊れる。** 指示がないと AI は律儀に毎回「ADR は不要と判断しました」と報告する。これが続くとシニアほどノイズに感じて仕組みごと無視し始める。「意識せずに使える」は、不要側のケースで完全に沈黙することで初めて成立する。

**判断基準は例で書き、足すのではなく入れ替えて育てる。** 「重要な決定なら書く」では AI も人間と同じように迷う。AI の判断が外れた（書くべきなのに書かなかった／些細なことで ADR を提案してきた）ときは、そのケースを CLAUDE.md の例に反映する。ただし追加一辺倒にしない——各リスト 5 個程度を上限に、古くなった例と入れ替える。足すだけの運用は CLAUDE.md を肥大させて指示全体の遵守率を下げ、後述の成立条件「CLAUDE.md を小さく保つ」を自分で破ることになる。

**既存 ADR を「読ませる」方が「書かせる」より効く。** この仕組みの価値の半分以上は、作業前に `docs/decisions/` を読んで既存決定と矛盾する変更を事前に指摘してくれる側にある。「その変更は 0001 で捨てた選択肢です」と AI が言える状態は、新メンバーのオンボーディングそのものでもある。

**Claude Code 以外でも同じ構造が使える。** 判断基準を AI が毎回読む指示ファイルに置くという構造は、`AGENTS.md` を読む他のコーディングエージェントでもそのまま成立する。ファイル名を差し替えるか、両方から同じ内容を参照させればよい。

## この仕組みが拾えないもの

導入を判断する材料として、敵対的に見て残る限界も正直に書いておく。前段までの構成で解決できるのは問題の一部で、以下は構造的に残る。

**セッションの外で終わった決定は見えない。** この仕組みが検知できるのは、PR を作るセッションの会話に選択の過程が現れた決定だけ。現実には重要な決定ほど会議・チャット・別の壁打ちセッション・依頼者の頭の中で終わっていて、実装セッションには「通知は SNS で」という結論だけが届く。AI から見ればそこに選択肢はなく、判断基準のどれにも引っかからない。つまり**決定の重要度と検知可能性は逆相関する**。緩和策は、選択肢の検討（壁打ち）自体をこのリポジトリを開いた AI 相手にやること。文脈をリポジトリに閉じ込める思想の帰結として、決定の現場ごとセッション内に引き込むのが一番筋がいい。

**可視化が検出できるのは「判断したか」までで、「判断が正しいか」ではない。** PR テンプレートは ADR セクションが空の PR（＝判断されていない）は拾えるが、「記録すべき意思決定を含まない」に誤ってチェックが付いた PR は、正しい判断と見分けがつかない。誤判断を捕まえるのはレビュアーの再判断であり、人間の規律はゼロにはならず、書く側からレビュー側に場所を変えて残る。「ゼロから書く」より「判断結果に異議を出す」方がはるかに軽い、という改善に留まる。

**書きたくないチームには効かない。** 「不要と言われたら従う」は必須の設計（従わない仕組みは丸ごと捨てられる）だが、裏を返せば、毎回「不要」と言う人には以前と同じ状態に戻る。AI の提案が数回外れてアラーム疲れが起きても同じ結末になる。「基準を育てる」ループも、誤判断に気づいて CLAUDE.md の例を直す人間——事実上の ADR の番人——が最低 1 人いる前提で回る。この仕組みは **ADR を書きたいチームの摩擦を下げる装置であって、書きたくないチームに書かせる装置ではない**。

**AI が書き起こす ADR は「もっともらしいが本当の理由ではない」文書になりうる。** 決め手が予算・体制・当時の担当者の事情のような、会話に打ち込まれない理由だった場合、AI は diff と会話から再構成した、もっともらしい別の理由を書く。間違った理由が書かれた ADR は、後から読んだ人が信じるぶん、無い ADR より悪い。だから ADR を含む PR の承認を形式にしないこと。ADR の内容の責任は起案した AI ではなく、承認してマージした人間の側にある。

まとめると成立条件は 3 つ。番人役が最低 1 人いること、CLAUDE.md を小さく保つこと、セッション外の決定は拾えないと割り切る（か、壁打ちからリポジトリ内で行う）こと。それでも比較対象は「完璧な ADR 運用」ではなく「何も書かれない現状」であり、セッション内に現れた決定の何割かが構造化されて残るだけで純増。さらに価値の過半は書かせる側ではなく、作業前に既存 ADR を読ませて矛盾を指摘させる側にある——という期待値で導入するのが正しい。
