セッション管理と入力の扱いをゼロから理解する

対策の名前は言える。「なぜそれで防げるのか」を説明しろと言われると詰まる——その隙間を埋める。

名前を覚えても、記述式では書けない

プリペアドステートメント、HttpOnly、セッション ID の再発行。名前はすぐ出てくる。ところが「なぜその対策で防げるのか」と問われた瞬間、手が止まる。午後試験で採点されるのはまさにそこだ。

Web アプリの守りは、突き詰めると ログイン状態をどう持つか（セッション管理）と外から来た値をどこでどう扱うか（入力の扱い）の 2 本しかない。この 2 本を「何を・どこで・なぜ」で言い切れるところまで整理する。

セッション ID は「本人であること」そのもの

HTTP はリクエストごとに独立していて、前回誰だったかを覚えていない。そこでサーバは認証に成功した時点でセッション ID を発行し、以降はその ID だけを見て「ログイン済みの誰々」と判断する。

つまりセッション ID はパスワードと同じ重みを持つ。攻撃者はパスワードを知らなくても、有効な ID をひとつ手に入れれば本人として振る舞える。連番や「ユーザ ID + 時刻」から組み立てた ID が危険なのは、他人の値を計算で作れてしまうから。要件は暗号論的な擬似乱数で十分な長さ、そして自作しないこと。

ログイン時に ID を再発行する理由

言い切る形にするとこうなる——何を：セッション ID を新規発行して古い ID を破棄する。どこで：認証に成功した直後。なぜ：攻撃者が事前に用意・固定した ID が、認証済みの状態と結びつかないようにするため。

それでも破られる条件：再発行はフィクセーション専用の対策で、ログイン後に新しい ID が盗聴や XSS で漏れれば、ハイジャックは普通に成立する。

ハイジャックとフィクセーションの成立条件

セッションハイジャックセッションフィクセーション
攻撃者に必要なこと被害者の ID を知る（盗聴・XSS・Referer やログからの漏えい）知る必要はない。自分の ID を使わせるだけ
アプリ側の欠陥ID が漏れる経路がある／ID が推測できるログイン前後で ID を変えていない
効く対策推測不能な ID、Secure、HttpOnly、TLS 全面化ログイン成功時の ID 再発行

対策は交換できない。属性をいくら固めてもフィクセーションは防げず（そもそも漏れていない）、再発行してもハイジャックは防げない。

Cookie の属性は、それぞれ別の穴を塞いでいる

セッション ID は普通 Cookie で運ぶ。属性は「まとめて付けておく」ものではなく、1 つずつ塞ぐ穴が違う。属性そのものの構文は別記事にあるので、ここは防御の観点で並べる。

属性何を防ぐのか（なぜ）それでも破られる条件
SecureHTTPS のリクエストにしか Cookie を載せない。平文で流れないので、経路上の盗聴で ID を拾われないHSTS がないと最初の 1 回が HTTP になりうる。TLS を張る前の段階で剥がされれば意味がない
HttpOnlyJavaScript の document.cookie から読めなくする。XSS が起きても ID を外部サーバへ送り出せないXSS 自体は止まらない。スクリプトは被害者のブラウザ内で、Cookie が自動付与された状態のまま送金や設定変更を実行できる
SameSite他サイト起点のリクエストに Cookie を付けない。攻撃者のページから勝手に投げられたリクエストが認証済み扱いにならない（CSRF）Lax はトップレベルの GET には付くので、GET で状態を変える実装は守られない。同一サイト内の別サブドメインからは付く
Domain送信先ドメインを絞る。無関係なホストへ ID が飛ばない指定するとサブドメイン全体に送られる。脆弱なサブドメインが 1 つあれば、そこから ID を回収できる。狭くしたいなら指定しないほうが狭い

SQL インジェクション：値が構文になってしまう

危険な文字を渡されることが問題なのではない。値として渡したはずのものが、命令の一部として解釈されることが問題。

文字列連結で SQL を組み立てると、DB が受け取るのは値と命令の区別がない 1 本の文字列になる。パーサは引用符の内側か外側かだけを見て解析するので、値の中に ' が現れた瞬間に境界がずれ、そこから先が構文として読まれる。

# 文字列連結 — 値がそのまま SQL の一部になる
cur.execute("SELECT * FROM users WHERE name = '" + name + "'")

# 静的プレースホルダ — 骨格と値を別々に渡す
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

バインド機構・プリペアドステートメント・静的／動的

バインド機構は、値を SQL 文字列に埋め込まず別枠で渡す仕組み全般を指す。プリペアドステートメントは、その SQL をあらかじめ DB に準備させておく形。準備の段階でパースが終わるので、値は後から差し込むしかなくなる。

どこで値を差し込むか安全性の根拠と、残る穴
静的プレースホルダDB サーバ側。? 付きの SQL を先に送り、構文解析を済ませてから値を送る構文が確定した後に値が届くので、原理的に値は構文になれない
動的プレースホルダドライバやライブラリ側。内部でエスケープして 1 本の SQL を組み立て、DB へ送る最終的に文字列連結をしているのは同じ。文字エンコーディングの扱いを誤ると引用符を作れる組合せが残り、実装依存の穴になる

どちらにも共通して破られる条件：プレースホルダはテーブル名・カラム名・ORDER BY の並び順には使えない。ここだけ連結で書いた実装が実際によく残る。可変にしたいなら、外部入力を SQL に混ぜるのではなく許可リストから選ばせる。

エスケープに頼る方式が残す穴

「入口で危険文字を潰しておく」方式が破綻するのは、入口の時点ではその値がどこへ行くのかが決まっていないから。同じ値が SQL にも HTML にもシェルにも流れうるのに、エスケープすべき文字は行き先ごとに違う。多バイト文字の解釈差をつけばすり抜ける組合せも作れるし、経路が 1 つでも漏れれば終わる。

原則は逆側にある——入口でまとめて無害化せず、値を使う場所で、その場所の作法で処理する。入力時の検証は「型・長さ・書式が仕様どおりか」を確かめるものであって、防御の本体ではない。

XSS の対策は、出力の側にある

XSS も構造は SQL インジェクションと同じで、値がマークアップやスクリプトとして解釈されることが問題。反射型・格納型・DOM 型という攻撃側の分類は別記事にあるので、ここは対策側だけを見る。効くのは値を埋め込む直前の処理で、しかも埋め込み先の文脈ごとに必要な処理が変わる。

埋め込む場所必要な処理（なぜ）破られる条件
HTML の本文< > & " ' を文字参照へ。タグの開始として読まれなくなるこの処理だけを全文脈に使い回すこと
属性値必ず引用符で囲んだうえでエスケープ。囲まないと空白で属性を継ぎ足せる引用符なしの <img src=…> に onerror= を足される
<script> 内HTML エスケープでは不十分。JS の文字列リテラルに値を直書きせず、JSON として渡す文字列を閉じずともテンプレートリテラルやコメントで脱出されうる
href / srcエスケープでは足りない。スキームを http / https の許可リストで確認するjavascript: は文字としては無害なので、エスケープを素通りする
CSPインラインスクリプトを禁じ、XSS が起きても実行される範囲を狭めるあくまで多層防御。既存アプリへの後付けは重く、単独の対策にはならない

その上で、WAF はどこに置くか

WAF はリクエストを検査して遮断する仕組みで、判定方式は 2 つある。

  • ポジティブモデル（許可リスト）：通してよい形だけを定義し、それ以外を落とす。精度は高いが、アプリの全パラメータの仕様を書き出し、改修のたびに追随する必要がある。運用が重い。
  • ネガティブモデル（シグネチャ）：既知の攻撃パターンに一致したものを落とす。導入が容易で実際に多いが、知らない形は通る。

根本的な限界は、WAF が見ているのがリクエストの見た目だけで、その値がアプリ内でどう使われるかを知らないこと。エンコードやコメントを混ぜた変形で回避されるし、HTTP を通らずに入るデータ（外部連携ファイル、他システム経由のレコード）は素通りする。誤検知を嫌って緩めれば、緩めた分だけ穴が開く。

提案するときの言い方

「WAF は脆弱性を直すものではなく、直すまでの時間を買うもの。改修に何か月かかるかと、その間どう検知するかがセットで決まっていないなら、入れても止まりません」

「何を・どこで・なぜ」で言い切る

何をどこでなぜ
セッション ID を再発行する認証に成功した直後攻撃者が事前に固定した ID が、認証済み状態と結びつかないようにするため
HttpOnly を付けるCookie を発行する Set-CookieXSS が起きても、スクリプトからセッション ID を読み出せないようにするため
静的プレースホルダを使うSQL を組み立てるアプリ側構文を先に確定させ、入力値が構文として解釈されないようにするため
出力時にエスケープする値を HTML に埋め込む直前埋め込み先の文脈で、値がタグやスクリプトとして解釈されないようにするため
