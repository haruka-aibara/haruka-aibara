# 壁打ち AI と実装 AI を分けてセキュリティ機能を開発する

AI エージェントにセキュリティ機能の開発を任せるとき、1 つの AI に「設計の相談から実装、テストまで」を一気通貫でやらせると、設計時の思い込みが実装とテストにそのまま伝播する。同じ解釈ミスをしたテストは通ってしまうし、LLM は自分（と同系統のモデル）の出力を高く評価する self-preference bias を持つことが研究で示されている。つまり **作った本人に検収させている** 状態になる。

これに対する実践的な答えが、**壁打ち（設計）役と実装役を別モデルのエージェントに分ける**構成だ。例えば設計壁打ちを Claude（Claude Code）、実装を Codex に割り当てる。

## 前提：AI には AWS を触らせない

この記事の前提はシンプルに置く。**AI は AWS アカウントに接続しない。AI の仕事は IaC とコードを書いて PR を出すまで。マージと apply は人間側に残す。**

こうすると、統制設計のほとんどが不要になる。AI 用サンドボックスアカウントの分離も、SCP の設計も、エージェントへの認証情報の払い出しと失効管理も、そもそも要らない。プロンプトインジェクションで AI が完全に乗っ取られたときの最悪ケースが「不採用の PR が 1 本できる」に固定され、それはレビューとゲートで止める前提の設計になっている。単一アカウント運用のままで始められる。

AI に実行環境や AWS アクセスまで渡して自律開発させる構成（マルチアカウント分離・SCP・承認設計）は [セキュリティ機能開発をAIに任せて人間は承認だけにできるか](./セキュリティ機能開発をAIに任せて人間は承認だけにできるか.md) で扱った。この記事はその手前、**組織側の整備を待たずに単一アカウントで回せる形**に絞る。実際に試すときの設定手順は [導入チェックリスト](./壁打ちAIと実装AIを分ける開発フロー_導入チェックリスト.md) にまとめた。

## なぜ分けるのか — 「2 倍手間」ではなく「検証の独立性」

分ける理由は好みではなく構造的なものだ。

- **生成と検証の独立**。実装した AI と同じモデル・同じコンテキストがレビューやテストを書くと、同じ盲点がそのまま残る。別モデルに分けるのは、フォールトトレランス設計の N-version programming と同じ発想——完全な独立は得られないが、単一系統よりは共通故障が減る
- **self-preference bias の回避**。LLM 評価者は自分の生成物を認識し、人間評価では同等品質でも自分の出力に高いスコアを付ける。レビュー役を実装役と別モデルにするのは、このバイアスの構造的な回避策になる
- **役割ごとの要求が違う**。壁打ちに必要なのは「前提を疑う・脅威を列挙する・トレードオフを言語化する」能力、実装に必要なのは「仕様を忠実にコードへ落とす」能力。フェーズごとに得意なエージェントを割り当てられる

ただし過信しないこと。**別モデルでも学習データは大きく重なっており、独立した検証者ではない。** 「よくある IAM の書き方の穴」のような業界共通の盲点は両方が素通しする。また仕様自体が間違っていれば、両方のモデルが忠実にその間違いを実現する。だから機械ゲートと人間のレビューは依然として外せない。

## 核心：受け渡しは「チャットの記憶」ではなく「リポジトリ上の成果物」

2 つのエージェントは会話コンテキストを共有できない。これを欠点と捉えて壁打ちのチャットログを実装役に丸ごと渡すと、壁打ち中の思いつき・撤回済みの案・暗黙の前提まで実装役に流れ込む。

そうではなく、**壁打ちの成果を必ず「仕様書」というリポジトリ上の成果物に落とし、実装役にはそれだけを渡す**。仕様書が 2 つの AI の間のコントラクトになる。

セキュリティ機能の仕様書に最低限入れるもの：

- **目的とトリガー**：何の脅威に対する機能か。いつ発火すべきか
- **受け入れ基準＋デプロイ後の確認手順**：AI はデプロイしないので、マージ前に「動いた証拠」は取れない。その代わり、検知機能なら「apply 後にこの手順（GuardDuty のサンプル検出生成、テストイベント投入など）で発火を確認する」という**人間がそのまま実行できる確認手順書**を成果物に含めることを受け入れ基準にする
- **許可する IAM 権限の上限**：実装がこれを超える権限を要求してきたら、それ自体がレビュー対象
- **触ってよいリソースの範囲**と**ロールバック手段**（`terraform destroy` で戻るのか、戻らない副作用があるのか）
- **やらないこと**：スコープ外を明記しないと、実装 AI は気を利かせて余計なものを作る

この方式には副産物がある。仕様書・実装 PR・レビュー結果がすべてリポジトリに残るので、**「AI に任せた開発」の監査証跡がそのまま揃う**。チャット駆動で開発すると、この証跡が一番先に失われる。

両エージェントへの共通指示（リポジトリ構成、テストコマンド、コーディング規約、触ってはいけない場所）は `CLAUDE.md` と `AGENTS.md` の両方に同じ内容で整備する。片方だけ更新して指示が食い違うのが典型的な事故なので、片方を実体・もう片方をシンボリックリンクにするか、CI で差分検知する。

## 開発ループの全体像

```
Phase 1  壁打ち（例：Claude）
         要件の言語化・脅威モデル・既存構成との整合確認
         → 成果物：仕様書の PR
         → ★人間が仕様を承認（ここが人間の主要な介入点）

Phase 2  実装（例：Codex）
         仕様書を入力に IaC＋コードを実装。AWS には接続しない
         → 成果物：実装 PR（静的検査の結果＋デプロイ後確認手順付き）

Phase 3  クロスレビュー（例：Claude）
         実装 PR を仕様書と突合。特に：
         - 仕様にない IAM 権限・リソースが増えていないか
         - 受け入れ基準と確認手順が対応しているか
         - 「テストを通すためのテスト」になっていないか

Phase 4  機械ゲート → 人間レビュー → 人間がマージ・apply
         → apply 直後に仕様書の確認手順を実行して発火を確認
```

運用上の要点：

- **人間の介入を仕様承認（Phase 1 の出口）に集中させる**。仕様が正しければ、以降のフェーズは機械ゲートとクロスレビューで大半を吸収できる。逆に仕様承認を流し読みすると、後段の全てが「間違った仕様の忠実な実現」を検証するだけになる
- **壁打ちの終了条件を「仕様書の PR が出ること」にする**。壁打ちで一番多い失敗は、議論が盛り上がって結論がチャットに残ったまま終わること。成果物が出ない壁打ちは未完了として扱う
- **クロスレビューでの指摘は仕様書に還流する**。実装役とレビュー役の意見が割れたら、AI 同士で往復させ続けない（収束しないピンポンはコストだけ食う）。往復は 2 回までと決め、割れたまま残った論点は人間が裁定して仕様書を更新する

## 「デプロイしない」ことの穴を機械ゲートで埋める

AI に AWS を触らせない構成で失うものは、マージ前のランタイム検証だ。「サンドボックスで動かして発火を確認した証拠」は取れない。単一アカウントで完結させるなら、この穴は PR 上の決定論的なチェックで埋める。

| ゲート | ツール例 | 見るもの |
|---|---|---|
| シークレット混入 | gitleaks | AI が例として書いたキーの混入含む |
| IaC ミスコンフィグ | Trivy config / Checkov | HIGH 以上ブロック |
| IAM ポリシー検証 | IAM Access Analyzer のポリシーチェック | 過剰権限・public 化 |
| 組織ルール準拠 | OPA / cfn-guard | 仕様書の「権限の上限」をポリシー・アズ・コード化 |
| plan 差分 | CI 上の terraform plan | delete/replace や仕様外リソースの検出 |

補足が 2 つ。

- **terraform plan を実行するのは CI であって AI ではない**。plan には実アカウントへの read アクセスが要るが、それは CI パイプラインの read-only ロール（OIDC の短命トークン）に持たせ、結果を PR に貼る。AI の実行環境（Codex cloud や壁打ち側のセッション）には AWS 認証情報を一切置かない
- **壁打ち役に既存構成を調べさせたいとき**も、まずは人間が CLI の出力や構成図を貼って渡すことで足りる。それでは回らない規模になったら read-only を検討する——そこが「AI に AWS を触らせる側」の設計への分岐点で、その先は冒頭で挙げた別記事の領域になる

それでも埋まらない分は運用で受ける。検知系の機能はまず検知のみ（learn mode）で入れて誤検知率を見てから enforce に昇格する、apply 直後に仕様書の確認手順を必ず実行する、の 2 つで「動かしてみたら違った」を吸収する。

## いつ使うか — 全部にこの体制は過剰

2 モデル体制は往復コストがかかる。リスクベースで使い分ける。

| 変更の種類 | 体制 |
|---|---|
| 検知ルールの閾値調整、タグ付与などの低リスク変更 | 単一エージェント＋機械ゲートで十分 |
| 新しい検知機能、Lambda を伴う自動化 | 壁打ち→仕様書→実装の分割を推奨 |
| IAM の書き込み権限、自動修復（enforce）など壊れると痛い変更 | 分割＋クロスレビュー＋人間の複数名レビューを必須に |

### ビジネス側への言語化

| 技術的な言い方 | ビジネス側に刺さる言い方 |
|---|---|
| AI に AWS 認証情報を渡さない | AI 起因の事故の最悪ケースを「不採用の PR が 1 本できる」に固定できる。専用環境や新たな権限管理への投資が不要 |
| 設計 AI と実装 AI を別モデルに分ける | 作った本人に検収させない、という当たり前の職務分離を AI にも適用する |
| 受け渡しを仕様書ベースにする | AI に任せた開発の判断過程が全部文書で残り、監査にそのまま出せる |
| 人間の承認を仕様承認に集中させる | 人間は全 PR を眺める係ではなく、「何を作るか」の意思決定に時間を使える |
