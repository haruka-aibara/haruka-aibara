Lambda の Python ランタイムを上げるときのコード移行手順

ランタイム非推奨の通知が来るたびに使える、バージョンに依存しない手順。壊れる箇所を「何で見つけるか」で整理し、洗い出し → 修正 → 確認の順に進める。

何が問題なのか

AWS から「このランタイムはサポートを終了します」と通知が来る。Terraform の runtime = "python3.X" を書き換えるのは1行で終わる。困るのはその先で、新しい Python で自分のコードのどこが壊れるのかが分からない。

リリースノートを頭から読むのは長すぎる。とりあえず上げて動かすと、エラーは実行した経路でしか出ない。月に1回しか動かないバッチの分岐は、本番で初めて落ちる。毎回その場しのぎで対応していると、次の通知でも同じことを繰り返す。

解決策は、壊れ方を種類で分け、種類ごとに決まった道具で機械的に洗い出すこと。こうしておけば、どのバージョンに上げるときも同じ手順で回せる。

何が壊れるのか

Python のバージョンアップで壊れる箇所は4種類しかない。種類によって、見つけられる道具が違う。

「警告が出てから消える」を前提にする

Python では、機能は予告なしには消えない。まず DeprecationWarning を出す期間を置き、最低2バージョン後に削除する決まりがある（PEP 387）。つまり、今のバージョンで出ている警告は、将来のエラーの予告になっている。

Lambda のランタイムは数年で廃止されるので、廃止通知のタイミングで上げると2〜3バージョンを一気に飛ぶのが普通になる。そうすると「警告が出ていないから大丈夫」は成り立たない。そもそも警告が出るバージョンを経由していないからだ。これが、手順の最初に静的チェックを置く理由になる。

見つけ方の選択肢とトレードオフ

方法拾えるもの拾えないもの・弱点コスト
What's New の「Porting to Python 3.X」節を読む公式が互換性のない変更として挙げたもの全部自分のコードのどこが該当するかは自分で探す。飛ばしたバージョン分を全部読む中（1バージョンで数十項目）
型チェッカー（pyright / mypy）で対象バージョンを指定①消えた標準ライブラリ・関数。テストが通らない経路も含む②挙動の変化。型ヒントがないと拾える範囲が狭くなる低（設定1行）
ruff で target-version を上げて UP ルールを実行古い書き方。大半を --fix で自動修正できる削除の検出は網羅的ではない。壊れない書き換えも混ざる低
新バージョンでテスト（警告はエラー扱い）②③と、テストが通る経路の①テストがない経路。モックした AWS 部分テストの量次第
dev 環境の Lambda に上げて実イベントを流す④を含む、本番で起きることほぼ全部流したイベントの経路だけ。遅い中

どれか1つで足りるものはない。上から順に重ねて、下の方法ほど調べる範囲を狭くしていくのが効率のよい使い方になる。What's New は最初に一通り読むものではなく、ツールが出したエラーの意味を調べる辞書として使うと速い。

手順

1. 上げる先を決める：Lambda が対応している最新に一気に飛ぶ

1つずつ刻むと、同じ検証を何回も繰り返すことになる。手順2の静的チェックは飛ばしたバージョン分をまとめて拾えるので、刻む理由はない。ただし、使っている主要ライブラリが新バージョンに対応していない場合は、1つ手前で止める。PyPI でそのバージョン向けの wheel が出ているか、classifiers に対象バージョンが入っているかで判断する。

2. 静的に洗い出す：設定を対象バージョンに合わせる

コードは変えずに、ツールの「前提とする Python」だけを新しいバージョンに書き換えて実行する。出てきたエラーが修正リストになる。

# pyproject.toml（3.XX は上げる先のバージョン）
[project]
requires-python = ">=3.XX"

[tool.ruff]
target-version = "py3XX"

[tool.ruff.lint]
extend-select = ["UP"]

[tool.pyright]
pythonVersion = "3.XX"
reportDeprecated = "error"
ruff check --fix .   # 古い書き方を自動で書き換え
pyright              # 消えたモジュール・関数を検出

型チェッカーで消えた標準ライブラリが見つかるのは、typeshed（標準ライブラリの型定義）がモジュールや関数ごとに「どのバージョンにあるか」を持っているからだ。テストが通らない経路の import も拾えるのがテストとの違い。mypy なら python_version で同じことができる。

3. 依存を先に上げる

古いライブラリは新しい Python に対応していないことが多い。コードを直す前に、依存を新バージョンで入れ直す。

  • lock ファイルのある依存：新バージョンで uv lock --upgrade（pip なら pip-compile --upgrade）をかけ、入らないものを特定する
  • zip や Layer に直接置いた依存：対象バージョンを指定して入れ直す。C 拡張を含むものは、手元の OS 向けではなく Lambda 向けのバイナリが要る
    pip install --python-version 3.XX --platform manylinux2014_x86_64 --only-binary=:all: -t python/ -r requirements.txt
  • ランタイム同梱の boto3：同梱されているバージョンはランタイムごとに違う。新しい API に頼っているなら、boto3 を自分のパッケージに含めて固定する

4. 新バージョンでテストする：警告もエラーにする

プロジェクトの設定を変えずに、別のバージョンでテストだけ回せる。

uv run --isolated --python 3.XX pytest -W error::DeprecationWarning

-W error::DeprecationWarning を付けると、上げる先のバージョンで出ている警告（次の削除予定）もその場で潰せる。サードパーティ由来で直せない警告は、filterwarnings でそのライブラリだけ除外する。

テストがない関数でも、最低限これだけは回す。ハンドラを import して、保存しておいた実イベントを1件渡す。import だけでも「消えたモジュール」と構文エラーは全部出る。

# tests/test_smoke.py
import json
from pathlib import Path

import lambda_function


def test_handler_runs_with_real_event():
    event = json.loads(Path("tests/events/sample.json").read_text())
    lambda_function.lambda_handler(event, None)

イベントは CloudWatch Logs に出したものや、コンソールのテストイベントから取っておく。外部 API を叩く関数は moto などで AWS 部分を差し替える（書き方は Python/18_テスト/ の記事を参照）。

5. dev 環境で実イベントを流す

ここで初めて Terraform の runtime を書き換えて dev に apply する。値を locals に1か所だけ書いておけば、変更は1行で済む。手元で再現しない④（OS の違い、同梱ライブラリ、Layer の中身）はここで出る。

dev の関数では警告をログに出す。こうすると、テストのない経路で出た警告も CloudWatch Logs で拾える。

environment {
  variables = {
    PYTHONWARNINGS = "default"   # dev だけ。警告を stderr → CloudWatch Logs に出す
  }
}

6. 本番に反映する：戻し方も確認しておく

ランタイムの変更は関数の作り直しではなくインプレース更新なので、戻すときは PR を revert して apply するだけで済む。

旧ランタイムに戻せるのは、そのランタイムの「更新ブロック日」まで

Lambda は廃止日の後、段階的に「新規作成」「更新」をブロックする。更新ブロック日を過ぎると、revert による旧ランタイムへの切り戻しも「更新」として拒否される。廃止ぎりぎりに上げると、何かあったときに逃げ道がない。通知が来たら、日付の早いうちに手順を回し始める。

AI に任せる場合

この作業は AI エージェント（Claude Code など）に向いている。修正の多くは「消えた API を後継の API に置き換える」という定型作業で、正しく直せたかどうかも機械的に確かめられるからだ。

任せ方のポイントは2つ。手順2と4のエラー出力をそのまま渡す（「3.XX に上げて」とだけ頼むと、推測で直す範囲が広がる）。そして完了の判定はテストと型チェックの結果で行う（AI の「直しました」で判断しない）。この記事の手順は、そのまま AI への指示と合否判定にも使える。

次回を軽くする

  • CI で普段から -W error::DeprecationWarning を付ける。今のバージョンで出た警告をその都度直しておけば、次に上げるときに消えるものが残っていない
  • バージョンを書く場所を揃える。runtime、requires-python、ruff の target-version、pyright の pythonVersion、CI の Python。どれか1つだけ古いと、テストは緑なのに本番で落ちる
  • 通知を待たず、新しいランタイムが出て主要ライブラリが対応したら上げる。飛ばすバージョンが少ないほど、手順2の出力は短くなる
