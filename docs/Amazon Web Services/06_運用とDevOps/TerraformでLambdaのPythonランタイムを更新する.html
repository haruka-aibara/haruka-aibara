Terraform で Lambda の Python ランタイムを更新する

「runtime の文字列を1つ書き換えるだけ」に見えて、実際には依存パッケージ・Layer・CI・ロールバックまで一緒に動く作業。選択肢とトレードオフ、落ち着きどころをまとめる。

何が問題なのか

ある日 AWS Health から「Python 3.10 のサポートが 2026-10-31 に終了します」とメールが来る。Terraform のコードを grep すると runtime = "python3.10" がモジュールのあちこちに散らばっていて、どれが本番で動いているのかも怪しい。しかも、放置した場合に何が起きるのかがよく分からない。

ランタイムの廃止は1回で終わる話ではない。Python は毎年新しいバージョンが出て、Lambda のランタイムはだいたい3〜4年で廃止される。「1回うまく上げる」より「毎年ほぼ自動で回る状態を作る」ほうが価値が大きい。この記事はその前提で書く。

廃止されると何が止まるか

2026-09 時点の Python ランタイムの状況はこう。3.12 以降は OS が Amazon Linux 2023（AL2023）に変わっていて、3.11 以前（AL2）からの移行は OS の入れ替えも兼ねる。

ランタイムOS廃止日作成ブロック更新ブロック
python3.14AL20232029-06-302029-07-312029-08-31
python3.13AL20232029-06-302029-07-312029-08-31
python3.12AL20232028-10-312028-11-302029-01-10
python3.11AL22027-06-302027-07-312027-08-31
python3.10AL22026-10-312027-02-012027-03-03

3.13 と 3.14 の廃止日が同じなのは、AL2023 自体のサポート終了（2029-06-30）に頭打ちされているから。「新しいほど長く使える」が成り立たない区間があるので、どちらを選ぶかは寿命ではなくライブラリの対応状況で決めてよい。

ランタイムを上げると何が動くか

文字列1つの変更で済まないのは、下の層ほど「バージョンに縛られたもの」が埋まっているから。

よく壊れる箇所：

  • C 拡張を含む依存（pydantic-core、cryptography、numpy など）。手元の Mac で pip install した zip をそのまま上げていると、ランタイムを上げた瞬間に ImportError になる。ビルドは pip install --platform manylinux2014_x86_64 --python-version 3.13 --only-binary=:all: -t build/ のようにターゲットを明示するか、public.ecr.aws/lambda/python:3.13 のコンテナ内で行う
  • 標準ライブラリの削除。3.12 で distutils・imp、3.13 で cgi・telnetlib など（PEP 594）が消えた。飛ばしたバージョン分の「What's New」の削除項目は全部読む
  • Layer の compatible_runtimes はただの宣言で、中身のバイナリが合っているかは誰も確認しない。関数と一緒に作り直す
  • ランタイム同梱の boto3。ランタイムごとに同梱バージョンが違うので、新しい API を使っているなら boto3 を自分でパッケージに含めて固定するほうが安全

やり方の選択肢とトレードオフ

「どこに書くか」「どう気づくか」「どう反映するか」の3つを分けて選ぶ。

どこに書くか

方法良いところ弱いところ
各 aws_lambda_function に直書き読めば分かる。関数ごとに違う版にできる関数が増えると上げ漏れが出る。grep 頼み
locals に1か所だけ書く（モジュールには変数で渡す）1行の変更で全関数が揃う。PR の差分が小さい全関数が一斉に動くので、1つ壊れると PR 全体が止まる
モジュール変数のデフォルト値に置くモジュール利用側は何もしなくても追従するモジュールのバージョンを上げるまで反映されない。呼び出し側で上書きされると追跡しづらい
コンテナイメージ（package_type = "Image"）ベースイメージのタグ更新は Dependabot / Renovate が標準で扱える。依存のビルド環境も固定できるOS・ランタイムのパッチも自分でイメージを再ビルドしない限り当たらない。ECR とビルドの仕組みを持つ必要がある
locals {
  python_runtime = "python3.13"
}

resource "aws_lambda_function" "notifier" {
  runtime = local.python_runtime
  # ...
}

resource "aws_lambda_layer_version" "deps" {
  compatible_runtimes = [local.python_runtime]
  # ...
}

コンテナイメージ化は「ランタイム更新を楽にする」目的だけで選ぶと割に合わない。パッチ適用の責任が AWS から自分に移るので、毎年1回の文字列変更と引き換えに、毎月の再ビルドを背負うことになる。依存が大きくて zip の 250MB 制限に当たる、などの別の理由があるときの選択肢。

どう気づくか

仕組み見ているもの向いている場面
AWS Health（メール・EventBridge）デプロイ済みの関数無料で全アカウントに届く。最低限これは受け取れる状態にしておく
Trusted Advisor / Security Hub CSPM（Lambda.2）/ Config（lambda-function-settings-check）デプロイ済みの関数Terraform 管理外や手作りの関数も拾える。既に運用しているなら追加コストなし
tflint の aws_lambda_function_deprecated_runtimeコード（plan 前）PR の時点で止めたいとき。判定リストはプラグインに埋め込みなので、プラグイン自体の更新が前提

前者2つは「動いているもの」、tflint は「これから入るもの」を見る。コピペで古いランタイムの関数が新しく増えるのを防げるのは tflint だけなので、両方あると穴がない。

どう更新 PR を作るか

Dependabot は Terraform の runtime 属性を依存として扱わない。Renovate なら正規表現のカスタムマネージャで拾える。バージョンの出どころを Lambda のベースイメージのタグにしておくのがコツで、Python 本体のリリースを見てしまうと、Lambda がまだ対応していないバージョンの PR が数か月早く届いてしまう。

{
  "customManagers": [
    {
      "customType": "regex",
      "managerFilePatterns": ["/\\.tf$/"],
      "matchStrings": ["runtime\\s*=\\s*\"python(?<currentValue>3\\.\\d+)\""],
      "depNameTemplate": "public.ecr.aws/lambda/python",
      "datasourceTemplate": "docker",
      "versioningTemplate": "regex:^(?<major>\\d+)\\.(?<minor>\\d+)$"
    }
  ]
}

自動 PR はテストがあって初めて意味を持つ。CI の Python バージョン（setup-python の python-version や .python-version）が runtime と別管理だと、「CI は 3.10 で緑、本番は 3.13」というズレが起きる。ランタイムの値と CI の Python は同じ PR で動くようにする（Renovate なら同じ groupName にまとめる）。

どう反映するか

  • そのまま apply：runtime の変更はインプレース更新で、関数は作り直されない。ロールバックは PR を revert して apply。定期実行・イベント駆動の関数ならこれで十分
  • エイリアスで段階切り替え：publish = true で新バージョンを作り、aws_lambda_alias の routing_config で数％だけ流す。トラフィックの多い同期 API 向け。Terraform で重みを段階的に変えるのは手作業になりやすく、CodeDeploy まで入れると構成が一段重くなる

ロールバックできるのは更新ブロック日まで

revert で旧ランタイムに戻すのも「更新」なので、旧ランタイムの更新ブロック日を過ぎると戻せない。廃止直前にまとめて上げると、何かあったときに逃げ道がない状態で本番を切り替えることになる。

落ち着きどころ（デファクトに近い形）

小〜中規模で Terraform 管理の zip 関数なら、次の組み合わせがいちばん手数が少ない。

  1. ランタイムの値は locals（モジュールなら変数）の1か所に集める
  2. 上げる先は「Lambda が対応している最新」に一気に飛ぶ。3.10 → 3.11 → 3.12 と刻むと、同じ検証を3回やることになる。飛ばした分の削除項目を読むほうが安い
  3. 上げるタイミングは廃止通知ではなく、新ランタイムのリリース後しばらくしてから。主要ライブラリが wheel を出すまで数週間〜数か月待つのが無難で、廃止日の半年以上前に終わっている状態を目標にする
  4. 更新 PR は Renovate で自動で作り、CI の Python と一緒に上げる
  5. AWS Health は必ず受け取れるようにし、tflint は PR で回す
  6. 段階リリースは、止まると困る同期 API だけ。それ以外は apply と revert で足りる

全関数を一斉に上げるのが怖い場合は、locals を「新しい版」「据え置き」の2つに分け、関数ごとに段階的に移す。ただし据え置き側がそのまま忘れられやすいので、移行が終わったら1つに戻す。
