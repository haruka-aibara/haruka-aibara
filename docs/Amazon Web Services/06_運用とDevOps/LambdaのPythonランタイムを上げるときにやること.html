Lambda の Python ランタイムを上げるときにやること

直すところは機械に探させる。直すのはそこだけ。最後に sandbox で1回だけ動かす。

何が問題なのか

AWS から「このランタイムのサポートを終了します」と通知が来る。Terraform の runtime = "python3.X" を書き換えるのは1行で済む。

困るのは、新しい Python でコードのどこが動かなくなるかが分からないこと。Python は新しいバージョンで古い機能を削除するので、それを使っている行は動かなくなる。一方で、本番で動いているものを「試しに上げてみる」ことはできない。壊れていたら、その間は機能が止まるからだ。

そこで、動かす前に機械で探して、見つかったところだけ直す。

1. pyright で動かなくなる所を探す

pyright は、コードを実行せずに読むだけで「存在しないものを使っている行」を見つけるツール。上げる先の Python の上で動かすと、そのバージョンで消えた機能を使っている行が分かる。関数のすべての分岐を読むので、めったに通らない分岐も漏れない。

古いコードにそのままかけると型の細かい指摘が大量に出るので、「消えたもの」と「非推奨」だけを出す設定にする。

// pyrightconfig.json
{
  "typeCheckingMode": "off",
  "reportMissingImports": "error",
  "reportAttributeAccessIssue": "error",
  "reportDeprecated": "warning"
}

このファイルは pyright を実行するディレクトリ（Lambda の .py を置いているディレクトリ）に置く。pyproject.toml があるなら、同じ内容を [tool.pyright] に書いてもよい。

コマンドは uv で動かす。uv は curl -LsSf https://astral.sh/uv/install.sh | sh（Mac なら brew install uv でも可）で入る。--python 3.XX で指定したバージョンの Python は uv が自動で取ってくるので、別に入れる必要はない。

# 3.XX は上げる先のバージョン。boto3 は Lambda に最初から入っているものの代わり
uv run --python 3.XX --with pyright --with boto3 pyright .
error: Import "cgi" could not be resolved
error: "coroutine" is not a known attribute of module "asyncio"
warning: The method "utcnow" in class "datetime" is deprecated
  • error：直さないと動かない。これは必ず直す
  • warning：今は動くが、いずれ消える。余裕があれば直す

boto3 以外のライブラリを使っているときは、それも読めるようにする。

  • requirements.txt がある：コマンドに --with-requirements requirements.txt を足す。新しい Python でインストールに失敗したライブラリも、ここで分かる。失敗したものだけバージョンを上げる
  • Layer のディレクトリに直接置いている：pyrightconfig.json に "extraPaths": ["layer/python"] のようにその場所を足す

2. ruff で古い書き方を新しくする

ruff は、動くけれど古い書き方（typing.List → list など）を新しい書き方に自動で直す。必須ではないが、上げるついでに基本的にやっておく。上げる先のバージョンを指定して実行する。

uvx ruff check --target-version py3XX --select UP --fix .

1 の修正とは別のコミットにしておく。壊れたときに、どちらの変更が原因かすぐ分かる。

3. 挙動の変化は AI に照合させる

pyright が見つけられないのは「関数はあるが、結果が変わった」ものだけ。これは Python 公式の What's New の「Porting to Python 3.X」節に一覧がある。飛ばしたバージョン分のその節とコードを AI に渡して、「このコードで該当する箇所だけ挙げて」と頼む。該当するのはたいてい 0〜数件で済む。

4. sandbox で1回だけ動かす

dev も本番と同じように使っているなら、dev では試せない。本番とつながっていない sandbox アカウントに同じ関数を作って、そこで流す。

これを軽くやるための条件は1つだけ。Lambda を Terraform のモジュールにして、ランタイムと外部の送り先（Slack など）を変数で渡せるようにしておくこと。そうすれば、sandbox 用の小さな設定から同じモジュールを呼ぶだけで済む。

# sandbox/main.tf
provider "aws" {
  profile = "sandbox"
}

module "app" {
  source         = "../modules/app"
  python_runtime = "python3.XX"                 # 上げる先
  slack_webhook  = "https://hooks.slack.com/..." # テスト用チャンネル
}
terraform apply
aws lambda invoke --profile sandbox --function-name app \
  --cli-binary-format raw-in-base64-out --payload file://event.json out.json
terraform destroy

event.json は本番の CloudWatch Logs などから保存した本物のイベント。エラーが出なければ、本番の runtime を書き換えて apply する。

通知が来たら早めに始める

Lambda はサポート終了後しばらくすると、そのランタイムの関数を更新できなくなる。そうなると、問題が出たときに古いバージョンへ戻すこともできない。

次の一歩

sandbox で流す作業に慣れたら、同じ確認を pytest と moto で手元だけで回せるようにする。偽の AWS の上で関数を呼ぶテストを1本書いておけば、sandbox を作らなくてもコマンド1つで確かめられる。考え方は pytest と moto をゼロから理解する にある。
