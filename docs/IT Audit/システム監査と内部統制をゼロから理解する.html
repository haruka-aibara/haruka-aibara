システム監査と内部統制をゼロから理解する

誰の依頼で、何を根拠に、どこまでやるのか。監査まわりの用語はこの 3 つを埋める順に並べると繋がる。

「来月、監査が入ります」と言われて困ること

何を準備すればいいのか分からない。ログを出せば済むのか、手順書の妥当性まで問われるのか。そもそも監査人は法律で来ているのか、社内の都合で来ているのか。指摘されたら誰が直すのか。

監査という言葉そのものには、誰の依頼で・何を根拠に・どこまでやるかが含まれていない。だから不安になる。逆に言えば、用語はこの 3 つを埋める順に整理すれば繋がる。

最初の原則：監査人は自分で直さない

監査人がやるのは、あるべき姿（基準）と実態を突き合わせ、ズレを指摘して改善を助言するところまで。設定を直したり手順書を書き換えたりはしない。直すのは被監査部門で、直させるのは監査を依頼した経営者。

理由は単純で、自分が作ったものを自分で評価すると甘くなるから。監査人が改善作業に手を出した瞬間、次の監査で自分の仕事を評価することになる。これを避けるのが監査人の独立性で、外観上の独立性（監査対象と身分・利害の関係がないこと）と精神上の独立性（偏りのない態度で臨むこと）の両方が求められる。

ただし報告書のゴールには 2 種類ある。助言型は「ここをこう改善するとよい」と改善提案を主目的にするもの。保証型は「統制は有効に機能している」と意見を表明し、その正しさを監査人が引き受けるもの。社内の改善が目的なら助言型、取引先や市場に示す必要があるなら保証型になる。

システム監査とセキュリティ監査

どちらも情報システムを見るが、見る観点の広さが違う。セキュリティ監査はシステム監査の一部と考えてよい。

システム監査情報セキュリティ監査
何を見るか情報システムが経営に貢献しているか。可用性・機密性・完全性に加え、有効性・効率性・準拠性まで情報セキュリティが確保されているか（機密性・完全性・可用性）
対象企画・開発・運用・保守のライフサイクル全体組織の情報セキュリティ管理策全般
あるべき姿の拠り所システム管理基準情報セキュリティ管理基準

誰が監査するのか — 第一者・第二者・第三者

監査の性格は「誰が依頼して誰がやるか」でほぼ決まる。同じチェック項目を見ても、この違いで報告書の使い道が変わる。

種類やる人典型例
第一者監査
（内部監査）		自組織の監査部門ISMS の内部監査、社内のシステム監査。目的は自分たちの改善
第二者監査取引先・委託元など利害関係者委託先監査。「預けたデータが約束どおり扱われているか」を委託元が見に行く
第三者監査利害関係のない外部機関ISMS 認証審査、SOC 報告書。対外的な保証が要るときはこれしかない

監査証跡と監査証拠

この 2 つは混同しやすい。分かれ目は誰のものかにある。

監査証跡（audit trail）監査証拠（audit evidence）
誰のものか被監査部門側にもともとあるもの監査人が入手・評価したもの
正体処理の履歴。アクセスログ、変更履歴、承認記録、伝票結論の裏付けになる事実。証跡の写しに加え、ヒアリング記録、現地で観察した事実、再実行した結果
監査がなければそれでも存在する存在しない

関係としては、監査証跡は監査証拠の材料の一つ。証跡が残っていても監査人が入手・評価していなければ証拠ではないし、逆に証拠は証跡だけで構成されるわけでもない。実務で効いてくるのは前者で、証跡が取れていない領域は、監査で証拠を作れない。ログ設計を後回しにしたシステムは、監査の場で「有効だと言えない」と評価される。

監査計画は 3 階層

監査は毎年すべてを見るわけにはいかない。だから計画を粒度の違う 3 枚に分ける。

拠り所になる基準類

基準は「監査人がどう振る舞うか」と「被監査側のあるべき姿は何か」がペアになっている。この対応が分かると、どれを開けばいいか迷わなくなる。

基準発行何を規定するか
システム監査基準経済産業省監査人の行為規範と監査手続。独立性、計画、証拠の入手、報告の作法
システム管理基準経済産業省被監査側のあるべき姿。IT ガバナンスと、企画・開発・運用・保守の管理項目
情報セキュリティ管理基準経済産業省セキュリティ版のあるべき姿。ISO/IEC 27001・27002 がベース
ISO 19011
（JIS Q 19011）		ISO / JISマネジメントシステム監査の指針。第一者・第二者監査で使う共通の作法（第三者の認証審査は ISO/IEC 17021-1）

内部統制と IT 統制の 3 分類

内部統制は、業務が適正に行われることを確保するために組織に組み込む仕組み。その基本的要素の一つに「IT への対応」があり、IT の統制はさらに 3 つに分かれる。

なぜこの順序なのかは、逆から考えると早い。誰でも本番のプログラムを差し替えられる環境なら、入力チェックが今この瞬間も実装されている保証はない。業務処理統制の有効性は、全般統制が支えていて初めて主張できる。

提案するときの言い方

「変更管理を整備しましょう」では通らないことが多い。「本番へのデプロイに承認記録が残っていないと、監査で業務処理統制まで有効と言えなくなる。個別の機能を作り込む前に、ここを整えるほうが安く済む」——統制は積み上げの順序があり、下から積むと手戻りが出る、という言い方のほうが伝わる。
