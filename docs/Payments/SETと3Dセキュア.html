SET と 3D セキュア — 技術的に正しくても、面倒なら普及しない

カード情報を店に見せない完璧な仕組みは消え、利用者の手間を減らした仕組みが残った。

何が問題なのか

ネット通販でカード決済をするとき、リスクは2種類ある。

  • カード情報が加盟店から漏れる：店のデータベースが侵害されれば、番号がまとめて流出する
  • 盗まれた番号で他人が買い物をする：番号さえ分かれば決済できてしまう（対面と違い、カードの現物も本人確認もない）

この2つに、まったく違うアプローチで挑んだのが SET と 3D セキュア。片方は技術的に優れていたが消え、もう片方が生き残った——その理由まで含めて、設計を考えるときの教材になる。

SET：カード番号を店に渡さない

1996 年に Visa と Mastercard が策定した仕様。発想は徹底していて、加盟店にはカード番号を一切見せない。利用者・加盟店・決済ゲートウェイのすべてが証明書を持ち、「二重署名」という手法で情報を分離した。

それでも SET は普及しなかった。利用者が専用ソフト（電子ウォレット）を入れ、証明書を取得しなければ買い物ができないからだ。結局、加盟店まで SSL/TLS で暗号化して番号を送るという簡便な方法が事実上の標準になった。

3D セキュア：カード会社が本人確認する

そこで狙いを「漏洩の防止」から「なりすましの防止」に切り替えたのが 3D セキュア。番号は従来どおり流れるが、決済の途中でカード発行会社が本人確認を行う。名前の 3D は、関わる3つの領域（カード発行会社・加盟店側・両者をつなぐ決済網）から来ている。

初期のバージョンは専用のパスワードを入力させる方式だった。これが不評で、入力画面で購入をやめる利用者が続出した（カゴ落ち）。SET ほどではないにせよ、やはり手間が普及の壁になった。

設計を考えるときに持ち帰る点

SET は技術的に隙がなかったが、利用者に手間を要求したために消えた。3D セキュアも初期版は同じ失敗をし、リスクベースにして手間を「必要なときだけ」に絞ったことで定着した。
社内でセキュリティ施策を提案するときも構図は同じ。全員に恒常的な手間を課す案は、正しくても運用で骨抜きにされる。リスクの高い操作にだけ強い認証を求める、普段は透過的に済ませる、という設計に寄せられないかを先に検討する。
