# c7n のソースを丸ごと git 管理するか wheel で持つか

`modules/aws-config-custodian` は、c7n を PyPI の wheel のまま `vendor/` に置き、判定は YAML のポリシーで書いている。判定ロジックの Python コードも git で持ちたくなったときに、c7n のソースを丸ごと持ってくるとどうなるか。

c7n は Apache 2.0 なので、コピー・改変・商用利用とも、連絡や許可なしでできる。持ってくるなら LICENSE と著作権表示を残し、手を入れたファイルにはその旨を書く。

## 規模（c7n 0.9.52）

| | 量 |
|---|---|
| wheel | 1 ファイル、750KB |
| ソース丸ごと | 193 ファイル（うち .py が 192）、約 8.8 万行、3.4MB |
| うち `resources/`（AWS の全リソース定義） | 約 6.8 万行 |
| 今回使っている部分の中心 | `resources/rds.py` 2,400 行、`resources/iam.py` 3,400 行、`policy.py` 1,400 行、`filters/core.py` 1,300 行 |

使うリソースの分だけ抜き出すのは難しい。起動時に全リソースの定義を読み込む作りで、ファイル同士の依存も多いので、実際には丸ごと持つことになる。

## どっちがいいか

| | wheel のまま（今） | ソースを丸ごと git 管理 |
|---|---|---|
| リポジトリに入る量 | 750KB のバイナリ 1 つ | 約 8.8 万行 |
| 判定ロジックを読む | 上流リポジトリの同じバージョンのタグを見る | 手元で読める、grep できる |
| c7n の更新 | wheel を差し替えるだけ | 上流との差分を自分で取り込む。手を入れていると衝突する |
| c7n にないチェックを足す | できない（YAML で書ける範囲だけ） | 直接書ける |
| PR のレビュー | ポリシーの YAML の差分だけ | 更新のたびに数千行の差分が出る |

判定ロジックを読みたいだけなら、wheel のままで、上流の同じバージョンのタグを参照するほうがいいだろう。バージョンを固定していれば、どのコードで判定しているかは一意に決まる。

ソースを持つ意味が出てくるのは、c7n にないチェックを書きたい、または c7n のバグを上流の修正を待たずに直したい、というときくらい。その場合も丸ごと持つのではなく、足したいフィルタだけを別ファイルで書いて c7n に読み込ませる形のほうが、更新を追いやすいだろう。
