# ISMS 8.17 クロックの同期は AWS では何をやるか

ISO 27002 の 8.17（組織のシステムのクロックを承認された時刻源に同期する）を AWS 環境に当てはめると、
**時計を自分で持っているところだけが対象**で、それ以外は AWS の責任範囲に入る。
マネージドサービス中心の構成なら、やることはほぼ「方針に書く」だけになる。

## ログを出す主体ごとの整理

| 主体 | 時刻を刻むのは誰か | こちらでやること |
|---|---|---|
| CloudTrail / Config / GuardDuty / Security Hub CSPM | AWS | なし（UTC で記録される） |
| CloudWatch Logs の取り込み時刻、VPC Flow Logs、ALB / CloudFront / S3 アクセスログ | AWS | なし |
| Lambda / Fargate / RDS / Aurora 等のマネージド実行基盤 | AWS（ホスト側で Amazon Time Sync に同期済み） | なし。RDS の `time_zone` パラメータは変えずに UTC のまま使う |
| EC2（EKS・ECS on EC2 のノードを含む） | **自分の OS** | chrony / w32time が Amazon Time Sync Service を向いていることを確認する |
| コンテナ | ホストのカーネル時計をそのまま使う | コンテナ内では何もしない。ノード側で担保する |
| アプリが自分で埋め込むタイムスタンプ | そのプロセスが動くホスト | UTC・ISO 8601 で出すようにする |
| オンプレ・VPN 越しの機器・社内 PC | 自分 | `time.aws.com` か社内 NTP に向ける（AWS とは別論点） |

マネージドサービスの時刻源は利用者から見えないし設定もできない。
監査で問われたら「共有責任モデル上 AWS の管理範囲。AWS の ISO 27001 / SOC 2 報告書（AWS Artifact）で担保」と答えるのがデファクト。

## EC2 でやること

- **時刻源は Amazon Time Sync Service**：`169.254.169.123`（IPv6 は `fd00:ec2::123`）。VPC 内のリンクローカルなので外向き通信も SG の穴あけも要らない
- **Amazon Linux 2 / 2023・Bottlerocket・EKS 最適化 AMI・AWS 提供の Windows AMI は最初から向いている**。何もしなければ満たされる
- **Ubuntu / RHEL 等の他ディストリや自作 AMI は要確認**。外部の公開 NTP（`pool.ntp.org` 等）を向いたままのことがある
- **Amazon とそれ以外の NTP を混ぜない**：Amazon はうるう秒をスメア（徐々に調整）するので、スメアしない公開 NTP と併用するとずれる
- マイクロ秒精度が要る用途（金融取引・分散 DB）は Nitro の PTP ハードウェアクロックや ClockBound があるが、ISMS 目的では不要

確認コマンド：

```sh
chronyc sources -v   # 169.254.169.123 に ^* が付いていれば同期中
chronyc tracking     # System time の offset
```

## 「すべてのシステムを同期対象とする」の現実的な満たし方

EC2 を 1 台ずつ見るのではなく、**AMI で担保する**。

1. 使ってよい AMI を Amazon Linux / Bottlerocket / AWS 提供 Windows に絞る（または自作 AMI のビルド手順に chrony 設定を入れる）
2. 方針文書に「EC2 は Amazon Time Sync Service に同期する。マネージドサービスは AWS の責任範囲」と書く
3. 例外（他ディストリ）があれば SSM State Manager で chrony 設定を配る

## 時刻同期の監視

ここが一番「やらないでも済ませている」ところ。デファクトは次の程度。

- **何もしない（AMI 標準に任せる）**：実際にはこれが大多数。リンクローカルの時刻源が止まることはまずない
- **やるなら機械側で閉じる**：CloudWatch エージェントで chrony の offset をカスタムメトリクスに出し、閾値超過をアラームにする。人間のチャンネルに流すのは閾値超過だけ
- **監査証跡としては「設定が入っていること」を定期に取れば足りる**：SSM Inventory や Run Command で `chronyc sources` の結果を集める程度

監視を足すかどうかは EC2 の台数次第。マネージド中心で EC2 がほぼ無いなら、監視はやらずに「AMI 標準で担保」と書くほうが素直。

## タイムゾーン

- **保存・ログ出力は UTC に統一**（AWS のサービスログはすべて UTC なので、揃えないと突き合わせで事故る）
- 表示だけ JST にする（Athena / CloudWatch Logs Insights / ダッシュボード側で変換）
- アプリログは `2026-09-26T01:23:45Z` のように ISO 8601 でオフセット付きにする
- EC2 の OS タイムゾーンを JST に変える運用は避ける。cron の時刻がずれる事故も含めて得がない

## 方針文書に書く文面の叩き台

> - AWS マネージドサービスの時刻は AWS の管理範囲とし、AWS の第三者認証報告書で担保を確認する
> - EC2 は Amazon Time Sync Service に同期する。承認 AMI の標準設定で担保し、例外は構成管理で配布する
> - ログのタイムスタンプは UTC で記録し、表示時に JST へ変換する
