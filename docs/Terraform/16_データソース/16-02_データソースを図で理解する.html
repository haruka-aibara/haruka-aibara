データソース（data）を図で理解する

Terraform が「知らない」リソースを、壊さずに読み取るための仕組み。

何が問題なのか

Terraform は自分が管理しているリソースしか知らない。でも現実には、管理外のリソースを参照したい場面がたくさんある——ネットワークチームが管理している VPC、コンソールで手作業で作られた Route53 ホストゾーン、AWS 側が更新し続けている最新の AMI。

それを解決するのが data ブロック。作成も変更も削除もせず、読み取るだけ。

参照したいというだけで resource に書いてしまうと、Terraform はそれを自分の持ち物だと解釈する。他チームのリソースを上書きしたり、destroy で消したりできてしまう。data はそこを構造的に分ける。

書き方

デフォルト VPC を読み取る例。default = true は「どれを探すか」の条件。

data "aws_vpc" "default" {
  default = true
}

読み取った値は data. から始まる名前で参照する。

あとは resource の中でふつうに使える。

resource "aws_subnet" "app" {
  vpc_id     = data.aws_vpc.default.id
  cidr_block = "172.31.100.0/24"
}

よくある例：最新の AMI を拾う

AMI ID を ami-0123456789abcdef0 のように直接書くと、セキュリティ更新が出ても古いままになる。data で条件を書いておけば、apply のたびに最新のものが選ばれる。

data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"
}

最初に知っておくこと

  • 条件に合うものが見つからないとエラーで止まる：空っぽの値が返るのではなく、no matching ... found で plan ごと失敗する。フィルタの書き間違いはここで気づく。
  • 条件に複数マッチしてもエラー：aws_vpc や aws_ami は「ちょうど1件」を要求する。1件に絞れる条件を書く。
