トークンローテーションを1回の run で完了させる — そして Vault ならどうなるか

23-07 の自己ローテーションは、run が1回走って切替が済んでも、古いトークンがしばらく生き残る。「旧トークンが無効になるまで」を完了と呼ぶなら、それを1回の run で終わらせる方法。そして Vault があれば、この問いごと消せる。

「切替」で終わった気になっていないか

23-07 のブルーグリーン構成では、run が1回走ると新トークンの発行と TFE_TOKEN の切替までは終わる。しかし直前まで使っていた旧トークンはまだ有効なままだ。Terraform がそれを revoke するのは、半周期後にその色を作り直す次の run。つまり「旧トークンで API を叩けなくなった時点」をローテーションの完了とすると、完了は run 2回分先で、しかも2回目の run がいつ走るかに依存する。漏えい対応や監査で「無効化はいつ終わるのか」と聞かれたとき、これでは答えに詰まる。

なぜ1回の apply では完了できないのか

apply は、自分が認証に使っているトークンを消せない。途中で消すと残りの API 呼び出しが 401 になり、管理用ワークスペースが文鎮化する（23-07 の落とし穴）。旧トークンを API で消せるのは「新トークンで認証した次の run」だけ。つまり revoke という操作にこだわる限り、run は最低2回必要で、1回の run には収まらない。

消すのをやめて、期限に任せる

発想を変えて、revoke を構成から消す。1回の apply がやるのは発行と切替だけ。旧トークンの無効化は expired_at に任せ、期限を「次の色へ引き継いだ直後」まで縮める。

# 23-07 からの変更点は expired_at だけ（blue も同様に変える）
resource "tfe_team_token" "green" {
  team_id     = tfe_team.manager.id
  description = "manager green ${time_rotating.green.rotation_rfc3339}"
  # rotation_rfc3339 は作成から60日後。-27日 = 作成から33日
  # = blue への引き継ぎ（作成から30日後）の3日後に自動失効
  expired_at  = timeadd(time_rotating.green.rotation_rfc3339, "-648h")
}

これで完了時刻は「マージ + バッファ」を上限に確定し、2回目の run を待つ必要も、その run がいつ走るかを気にする必要もなくなる。バッファの3日は「引き継ぎの run が予定から遅れても確実に走り終わる」余裕で、毎日スケジュール run を回している前提の値。

トレードオフ：expired_at を縮めるほど、run が止まったときに全トークンが失効して手動ブートストラップに戻るまでの猶予も縮む。23-07 の注意①と同じく定期 run が回っていることが前提で、止まったら検知すべき異常として扱う。

周期を変えたら expired_at も引き直す

上の -648h（27日）は周期60日に合わせて計算した定数だ。周期だけ変えてこの値を据え置くと静かに壊れる。たとえば周期を160日にして -648h のままだと、トークンの寿命は 160 − 27 = 133日になる。「認証情報は90日以内に失効させること」のような要件があるなら、これは気づきにくい違反になる。

覚えるのは関係式ひとつでいい。

  • 引き継ぎ ＝ 半周期（rotation_days ÷ 2）
  • トークンの寿命 ＝ 引き継ぎ ＋ バッファ
  • expired_at で引く値 ＝ 半周期 − バッファ

バッファ3日のときの対応は次のとおり。

rotation_days引き継ぎトークンの寿命引く値
60日30日33日-648h（27日）
160日80日83日-1848h（77日）
174日87日90日-2016h（84日）

要件から逆算するなら、許される寿命の上限を L として rotation_days ≤ (L − バッファ) × 2。L が90日・バッファが3日なら周期174日が天井で、ここは寿命がちょうど90日に張り付く。数日の余裕がほしければ周期を短くとる（160日なら寿命83日で7日の余裕）。逆にここで引き継ぎを90日にしたくなるが、それだと寿命が93日になって要件を割るので注意。

この定数を手で管理していると周期変更のときに引き直しを忘れる。変数から導出しておけば連動する。

variable "rotation_days" { default = 160 }
variable "buffer_days"   { default = 3 }

resource "time_rotating" "green" {
  rotation_days = var.rotation_days
}

resource "tfe_team_token" "green" {
  team_id     = tfe_team.manager.id
  description = "manager green ${time_rotating.green.rotation_rfc3339}"

  # 半周期 − バッファ だけ手前に引く
  expired_at = timeadd(
    time_rotating.green.rotation_rfc3339,
    "-${(var.rotation_days / 2 - var.buffer_days) * 24}h"
  )
}

なお 23-07 のままの expired_at（timeadd(rotation_rfc3339, "336h")）は「周期 ＋ 14日」なので、寿命は必ず周期より長くなる。失効期限に要件があるなら、23-07 の形では満たせない。本記事の引き算型にする必要がある。

定期ローテーションに PR は要らない

見落としやすいが、周期ローテーションではコードが1文字も変わらない。time_rotating が state に持っている「次にローテーションする時刻」を plan のたびにプロバイダが現在時刻と比べていて、過ぎていれば置き換えを要求する——という仕掛けなので（23-07 の仕組み）、周期の日を過ぎた最初の plan に、誰も何も変更していないのに差分が現れる。

だからやることは Plan & Apply を1回通すだけ。その apply の中で発行・切替・失効時刻の確定まで終わるので、2回目の run も PR も要らない。PR が要るのは次節の予定外ローテーションだけだ。

ただしこの「1回」には締切がある。トークン作成からの経過時間で並べるとこうなる。

  • 0日：green 発行、使用開始
  • 30日：blue が作り直され、TFE_TOKEN が blue へ切り替わる ← この run が必要
  • 33日：green が expired_at で自動失効

走らせ忘れると文鎮化する：34日目に Plan & Apply を押しても、使用中の green はすでに失効していて認証が通らない。初回と同じ手動ブートストラップからやり直しになる。つまり expired_at のバッファは、そのまま「run を走らせ損ねても許される日数」だ。3日という値は毎日スケジュール run が回っている前提であって、人が思い出して押す運用と組み合わせてはいけない。

逆に早く走らせるぶんには無害で、周期前なら time_rotating がまだ回っていないので差分ゼロの no-op になる。安全側の運用は「こまめに走らせる」——つまり定期 run に行き着く。手で押す運用にしたいなら、expired_at は 23-07 の timeadd(rotation_rfc3339, "336h")（切替の44日後に失効）のままにして、完了時刻が確定するというメリットのほうを諦める。バッファを何日にするかが、そのまま「誰が run を走らせるか」の宣言になる。

なお、差分が出たことを知らせる仕組みは用意されていない。plan を走らせて初めて分かるので、そこも定期 run に寄せる理由になる。

予定外のローテーションを PR で起こす

周期を待たずに今すぐ回したい（漏えいの疑いなど）ときは、description に世代番号を仕込んでおき、それを上げる PR を出す。description が変わればトークンは作り直されるので、マージ→run で切替まで終わる。

variable "green_serial" { default = 1 }  # 緊急ローテーション用

resource "tfe_team_token" "green" {
  # ...
  description = "manager green r${var.green_serial} ${time_rotating.green.rotation_rfc3339}"
}

上げてよいのは使っていない側の番号だけ。使用中の側を作り直す PR を出すと、その apply が自分の認証を消して文鎮化する。使用中トークンが漏えいした場合の手順は「先に切替、後に失効」——未使用側の番号を上げた PR をマージして切替を終わらせ、そのあと漏えいしたトークンを UI か API で revoke する。先に revoke すると、TFE_TOKEN が死んだトークンを指したまま次の run が動けなくなる。

Vault という答え

ここまでの工夫はすべて「長命トークンを持っている」ことへの対処だ。Vault を運用しているなら、持つこと自体をやめられる。run が Dynamic Credentials（OIDC）で Vault にログインし、Vault の Terraform Cloud secrets engine から TTL 付きの短命トークンを取得して tfe プロバイダに渡す。run が終わればトークンは TTL で勝手に失効する。

ただし静的シークレットがゼロになるわけではない。Vault が HCP Terraform の API を叩くための設定用トークンが1本、Vault の中に残る。正確には「消える」ではなく「1カ所に集約されて Vault の監査とアクセス制御の下に入る」だ。

判断軸はシンプルで、すでに Vault を運用しているかどうか。あるなら乗せる価値は大きい。このためだけに Vault を立てるのは、トークン1本の管理のために可用性を守るべきインフラを1つ抱えることになり、割に合わない。その場合は 23-07 の自己ローテーションに本記事の expired_at 短縮を足した構成が実質の最適解になる。

もう1つ、その Vault が Enterprise / HCP Vault Dedicated ならライセンスのクライアント枠も試算に入れる。クライアント数課金では JWT 認証のエンティティ（user_claim の一意な値）ごとに1クライアントを消費するので、ワークスペース単位で認証させればワークスペース数ぶん課金対象が増える（user_claim に sub を使うと run_phase ごとにエンティティが分かれて2倍になるので、terraform_full_workspace を使う）。本記事の範囲は管理用ワークスペース1個なので誤差だが、同じ仕組みを全ワークスペースの AWS 認証などへ横展開するとクライアント数はワークスペース数に比例して伸びる。Community 版のセルフホストならクライアント課金自体がない。
