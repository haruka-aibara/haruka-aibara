HCP Terraform を管理するワークスペースのトークンを自動ローテーションする

組織で一番強い権限を持つトークンほど、無期限発行して貼りっぱなしになりがち。ワークスペース自身に次のトークンを作らせて、人の手を初回の1回だけにする。

何が問題なのか

ワークスペース・チーム・Variable Set の作成を tfe プロバイダでコード化した「管理用ワークスペース」（workspace-of-workspaces）を作ると、手動管理が1つだけ残る。管理用ワークスペース自身が HCP Terraform の API を叩くための TFE_TOKEN だ。

AWS 側の認証は Dynamic Credentials（OIDC）で静的キーをなくせるのに、tfe プロバイダには執筆時点で OIDC 相当の仕組みがない。結果、「全ワークスペースを作り替えられる最強のトークン」が、無期限で発行されて変数にベタ貼りされたまま、という一番危ない状態になりやすい。

解決の軸は「管理用ワークスペースに、自分の次のトークンを作らせる」。tfe プロバイダは HCP Terraform 自身を操作できるので、トークンの発行も変数への書き戻しも Terraform リソースとして書ける。ループを閉じれば、人がトークンに触るのは初回のブートストラップだけになる。

部品は3つ

  • 専用チーム＋チームトークン：owners のトークンではなく、管理対象に必要な権限だけを持つチームを作り、そのトークンを使う。チームトークンは description を付ければ複数本を同時に有効化でき（2025年4月〜）、expired_at で有効期限も付けられる。Organization トークンは常に1本しか持てず権限も固定、User トークンは個人に紐づくため、どちらも不向き。
  • time_rotating：設定した周期が来ると差分が出るリソース。これがローテーションの起点になる。
  • tfe_variable（Variable Set）：発行した新トークンを sensitive な環境変数 TFE_TOKEN として、管理用ワークスペース自身に書き戻す。

落とし穴：使用中のトークンを消すと apply が死ぬ

トークンを1本だけ持って作り直す素朴な構成には罠がある。Terraform の「作り直し」は古いトークンの失効（revoke）を含むが、その apply 自身が古いトークンで API を叩いている。apply の途中で自分の認証を失効させると残りの API 呼び出しが 401 になり、変数の書き戻しに失敗して次の run も動けない——管理用ワークスペースが文鎮化する。

だからトークンは2本（ブルー／グリーン）を半周期ずらして持つ。使うのは常に「直近に作り直された方」。apply が置き換えるのは「もう使っていない古い方」だけなので、実行中の認証は壊れない。expired_at は、ローテーションが止まったときに古いトークンが生き残り続けないための保険として付ける。

書き方

# ローテーションの起点。アンカー日付を半周期（30日）ずらす
resource "time_rotating" "blue" {
  rfc3339       = "2026-01-01T00:00:00Z"
  rotation_days = 60
}

resource "time_rotating" "green" {
  rfc3339       = "2026-01-31T00:00:00Z"
  rotation_days = 60
}

# 管理専用チーム。権限は管理対象に必要な分だけ
resource "tfe_team" "manager" {
  name         = "workspace-manager"
  organization = var.organization
  organization_access {
    manage_workspaces = true
    manage_projects   = true
  }
}

# description が変わると新しいトークンとして作り直される
resource "tfe_team_token" "blue" {
  team_id     = tfe_team.manager.id
  description = "manager blue ${time_rotating.blue.rotation_rfc3339}"
  expired_at  = timeadd(time_rotating.blue.rotation_rfc3339, "336h") # 次の作り直し + 14日
}

resource "tfe_team_token" "green" {
  team_id     = tfe_team.manager.id
  description = "manager green ${time_rotating.green.rotation_rfc3339}"
  expired_at  = timeadd(time_rotating.green.rotation_rfc3339, "336h")
}

# 「直近に作り直された方」= 次の作り直しが遠い方を使う
locals {
  current_token = (
    timecmp(
      time_rotating.blue.rotation_rfc3339,
      time_rotating.green.rotation_rfc3339
    ) > 0
    ? tfe_team_token.blue.token
    : tfe_team_token.green.token
  )
}

# 管理用ワークスペース自身に書き戻す
resource "tfe_variable" "tfe_token" {
  key             = "TFE_TOKEN"
  value           = local.current_token
  category        = "env"
  sensitive       = true
  variable_set_id = tfe_variable_set.manager.id
}

注意は2つ。

① ローテーションは run が走ったときにしか起きない。周期の半分より短い間隔で run が回るように、スケジューラから定期的に API で plan / apply をキックする（VCS 連携で更新が頻繁にあるなら自然に回る）。run が完全に止まったまま expired_at を過ぎると初回と同じ手動ブートストラップからやり直しになるが、それは「検知すべき異常」として扱う。

② 初回だけは手動。自分の User トークンを TFE_TOKEN に入れて1回 apply すれば、以降はチームトークンに置き換わってループに入る。

さらに上を狙うなら

Vault を運用しているなら、Vault の Terraform Cloud secrets engine で run ごとに短命トークンを発行し、Vault-backed Dynamic Credentials で受け取る構成にできる。HCP Terraform 側に静的シークレットが一切残らないという意味ではこれが最高形。ただし Vault というインフラが1つ増えるので、Vault がない環境では本記事の自己ローテーションが実質の最適解になる。Vault 構成の中身と、「ローテーションはいつ完了と言えるのか」という論点は 23-08 で扱う。
