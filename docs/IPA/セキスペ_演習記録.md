### 落とした原因

**1(3) — JDBC の API が手に入っていない。** プレースホルダの理屈（先に構文を固定するから安全）は説明できるのに、`conn.createStatement()` と書いた。これは脆弱な側そのもの。理屈と API 名が結びついていない。

**2(2)(4) — レースコンディションの用語だけが単独で入っている。** 現象名は即答できたのに、原因（f: static）と対処（g: ローカル変数化）を両方落とした。`private` を付ければ直ると考えており、**可視性の問題と共有の問題を混同**している。

**2(5) — 認可の観点が出てこない。** 「注文番号だけで引ける＝番号を変えれば他人の注文が見える」に気づかず、絞り込みに**足す**項目ではなく**すでに入っている**項目を答えた。

**1(2) — 問題文からの読み取り。** 変数名を本文から拾う問題。知識ではなく精読・時間配分の課題。

### 覚え書き

**JDBC の書き分けは「SQL 文字列をいつ渡すか」で見分ける。**

```java
// 脆弱：SQLは実行時に渡す。文字列連結で組めてしまう
Statement stmt = conn.createStatement();
stmt.executeQuery("SELECT ... WHERE order_no = '" + orderNo + "'");

// 安全：SQLは生成時に渡す。値は後から ? に埋める
PreparedStatement stmt = conn.prepareStatement(sql);  // この時点で構文が確定
stmt.setString(1, orderNo);
stmt.executeQuery();
```

`prepareStatement(sql)` の `(sql)` が「先に構文解析させる」の実体。SQL 側の `?` が「値を入れる場所だけ空けておく」の実体。

**サーブレットのレースコンディションは、f →(3)→ g が一本の話。** サーブレットはインスタンスが1つで、複数リクエストが別スレッドで同時に入る。だから `static` やインスタンスフィールドに値を置くと全リクエストで共有され、他人の値で上書きされる。対処は**メソッド内のローカル変数にすること**（ローカル変数はスレッドごとのスタックに乗るので共有されない）。アクセス修飾子では直らない。生存期間と共有の問題であって可視性の問題ではない。

なお `OrderNo` は Java の命名規約ではクラス名の形。穴埋めは字句一致で採点されるので、変数名は小文字始まりで書く。

**「識別子を直接受け取って、本人のものか確認せずに引く」は午後の頻出パターン。** 名前は認可の欠落／水平権限昇格（IDOR）。設問で「検索条件に何を足すか」を問われたら、**所有者を絞る項目**を探す。今回なら得意先コード。
