OAuth — 他人のアプリに、パスワードを渡さずに一部だけ許可する

「このアプリにカレンダーの読み取りを許可しますか？」の裏側。認証ではなく認可の仕組み。

何が問題なのか

あるアプリに自分の SNS へ投稿させたい。素朴なやり方は、そのアプリに SNS の ID とパスワードを教えることだ。これだと投稿以外の何でもできてしまうし、やめたくなってもパスワードを変えるしかなく、他のアプリまで巻き添えになる。

OAuth はここを分解する。渡すのはパスワードではなく用途と期限が限られた引換券（アクセストークン）。何を許すかは利用者が選べ、あとから個別に取り消せる。

トークンには範囲と期限がある

  • スコープ：何ができるか（calendar.read のような単位）。アプリが要求し、利用者が同意した範囲に限られる。
  • 有効期限：アクセストークンは短命（数十分程度）。漏れても被害が続かない。
  • リフレッシュトークン：期限切れのたびに利用者に同意を求めないための長命の鍵。こちらが漏れると影響が長く続くので、保管の要求は厳しくなる。
  • 取り消し：利用者はサービスの設定画面から、アプリ単位で許可を取り消せる。パスワード変更と違って他のアプリに影響しない。

OAuth は認証ではない

もっとも多い誤用がこれ。アクセストークンが得られたことは「アプリがこのリソースを触ってよい」を意味するだけで、「目の前の人物が誰か」は保証しない。別のサイト向けに発行されたトークンを持ち込まれても見分けられず、なりすましのログインが成立してしまう。
「このサービスでログイン」を実装したいなら、OAuth の上に本人確認の層を足した OpenID Connect を使い、ID トークン（発行先と発行者が署名で確認できる JWT）を検証する。

実装で外せない点

  • PKCE を使う：認可コードを横取りされても交換できないようにする仕組み。スマホアプリや SPA のようにアプリの秘密を隠しておけない環境では必須で、現在はすべてのアプリ種別で推奨されている。
  • リダイレクト先を完全一致で登録する：ここを緩く（前方一致やワイルドカードで）登録すると、攻撃者のサイトへコードを送らせる経路ができる。
  • state パラメータを検証する：利用者の意図しない連携を仕込まれる（CSRF）のを防ぐ。
  • 暗黙的フロー（Implicit）は使わない：トークンをブラウザに直接返す古い方式で、現在は非推奨。
