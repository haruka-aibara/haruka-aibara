SAML — SaaS 側にパスワードを持たせずにログインさせる

認証は自社の IdP でやり、その結果だけを署名付きの XML で SaaS に渡す。

何が問題なのか

会社で使う SaaS が10個あると、利用者は10個のパスワードを持つ。管理側から見ると、退職者の無効化を10か所でやることになり、1つでも消し忘れれば外から入られる。パスワードポリシーも多要素認証も、SaaS ごとにできることが違う。

SAML は、認証そのものを自社側（IdP）に集約し、「この人は認証済みで、こういう属性を持つ」という証明書だけを SaaS に渡す仕組み。SaaS 側にパスワードは存在しなくなる。

登場人物は2つだけ

  • IdP（Identity Provider）：認証する側。Microsoft Entra ID、Okta、Google Workspace など。
  • SP（Service Provider）：使いたい側。SaaS アプリケーション。

アサーションの中身

やり取りされる XML を SAML アサーションと呼ぶ。入っているのは3種類。

  • 誰か：利用者を示す識別子（メールアドレスなど）
  • 属性：部署、ロール、グループ。SP 側はこれを見て権限を決められる
  • 条件：有効期限、あて先（この SP 宛てである、という指定）

全体に IdP の秘密鍵でXML デジタル署名が施されており、SP は事前に登録しておいた IdP の証明書で検証する。この署名がすべての土台になっている。

検証を1つ手抜きすると成りすませる

SP の実装で繰り返し起きてきた事故がある——署名の対象範囲を確認しない、あて先や有効期限を見ない、といった検証漏れ。XML の構造をいじって署名対象外の場所に別の利用者名を紛れ込ませるXML Signature Wrapping は、この種の実装不備を突く古典的な攻撃。自前で SAML の受け側を実装するのは避け、実績あるライブラリを使うべき領域。

実務で見るところ

  • 証明書の有効期限：IdP 側の署名用証明書が切れると、その SaaS に誰もログインできなくなる。更新日をカレンダーに載せる。
  • SCIM とセットで考える：SAML はログインを担うが、アカウントの作成・削除はしない。退職者の削除まで自動化するにはアカウント連携（SCIM）が要る。
  • SAML と OAuth は別物：SAML は「人が SaaS にログインする」ための仕組み。OAuth は「アプリが API を叩く許可を得る」ための仕組みで、目的が違う。新規のブラウザログインでは、SAML の役割を軽量な JSON で置き換えた OpenID Connect が選ばれることも増えている。
