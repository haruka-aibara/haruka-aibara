Kerberos — パスワードを1度も送らずに、社内の全サーバを使う

チケットを配る係を1つ置いて、以降はそのチケットで各サーバに入る。Active Directory の土台。

何が問題なのか

社内にファイルサーバ、データベース、業務システムが何十とある。利用者に毎回パスワードを入力させれば手間だし、サーバの数だけパスワードがネットワークを流れる。そのうえ各サーバがパスワードを検証できる＝パスワード（相当の情報）を持っているということで、1台の侵害が全体に波及する。

Kerberos の答えは「認証する係を1つに絞り、そこが発行した通行証を各サーバに見せる」。ネットワークは盗聴されている前提で設計されている。

登場人物

用語意味
realm（レルム）1つの KDC が管理する範囲。Active Directory のドメインにあたる。慣習として大文字で書く
プリンシパル認証の対象となる主体の名前。利用者だけでなくサービスにも付く（host/fs01.example.com など）
KDC（鍵配布センター）チケットを発行する中心。AS と TGS の2つの機能を持つ
AS（認証サーバ）最初の認証を行い、TGT（チケットを貰うためのチケット）を渡す
TGS（チケット発行サーバ）TGT と引き換えに、個別のサービス用チケットを発行する
KDB（鍵データベース）全プリンシパルの鍵を保管する。ここが漏れると realm 全体が終わる

チケットは「自分では中を読めない封筒」

サービスチケットはあて先サーバの鍵で暗号化されている。利用者はそれを持ち運ぶが、中身を読むことも書き換えることもできない。サーバ側は自分の鍵で開けるだけで、KDC に問い合わせる必要がない——ここが RADIUS のような都度問い合わせ型と違う点で、サーバが増えても KDC への負荷が増えにくい。

チケットには利用者名・有効期限・セッション鍵が入っている。利用者はチケットに加えて、現在時刻をセッション鍵で暗号化したもの（オーセンティケータと呼ばれる）を添えて送る。これで「チケットを盗んだだけの第三者」を弾く。

時刻がずれると認証が通らない

リプレイ攻撃を時刻で防いでいるため、KDC と各サーバ・端末の時計は同期していなければならない。既定の許容差は5分程度で、これを超えると正しいパスワードでもログインできなくなる。Active Directory 環境で突然認証が通らなくなったときに、まず NTP を疑うのはこのため。

攻撃の的になるのは KDC

設計上、KDB（とくに TGT に署名する krbtgt の鍵）を握られると、攻撃者は任意の利用者・任意の権限のチケットを自分で作れる。これが Golden Ticket 攻撃で、その後はパスワード変更でも止まらない（krbtgt の鍵を2回変更する必要がある）。ドメインコントローラを他のサーバと同じ扱いで運用しない、管理者アカウントの経路を分ける、といった対策の根拠はここにある。
