チャレンジレスポンス認証 — パスワードを流さずに本人を確かめる

毎回違う「お題」を出して、それに答えられるかで判定する。答えを盗んでも次には使えない。

何が問題なのか

パスワードをそのまま送れば、経路上で盗聴されて終わる。ではハッシュ値にして送れば安全か——ならない。盗聴した攻撃者は中身を知らなくても、その値をそのまま送り返せば認証を通れる。パスワードが漏れなくてもログインは奪われる（リプレイ攻撃）。

この「送る値が毎回同じだから再利用できる」という構造そのものを壊すのが、チャレンジレスポンス認証。

手順

どこで使われているか

  • CHAP：PPP のダイヤルアップ認証。この方式の代表例で、接続中に何度も再認証する。
  • APOP：POP3 のパスワードを平文で流さないための拡張（APOP）。
  • HTTP ダイジェスト認証・NTLM・EAP-MD5：いずれも同じ骨格。

この方式だけでは足りない

2つの限界がある。

1つはサーバ側の保管。サーバも同じ計算をする必要があるため、パスワードの平文（かそれに準ずるもの）を持たなければならない。ソルト付きハッシュで保管する現在の作法と両立しにくく、サーバが漏れたときの被害が大きい。

もう1つは中間者に無力なこと。攻撃者が経路に割り込めば、チャレンジをそのまま転送し、返ってきたレスポンスをそのまま使って本物のサーバにログインできる。相手が本物かを確かめる手段がこの方式には含まれていない。

そのため現在は、TLS で経路と相手を確保したうえで、その中でパスワードを送るという構成が主流になっている。チャレンジレスポンスは、暗号化された経路が前提にできなかった時代の解法として理解しておくとよい。
