AAA フレームワーク — 認証だけでは足りない残り2つ

誰か（Authentication）、何ができるか（Authorization）、何をしたか（Accounting）。分けて考えると設計の穴が見える。

何が問題なのか

アクセス制御の話をしていると、議論が「ログインできるかどうか」に寄っていく。だが実際の事故は、その先で起きる。正規のアカウントでログインした人が、必要のない権限まで持っていた。あるいは何をしたのか誰も分からない。認証が正しく動いていても、この2つは防げない。

AAA は、この3つを別々の機能として分けて設計するための枠組み。ネットワーク機器の世界で生まれた言葉だが、クラウドでもそのまま通用する。

実装はプロトコルや製品として存在する

RADIUSTACACS+Diameter
主な用途無線 LAN・VPN の利用者認証ネットワーク機器の管理者ログイン通信事業者網（RADIUS の後継として設計）
3つの分離認証と認可が一体認証・認可・記録を個別に扱える個別に扱える
通信UDP、パスワード部分のみ隠蔽TCP、本体全体を暗号化TCP／SCTP＋TLS

TACACS+ が「機器にログインして show は許すが configure は許さない」といったコマンド単位の制御に使われるのは、認可を認証と切り離して都度問い合わせられるため。用途で使い分ける。

クラウドでも同じ3つ

AWS で言えば、IAM の認証（サインイン、MFA、IAM ロールの引き受け）、IAM ポリシーによる認可、そして CloudTrail がアカウンティングにあたる。ネットワーク機器の話に見えて、構造はそのまま当てはまる。

提案するときの言い方

「ログを取りましょう」は用途が語られていないので通りにくい。「誰が何をしたかの記録がないと、インシデントが起きたときに原因調査も、被害範囲の特定も、外部への説明もできない」——止まるのは調査ではなく事業の説明責任のほう、という言い方をすると、認証・認可と同じ土俵で議論できる。
