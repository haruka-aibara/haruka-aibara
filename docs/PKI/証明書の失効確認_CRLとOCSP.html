CRL と OCSP — 期限内なのに無効になった証明書をどう伝えるか

秘密鍵が漏れた証明書は取り消される。その事実を、世界中の検証者にどう届けるか。

何が問題なのか

証明書には有効期限が書いてある。だが期限より前に無効にしたい事態が起きる——サーバの秘密鍵が漏れた、誤って発行した、社員が退職して従業員証明書を止めたい。

ここで困るのは、証明書が署名された時点で完結した文書だということ。中身に「無効になりました」と書き足すことはできない。取り消した事実は、証明書の外側で伝えるしかない。

「応答がないとき」をどう扱うかが難所

OCSP レスポンダに繋がらなかったら、接続を止めるべきか、通すべきか。

止める（hard-fail）と、レスポンダが落ちただけで世界中のサイトが見られなくなる。通す（soft-fail）と、攻撃者はレスポンダへの通信を遮断するだけで失効チェックを無効化できる。
実際のブラウザは soft-fail を選んできた。つまり失効チェックは攻撃者に止められる程度のものでしかない——これが長年の実情。

だから実装は別の方向へ動いた

  • OCSP ステープリング：サーバがあらかじめ OCSP レスポンダから「有効」の署名付き応答をもらっておき、TLS ハンドシェイクで一緒に渡す。検証側は問い合わせ不要になり、プライバシーの問題も消える。
  • 有効期間の短縮：そもそも証明書が短命なら、失効の出番自体が減る。サーバ証明書の有効期間が年々短くなっているのはこの流れによるもの。
  • ブラウザ独自の配布：主要ブラウザは、重要な失効情報を圧縮して自前の更新機構で配る方式（CRLSets、CRLite など）に移行している。

近年は OCSP そのものを縮小する方向が業界の合意になっており、CA/Browser Forum の要件でも OCSP は必須ではなくなった。「失効を後から伝えるのは難しいので、短命な証明書で自動更新する」という設計に置き換わってきている。

閉じたネットワークでの落とし穴

インターネットに出られないサーバやクライアント端末で、証明書の検証時に CRL や OCSP を取りに行こうとしてタイムアウトするまで数十秒固まるという事象がよく起きる。原因は失効確認の通信がプロキシで止まっていること。証明書の設定を疑う前に、失効情報の取得先（証明書に書かれている CDP／AIA の URL）に到達できるかを確認する。
