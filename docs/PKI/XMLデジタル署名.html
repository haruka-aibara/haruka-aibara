XML デジタル署名 — 署名を文書のどこに置くかで3種類

デタッチ・エンベロープド・エンベローピング。名前は紛らわしいが、図にすれば一目で分かる。

何が問題なのか

XML 文書に署名したい。ところが XML には、意味が同じでも書き方が何通りもあるという性質がある——タグの前後の空白、属性の並び順、名前空間の宣言位置、改行コード。バイト列としてハッシュを取ると、送受信の途中で処理系がこれらを整えただけで値が変わり、改ざんしていないのに署名検証が失敗する。

そこで XML の署名には2つの仕掛けが要る。1つは書き方のゆれを揃える正規化。もう1つが、署名を文書のどこに配置するかという形式の選択。

どれを使うか

  • デタッチ：署名の対象が XML 以外のとき、また大きなファイルに後から署名を添えるとき。
  • エンベロープド：既存の XML の構造を保ったまま署名を足したいとき。SAML のアサーションはこの形。
  • エンベローピング：署名とデータを1つにまとめて渡したいとき。

正規化を忘れると相互運用できない

署名を作る前に、正規化（Canonicalization、C14N）で書き方を揃える。属性を決まった順に並べ、名前空間の宣言を整理し、空白の扱いを統一する。この規則をどれにするかは署名の中に記録され、検証側も同じ規則で処理する。ここが送信側と受信側でずれると、正しい署名なのに検証が通らない、という形で表面化する。

XML Signature Wrapping

XML 署名では「署名の対象がどこか」を署名の中の URI で指している。この間接参照が攻撃の入口になる。攻撃者は正規の署名済み要素を文書の別の場所に移し、そこに自分が作った偽の要素を置く。実装が「署名は検証できたか」だけを見て「検証した要素が、実際に処理した要素と同じか」を見ていないと、偽の内容が受理される。
SAML の認証バイパスとして繰り返し報告されてきた古典的な脆弱性。XML 署名を自前で扱うときは、検証済みの要素そのものを処理対象にする実装になっているかを確認する。
