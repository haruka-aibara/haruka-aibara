# ファイルシステム

新しいディスクをマウントしようとして「wrong fs type」と怒られた。あるいはフォーマット時に `mkfs.ext4` か `mkfs.xfs` かで手が止まった。ファイルシステムは「気にしなくていいもの」に見えて、作るとき・壊れたとき・性能問題のときに突然選択を迫られる。

## ファイルシステムは「ブロックデバイスとファイルの間の翻訳層」

ディスクそのものはただのバイト列（ブロックデバイス）で、「ファイル」「ディレクトリ」という概念を持っていない。それをどう区画して、メタデータ（iノード）をどう置き、書き込み中の電源断からどう回復するか——この設計がファイルシステム。だから同じディスクでもフォーマット次第で性質が変わる。

いま使っているファイルシステムの確認：

```bash
df -T           # マウント中のファイルシステムと種類
lsblk -f        # ブロックデバイスごとのファイルシステム
```

## 主要な選択肢と使い分け

| FS | 特徴 |
|---|---|
| **ext4** | Linux の長年のデフォルト。枯れていて情報が多い。迷ったらこれで困ることはほぼない |
| **XFS** | 大容量・並列 I/O に強い。RHEL 系のデフォルト。**縮小できない**（拡張のみ）点だけ注意 |
| **Btrfs** | スナップショット・チェックサム・圧縮を内蔵。openSUSE や Fedora（デスクトップ）が採用 |

実務での判断はシンプルで、**ディストリビューションのデフォルトに従う**のが基本線。ext4/XFS の性能差が問題になるワークロードは限られていて、それが問題になる頃には計測に基づいて選べるようになっている。

なお、いずれもジャーナリング機能を持っており、書き込み途中でクラッシュしてもファイルシステム自体の整合性は保たれる（書き込み中だったデータの中身までは保証しない）。

## 壊れたときの修復

起動時に「ファイルシステムエラーで emergency mode に落ちた」場合の修復コマンドが fsck。

```bash
sudo umount /dev/sdb1        # 必ずアンマウントしてから
sudo fsck /dev/sdb1
```

**マウント中のファイルシステムに fsck をかけてはいけない**（破壊する可能性がある）。ルートファイルシステムの場合はレスキューモードやライブ USB から実行する。XFS は fsck ではなく `xfs_repair` を使う。
