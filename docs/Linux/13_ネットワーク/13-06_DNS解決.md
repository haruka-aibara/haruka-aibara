# DNS解決

障害の切り分けで「IP 直打ちなら届くのに、ホスト名だと失敗する」となったら、犯人は DNS。逆に「たまにタイムアウトする」「特定のホストからだけ接続できない」といった不可解な症状も、掘っていくと DNS 解決の失敗や遅延だったというのは定番中の定番。「とりあえず DNS を疑う」は経験則としてかなり強い。

## 名前解決の流れ

アプリがホスト名で接続するとき、OS のリゾルバが設定された DNS サーバーに問い合わせて IP に変換する。Linux でその設定を持つのが `/etc/resolv.conf`。

```bash
cat /etc/resolv.conf
```

```
nameserver 127.0.0.53    # systemd-resolved のスタブ。実体は resolvectl status で見る
```

最近の Ubuntu などでは `127.0.0.53` と書かれていて面食らうが、これはローカルの systemd-resolved が代理応答している構成。実際にどの DNS サーバーに聞いているかは `resolvectl status` で確認する。

もうひとつ、DNS より先に参照されるのが `/etc/hosts`。「hosts に古いエントリが残っていて、みんなと違う IP を見ていた」という一人だけ壊れる系の障害があるので、不可解なときは hosts も見る。参照順序は `/etc/nsswitch.conf` の `hosts:` 行が決めている。

## 調査コマンドは dig

```bash
dig example.com                    # A レコードを引く
dig example.com @8.8.8.8           # 問い合わせ先を指定（「どのDNSが悪いか」の切り分け）
dig +short example.com             # IP だけ欲しいとき
dig -x 93.184.216.34               # 逆引き
```

`@サーバー指定` が切り分けの要。「システム設定の DNS では引けないが 8.8.8.8 なら引ける」なら内部 DNS の問題、「どこに聞いても引けない」なら権威側かレコード自体の問題、と一発で二分できる。

`nslookup` でも同じことはできるが、出力の情報量と診断オプションの豊富さで dig が調査用途の標準。

## TTL とキャッシュ：「反映されない」の正体

DNS レコードには TTL（キャッシュしてよい秒数）があり、世界中のリゾルバがその期間は古い答えを返し続ける。「DNS を切り替えたのに古いサーバーにアクセスが来る」のは障害ではなく仕様。`dig` の応答の数字（TTL 残秒数）で、あとどれくらい待つかが分かる。切り替え作業の前に TTL を短くしておく、が定石なのはこのため。

セキュリティの視点をひとつ：DNS クエリは組織の通信の「行き先の記録」そのもので、マルウェアの C2 通信も大抵は名前解決から始まる。AWS なら Route 53 Resolver クエリログや DNS Firewall がこの層の可視化・制御に当たる。
