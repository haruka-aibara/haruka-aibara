# サブネット化

VPC を設計するとき、`10.0.0.0/16` を切るのか `/24` を並べるのか。ファイアウォールルールに `192.168.1.0/24` と書いたとき、それが具体的にどの範囲を許可しているのか。CIDR 表記を「読める」ことは、クラウド時代ではネットワーク機器を触らない人にも必須になった。

## CIDR 表記の読み方

`10.0.1.0/24` の `/24` は「先頭24ビットがネットワーク部（=固定）、残り8ビットがホスト部（=そのネットワーク内で自由）」という意味。

- `/24` → ホスト部 8bit → 256 アドレス（10.0.1.0〜10.0.1.255）
- `/16` → ホスト部 16bit → 65,536 アドレス
- `/32` → ホスト部 0bit → その1アドレスだけ（セキュリティグループで単一ホストを指すときの書き方）

覚え方は「**/が大きいほど範囲は狭い**」。/8 は巨大、/32 はピンポイント。手計算が面倒なら `ipcalc` に投げる：

```bash
ipcalc 10.0.1.0/24
```

なお実際に使えるホスト数は、ネットワークアドレスとブロードキャストアドレスを引いて254（AWS はさらに3つ予約するので251）。「/24 のサブネットに256台入れる」計画は最初から破綻している、という類の話はここから来る。

## なぜ分割するのか

技術的な理由（ブロードキャストドメインの分割）より、実務では**境界を作るため**と理解したほうが早い。

- **障害の境界**: セグメントが分かれていれば影響範囲を局所化できる
- **セキュリティの境界**: 「DBサブネットには Web サブネットからしか到達できない」のような制御は、サブネットが分かれていて初めて書ける。AWS のパブリック/プライベートサブネット分離はまさにこれ
- **経路制御の単位**: ルートテーブルはサブネット単位で紐づく

つまりサブネット設計は「どこに壁を立てたいか」の設計で、CIDR はその壁の座標を表す記法。

## Linux 側から見る

自分がどのサブネットにいて、どこがゲートウェイかは ip コマンドで見える。

```bash
ip addr show      # 自分の IP と /プレフィックス
ip route show     # 経路テーブル。default via ... がゲートウェイ
```

「同じサブネット宛は直接届き、それ以外はゲートウェイに投げる」——ホストの通信はこの1行に集約される。`ip route get 8.8.8.8` で「この宛先ならどの経路を使うか」をピンポイントで確認できるのは、切り分けで地味に便利。
