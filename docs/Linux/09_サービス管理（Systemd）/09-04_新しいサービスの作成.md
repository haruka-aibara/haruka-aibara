# 新しいサービスの作成

自作のスクリプトやアプリをサーバーで常駐させたい。`nohup ./app &` で放置したり cron の `@reboot` で起動したりしがちだが、それだとプロセスが死んでも誰も気づかないし、ログも散逸する。systemd のサービスにしてしまえば、自動起動・自動再起動・ログ集約・状態確認を全部 systemd が面倒を見てくれる。

## ユニットファイルを置く

自作サービスの定義は `/etc/systemd/system/` に `.service` ファイルとして置く（`/lib/systemd/system/` はパッケージが使う領域なので触らない）。

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=My Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=myapp
ExecStart=/opt/myapp/bin/server --config /etc/myapp/config.yml
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

3セクションの役割：

- **[Unit]**: サービスの説明と起動順序。ネットワークが必要なアプリなら `After=network-online.target` を書いておかないと、ブート時にネットワーク確立前に起動して失敗する
- **[Service]**: 何をどう実行するか。`ExecStart` が本体。`Restart=on-failure` を入れておくと異常終了時に勝手に再起動してくれる——これだけで nohup 運用より圧倒的に堅い
- **[Install]**: `enable` したときにどの起動段階に組み込むか。通常は `multi-user.target` で固定と覚えてよい

## root で動かさない

`User=` の指定は省略できるが、省略すると root で動く。アプリに脆弱性があったとき、root で動いていれば即サーバー全体の掌握につながる。専用ユーザーを作って権限を絞るのが基本。

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin myapp
```

## 反映して起動する

ユニットファイルを置いた（or 編集した）だけでは systemd は認識しない。リロードしてから enable する。

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
systemctl status myapp
```

「ファイルを直したのに挙動が変わらない」の原因はほぼ `daemon-reload` 忘れ。編集したら必ずセットで打つ。

アプリが stdout にログを吐いていれば、`journalctl -u myapp -f` でそのまま追える。ログファイルの置き場所やローテーションを自分で設計しなくていいのも、サービス化の利点のひとつ。
