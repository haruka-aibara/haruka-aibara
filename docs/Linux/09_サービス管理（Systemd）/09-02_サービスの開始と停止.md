# サービスの開始と停止

設定ファイルを書き換えたのに挙動が変わらない——サービスは起動時に設定を読み込むものが多いので、変更を反映するには再起動（またはリロード）が要る。この「変更したら反映操作をする」が systemctl を使う一番多い場面。

## 基本の4操作

```bash
sudo systemctl start nginx     # 起動
sudo systemctl stop nginx      # 停止
sudo systemctl restart nginx   # 停止→起動
sudo systemctl reload nginx    # プロセスを止めずに設定だけ再読み込み
```

状態を変える操作なので root 権限（sudo）が必要。確認系（`status`, `is-active`）は一般ユーザーでも打てる。

## restart と reload の使い分け

設定変更の反映だけなら、まず `reload` を検討する。restart はプロセスを一度殺すので、その瞬間のリクエストは切断される。reload は nginx や sshd のように対応しているサービスなら無停止で設定を読み直せる。

```bash
sudo systemctl reload-or-restart nginx
```

reload 対応ならreload、非対応なら restart にフォールバックしてくれるので、どちらか迷うならこれでいい。

なお nginx の設定変更なら、反映前に `sudo nginx -t` で構文チェックする癖をつけると「reload したら設定エラーで全断」を防げる。多くのミドルウェアに同種の dry-run がある。

## 「いま起動」と「次回ブートでも起動」は別

`start` はいまのセッションで起動するだけで、サーバーを再起動すると上がってこない。ブート時の自動起動は `enable` で設定する。

```bash
sudo systemctl enable nginx          # 次回ブートから自動起動
sudo systemctl enable --now nginx    # 自動起動を設定しつつ、いま起動もする
sudo systemctl disable nginx         # 自動起動をやめる（いま動いているものは止まらない）
```

ミドルウェアを入れて動作確認までしたのに、数週間後のメンテ再起動で障害になる——というのは `enable` を忘れた典型パターン。恒久的に動かすサービスは `enable --now` を習慣にするのが安全。

## 止めたのに勝手に復活するとき

`stop` してもすぐ `active` に戻る場合、ソケット起動（`.socket` ユニット）や他サービスの依存で再起動されていることがある。一時的にも起動させたくないなら：

```bash
sudo systemctl mask nginx    # 起動そのものを禁止（start も失敗するようになる）
sudo systemctl unmask nginx  # 解除
```
