# ICMP

ping や traceroute を毎日使っていても、その下で動いている ICMP を知らないと「ping は通らないのにサービスは動いている」「セキュリティグループで ICMP を塞いだら別の何かが壊れた」といった現象を正しく解釈できない。

## ICMP は「ネットワーク自身がエラーを報告するための言語」

TCP や UDP がアプリのデータを運ぶのに対し、ICMP（Internet Control Message Protocol）は**ネットワーク機器やホストが制御情報・エラーを伝え合う**ためのプロトコル。ポート番号を持たず、IP の上で直接動く。

代表的なメッセージ：

| タイプ | 意味 | 使われどころ |
|---|---|---|
| Echo Request / Reply | 生きてる？／生きてる | ping の実体 |
| Destination Unreachable | 宛先に届けられない | 「port unreachable」など、失敗理由の通知 |
| Time Exceeded | TTL が尽きた | traceroute はこれを利用して経路を炙り出す |
| Redirect | もっと良い経路がある | 経路の最適化通知（悪用もされるため無視する設定が多い） |

つまり ping と traceroute は「ICMP の特定メッセージを使った応用ツール」であり、ICMP はそれ以外の場面でも裏で失敗理由を運んでいる。

## 「ping 不通 ≠ ホストダウン」を正しく読む

ICMP はセキュリティ設定で落とされていることが多い。AWS のセキュリティグループはデフォルトで ICMP を許可しないので、**EC2 に ping が通らないのは正常**。ホストの死活は `curl` や `nc` で実際のサービスポートを叩いて判断する。

```bash
nc -zv 10.0.1.5 443    # TCP 443 に到達できるか（ping の代わりの死活確認）
```

逆に言うと、切り分けでは「ping 不通・ポート到達可」＝ ICMP だけフィルタされている、「ping 到達可・ポート不通」＝ホストは生きていてサービス側の問題、と情報を組み合わせて読む。

## ICMP を全部塞ぐと壊れるものがある

「セキュリティのため ICMP 全遮断」は昔からある雑な設定で、副作用として **Path MTU Discovery が壊れる**。経路上の MTU を超えたパケットに対して「Fragmentation Needed」という ICMP が返れなくなると、「小さい通信は通るのに大きいデータを送ると固まる」という極めて分かりにくい障害になる（VPN 経由で特定サイトだけ開けない、などの典型原因）。遮断するなら Echo だけに絞るなど、タイプ単位で制御する。
