# ping

「つながらない」の一報を受けて最初に打つコマンド。ICMP Echo Request を投げて返事を待つだけの単純な道具だが、単純ゆえに「返ってこなかったとき何を意味するか」の読み方で差がつく。

## 基本の使い方と出力の読み方

```bash
ping -c 4 10.0.1.5      # -c 4: 4回で止める（Linux はデフォルト無限なので付ける癖を）
```

```
64 bytes from 10.0.1.5: icmp_seq=1 ttl=64 time=0.42 ms
64 bytes from 10.0.1.5: icmp_seq=2 ttl=64 time=0.38 ms
--- 10.0.1.5 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3055ms
rtt min/avg/max/mdev = 0.38/0.41/0.45/0.03 ms
```

見るべきは3つ：

- **packet loss**: 0% なら到達性は健全。数%のロスは「つながるけど遅い・切れる」系の症状と符合する
- **time (RTT)**: 同一 VPC 内で数十 ms 出ていたら何かおかしい。継続的な監視値との比較で意味を持つ
- **icmp_seq の抜け**: 断続的なロスはケーブル・無線・輻輳など物理層/経路の不安定を示唆

## 切り分けの階段として使う

ping 単発ではなく、**近いところから順に登る**ことで問題の位置を特定する：

```bash
ping -c 3 127.0.0.1        # 自分の TCP/IP スタック
ping -c 3 10.0.1.1         # デフォルトゲートウェイ（ここまでは LAN の話）
ping -c 3 8.8.8.8          # インターネット（IP で）
ping -c 3 example.com      # 名前解決込み
```

この階段のどこで落ちるかで、自ホスト／LAN／経路／DNS のどれが犯人かが決まる。特に「8.8.8.8 は通るのに example.com がダメ」なら**ネットワークではなく DNS の問題**と即断できる——この2行の比較だけで調査範囲が半分になる。

## 返ってこないときの読み方

[15-01_ICMP](15-01_ICMP.md) の通り、**ping 不通はホストダウンを意味しない**。ICMP がフィルタされている環境（AWS のセキュリティグループのデフォルト等）は普通にある。不通だったら `nc -zv <host> <port>` で実ポートへの到達を確認してから結論を出す。

エラーメッセージにも情報がある：

- `Destination Host Unreachable`: 経路の途中（または自分）が「そこへの道を知らない」— ARP 解決失敗やルート欠落
- 無言でタイムアウト: パケットがどこかで黙って捨てられている — ファイアウォールの DROP が典型
