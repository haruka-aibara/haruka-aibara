# パケット解析

ログにもメトリクスにも出ない通信の問題——「接続はできるのに応答が変」「どちら側が切断したのか分からない」「本当にリトライしているのか？」——の最終手段が、実際に流れているパケットを見ること。推測が尽きたとき、パケットは嘘をつかない。

## tcpdump：サーバー上でキャプチャする

```bash
sudo tcpdump -i eth0 -n port 443
#             │       │  └ フィルタ式：443番ポートの通信だけ
#             │       └ 名前解決しない（出力が速く読みやすい）
#             └ インターフェース指定。全部なら -i any
```

フィルタ式は絞り込みの要。無指定だと出力が洪水になるので、必ず対象を絞る：

```bash
sudo tcpdump -i any -n host 10.0.2.15                  # 特定ホストとの通信
sudo tcpdump -i any -n 'tcp port 5432 and host 10.0.2.15'   # 組み合わせ
sudo tcpdump -i any -n icmp                             # ping が本当に届いているか
```

読み方の最初の一歩は **TCP のフラグ**。`[S]`（SYN=接続要求）、`[S.]`（SYN-ACK=応答）、`[R]`（RST=拒否）、`[F.]`（FIN=正常切断）。たとえば「SYN を送っているのに SYN-ACK が返らない」が見えれば、相手かその手前で落ちていると**確定**する——ここまでの各ツールが状況証拠なのに対し、これは直接証拠。

## 現実的なワークフロー：サーバーで採って、手元で見る

ターミナル上で流し読みできるのは単純なケースまで。実際の調査は「サーバーで pcap ファイルに保存し、手元の Wireshark で開く」が定石。

```bash
sudo tcpdump -i any -n port 443 -w /tmp/capture.pcap    # Ctrl-C で停止
# 手元に持ってきて Wireshark で開く
scp server:/tmp/capture.pcap .
```

Wireshark なら TCP ストリームの再構成（会話を時系列で追う）、再送・重複 ACK の自動検出、TLS ハンドシェイクの失敗箇所の特定までGUIでできる。「たまに遅い」系は再送の有無を見るだけで、ネットワーク起因かアプリ起因かが切り分けられる。

## 注意点

- **中身が見える＝見られる**。平文プロトコルの通信はパケットを採れば認証情報まで丸見えになる。だからこそ全部 TLS にする意味があり、逆に pcap ファイル自体も機密情報として扱う（調査が終わったら消す）
- キャプチャには root 権限が要る。本番サーバーで長時間流しっぱなしにするとディスクと CPU を食うので、フィルタと `-c`（パケット数上限）で範囲を絞る
- クラウドでは自ホスト以外のトラフィックは見えない。VPC 全体の観測は VPC Traffic Mirroring / Flow Logs の領分（Flow Logs はメタデータのみで中身は見えない、という違いも押さえておく）
