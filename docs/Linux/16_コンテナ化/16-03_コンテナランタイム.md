# コンテナランタイム

「Kubernetes が Docker を非推奨にした」というニュースに動揺した人は多かったが、あれはコンテナが動かなくなる話ではなかった。この手の話を正しく理解するには「コンテナランタイム」という層の分かれ方を知る必要がある。逆に言えば、それさえ分かればニュースも障害調査もクリアに見える。

## ランタイムは2層に分かれている

コンテナを動かす仕事は、実際には役割の違う2層に分かれている：

- **高レベルランタイム**: イメージの取得・展開、コンテナのライフサイクル管理、API 提供。**containerd**、CRI-O がこれ
- **低レベルランタイム**: namespace と cgroups を実際に設定してプロセスを起動する実行係。事実上の標準が **runc**（OCI Runtime Spec の参照実装）

Docker はこの上にさらに CLI・イメージビルド・ネットワーク管理などを被せた「全部入りツールキット」で、内部では containerd → runc を呼んでいるだけ。つまり：

```
docker CLI → dockerd → containerd → runc → コンテナ（ただのプロセス）
Kubernetes(kubelet) → containerd → runc → コンテナ
```

「Kubernetes の Docker 非推奨」の実態は、kubelet が dockerd を経由するのをやめて containerd と直接話すようにしただけ。**イメージは OCI 標準なので、Docker でビルドしたイメージはそのまま containerd でも動く**。層が分かっていれば何も怖くない話だった。

## どれに触れるかは環境で決まる

- **手元の開発**: Docker（または互換の Podman）。ビルドと試行錯誤の道具が揃っている
- **Kubernetes ノード**: containerd か CRI-O。デバッグでノードに入ったら docker コマンドはなく、`crictl`（CRI 用 CLI）や `ctr` を使う。「ノードに docker ps がない！」は初見で誰もが焦るポイント

```bash
crictl ps                # ノード上のコンテナ一覧（docker ps 相当）
crictl logs <container>  # ログ確認
```

- **AWS**: ECS/EKS のノードも containerd。Fargate のようなマネージド実行環境ではランタイム層自体が隠蔽される

## セキュリティの視点：ランタイムは隔離の要

コンテナの隔離はカーネル機能の設定で成り立っているので、**ランタイムの脆弱性＝隔離の破れ（コンテナエスケープ）**に直結する。runc には実際にエスケープ可能な CVE が複数出ている（CVE-2019-5736 など）。ここから言えること：

- ノードのランタイムを更新し続ける運用が必要（マネージドノードの利点はここ）
- より強い隔離が要る場合は、gVisor や Kata Containers のような「サンドボックス型ランタイム」に差し替えるという選択肢もある（runc 互換の口で置き換えられる——層が分かれていることの恩恵）
