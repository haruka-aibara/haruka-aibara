# パッケージリポジトリ

`apt install` したら「パッケージが見つからない」と言われた。あるいは、入れたいソフトの新しいバージョンが公式リポジトリにまだ来ていない。こういうとき「リポジトリとは何で、どこを参照しているのか」を知らないと手が止まる。

## リポジトリは「ディストリビューションが検証したパッケージの置き場」

パッケージマネージャは、野良のダウンロードサイトではなく、ディストリビューションが管理するサーバー（リポジトリ）からパッケージを取ってくる。ここに置かれるものは署名付きで、依存関係も解決済み。「どこかの zip を落として展開する」のと違って、出所の検証とアップデートの追従が仕組みとして保証されているのが本質的な価値。

Debian/Ubuntu 系は `.deb`、RHEL/Fedora 系は `.rpm` という形式で、リポジトリもそれぞれの系列ごとに別物。

## 「見つからない」の最初の一手はインデックス更新

`apt install` は、ローカルに持っている「リポジトリの目次のコピー」を見て動く。この目次が古いと、存在するはずのパッケージが見つからなかったり、古いバージョンを掴んだりする。

```bash
sudo apt update        # 目次を更新するだけ。パッケージ自体は変わらない
```

RHEL 系（dnf）はコマンド実行時に自動でメタデータを更新するので、この操作を明示的に打つ文化があるのは主に Debian/Ubuntu 系。`apt update` は「アップデートのインストール」ではなく「目次の更新」——ここを混同していると `apt upgrade` との違いが分からなくなる。

## どこを参照しているか確認する

```bash
# Debian/Ubuntu
cat /etc/apt/sources.list
ls /etc/apt/sources.list.d/

# RHEL/Fedora
dnf repolist
```

## サードパーティリポジトリを追加するとき

公式リポジトリにないもの（Docker、HashiCorp 製品など）は、ベンダーが自前のリポジトリを提供していることが多い。追加手順はだいたい「署名鍵を登録 → リポジトリ定義を置く → インデックス更新」の3点セット。

```bash
# 例: Docker の apt リポジトリ追加（公式手順の骨子）
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu noble stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update
```

署名鍵の登録は「このリポジトリの発行元を信頼する」という宣言。リポジトリを追加するということは、そこの発行者にサーバーへソフトを供給する権限を渡すのと同じなので、追加するのは公式ベンダーのものに限るのが原則。出所の怪しい PPA や rpm リポジトリはサプライチェーン攻撃の入口になる。
