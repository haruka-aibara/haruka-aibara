# Snap

apt のリポジトリに入っているバージョンが古すぎる、あるいはディストリビューションごとにパッケージの有無がバラバラで手順書が書きづらい。そういう「配布側の都合」を解決するために Canonical が作ったのが Snap。

## 何が違うのか

apt/dnf のパッケージは「システム共有のライブラリに依存する」前提で作られている。だからディストリビューションやバージョンごとにビルドし直しが必要で、リポジトリに入るバージョンも保守的になりがち。

Snap は**依存ライブラリを全部同梱した自己完結型パッケージ**。どのディストリビューションでも同じ snap がそのまま動き、開発元が Snap Store（Snapcraft）に直接公開するので最新版が来るのも速い。イメージとしてはコンテナに近い（実際、サンドボックス化されて動く）。

```bash
sudo snap install code --classic   # 例: VS Code
snap list                          # インストール済み一覧
sudo snap remove code
```

（`--classic` はサンドボックスの制限を外すオプション。エディタや開発ツールなどシステム全体にアクセスする必要があるものはこれを要求してくる）

## 自動更新とトランザクショナルな更新

Snap はデフォルトで**勝手に自動更新される**。更新はトランザクショナルで、失敗すると前のバージョンに自動ロールバックする。手元の開発マシンでは「放っておけば常に最新」で楽な一方、サーバー用途では「意図しないタイミングで更新が走る」と捉えることもできる。更新タイミングは制御できる。

```bash
snap refresh --list                          # 更新可能な snap を確認
sudo snap refresh --hold=72h firefox         # 更新を一時停止
sudo snap set system refresh.timer=sat,03:00 # 更新ウィンドウを指定
```

## 実務での位置づけ

- Ubuntu では一部パッケージ（Firefox など）が apt で入れても実体は snap になっている。「apt で入れたのに snap list に出てくる」のはこれ
- ディスク使用量は apt 版より大きく、初回起動もやや遅い。ループバックマウントが増えるので `df` の出力が snap だらけになるのも既知の挙動（異常ではない）
- サーバー構築を自動化する文脈では、バージョン固定がしづらい自動更新の性質から、apt/dnf や公式リポジトリを優先して Snap は避ける判断も普通にある

「どこでも同じものが最新で動く」が欲しいデスクトップ・開発ツール向きの仕組み、と押さえておけばよい。
