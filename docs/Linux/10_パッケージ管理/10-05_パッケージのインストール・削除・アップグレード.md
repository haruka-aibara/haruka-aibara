# パッケージのインストール・削除・アップグレード

インストールは [10-03](10-03_パッケージの検索とインストール.md) で扱ったので、ここでは運用で必ず発生する「アップグレード」と「削除」、つまりパッケージのライフサイクル管理を押さえる。放置されたパッケージは脆弱性の温床になるし、雑に消したパッケージは設定ファイルのゴミを残す。

## アップグレード

```bash
# Debian/Ubuntu：目次更新 → 更新内容の確認 → 適用
sudo apt update
apt list --upgradable
sudo apt upgrade

# RHEL/Fedora
dnf check-update
sudo dnf upgrade
```

いきなり `upgrade` せず、間に「何が上がるか」の確認を挟むのがサーバー運用での作法。カーネルや glibc が含まれるなら再起動計画とセットで考える必要があるし、ミドルウェアのメジャーバージョンアップが混ざっていたら個別に検証したい。

特定パッケージだけ上げることもできる。脆弱性対応で「openssl だけ今すぐ上げたい」ときはこれ。

```bash
sudo apt install --only-upgrade openssl
sudo dnf upgrade openssl
```

## 削除

Debian/Ubuntu では「削除」に2段階あるのを知らないと、消したはずの設定が残って混乱する。

```bash
sudo apt remove nginx    # 本体を削除。/etc の設定ファイルは残る
sudo apt purge nginx     # 設定ファイルごと削除
```

`remove` で設定が残るのは「入れ直すときに設定を引き継げる」ようにするための仕様。検証で入れて消すだけなら `purge`、再インストール前提なら `remove` と使い分ける。RHEL 系の `dnf remove` には purge 相当はなく、設定ファイルは `.rpmsave` として残ることがある。

依存として入ったが、もう誰からも必要とされていないパッケージは別途掃除する：

```bash
sudo apt autoremove
sudo dnf autoremove
```

## 事故ったときの調べ方

「昨日まで動いていたのに」という障害の原因が直近のパッケージ更新だった、はよくある話。何がいつ変わったかは履歴で追える。

```bash
less /var/log/apt/history.log   # Debian/Ubuntu
dnf history                     # RHEL/Fedora（dnf history undo <ID> で巻き戻しも可能）
```

障害調査の初動で「最近サーバーに加えられた変更」を確認する癖をつけると、この履歴が効いてくる。
