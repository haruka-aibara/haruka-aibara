# デバッグ

シェルスクリプトが「途中まで動いて、どこかで変になる」。printf デバッグで echo を差し込みまくる前に、シェルに元から備わっている仕掛けを使ったほうが早い。

## bash -x：実行トレース

スクリプトが実際に実行したコマンドを、変数展開後の姿で1行ずつ表示してくれる。

```bash
bash -x deploy.sh
```

```
+ APP_DIR=/opt/myapp
+ rsync -avz ./dist/ /opt/myapp/
+ systemctl restart myapp
```

`+` 付きの行がトレース。「変数に何が入った状態でコマンドが実行されたか」が見えるので、「パスが空文字で `rm -rf /` 相当になりかけていた」ような事故も実行前の dry-run 的な確認で気づける。特定の区間だけ絞りたいときはスクリプト内で挟む：

```bash
set -x    # ここからトレース開始
問題のありそうな処理
set +x    # ここで終了
```

## set -euo pipefail：転ばぬ先の3点セット

デバッグ以前に「エラーを握りつぶして進む」というシェルのデフォルト挙動を止めるのが先決。スクリプト冒頭にこれを書く：

```bash
#!/bin/bash
set -euo pipefail
```

- `-e`: コマンドが失敗したら即終了（デフォルトは失敗しても次の行へ進む）
- `-u`: 未定義変数の参照をエラーに（タイポした変数が空文字として通るのを防ぐ）
- `-o pipefail`: パイプ途中の失敗を検知（`curl ... | jq` で curl が死んでも、デフォルトでは jq の終了コードしか見ない）

「cd に失敗したのに続きを実行して別のディレクトリを破壊した」という類の惨事は、ほぼ `-e` がなかったことで起きる。

## shellcheck：書いた時点で指摘してもらう

実行前に静的解析でバグを見つけるツール。クォート忘れ、未定義変数、`[ ]` の誤用など、シェル特有の罠を的確に指摘してくれる。

```bash
shellcheck deploy.sh
```

指摘には SC2086 のような番号が付いていて、Wiki で「なぜ危険か・どう直すか」まで読める。エディタ拡張や CI に入れておけば、レビューで人間がクォート忘れを探す仕事がなくなる。シェルスクリプトを書くすべての現場で入れる価値がある。

## それでも分からないとき

- `trap 'echo "line $LINENO: exit $?"' ERR` — どの行で失敗したかを出す
- `echo "${var@Q}"`（bash 4.4+）— 変数の中身をクォート付きで表示。空白や改行の混入が見える
