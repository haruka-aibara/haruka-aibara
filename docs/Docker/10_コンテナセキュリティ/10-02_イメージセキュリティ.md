# イメージセキュリティ

コンテナのセキュリティ事故で最も多いのは、派手なエスケープではなく地味な話——**脆弱なライブラリ入りのイメージをそのまま動かしていた**、**イメージに秘密情報が焼き込まれていた**、**出所不明のベースイメージを使っていた**。イメージセキュリティはこの3つを潰す活動と言っていい。

## 1. 脆弱性：イメージは「作った瞬間から腐り始める」

イメージは不変＝**中のパッケージは自動更新されない**。半年前にビルドしたイメージは、半年分の CVE を抱えたまま動き続ける。だから：

**スキャンをパイプラインに組み込む**（手動でたまに、ではなく）：

```bash
trivy image myapp:1.4.2        # CI でビルド直後に実行し、Critical があれば fail
```

ECR なら push 時の自動スキャン（Inspector 連携で継続スキャンも）が使える。重要なのは「push 時に一度」だけでなく、**動いているイメージを新しい CVE 情報で再評価し続ける**こと——ビルド時点でクリーンでも、翌週に Critical が公表されることは普通にある。

**定期的に再ビルドする**：ベースイメージのパッチを取り込む唯一の方法は再ビルド。「アプリに変更がなくても週次でリビルド・再デプロイ」を仕組み化する。

**攻撃面を最初から減らす**：脆弱性の数はおおむねパッケージ数に比例する。`python:3.13-slim` や distroless のような最小イメージ＋マルチステージビルド（[07-03](../07_コンテナイメージのビルド/07-03_イメージサイズとセキュリティ/)）で、ビルドツールを最終イメージに残さない。

## 2. 秘密情報：レイヤーは足し算しかできない

`COPY .env` した後のレイヤーで消しても、レイヤーには永久に残る（[02-03_ユニオンファイルシステム](../02_基盤技術/02-03_ユニオンファイルシステム.md)）。

- ビルド時の秘密は `--mount=type=secret`、実行時の秘密は環境変数やオーケストレータの secret 機構で**実行時に注入**
- `.dockerignore` に `.env` `.git` `*.pem` を入れて、そもそもビルドコンテキストに秘密を入れない
- push 前の検査として `docker history` やシークレットスキャナ（trivy は秘密検出もする）をかける

「public レジストリに社内イメージを push したら AWS キーが入っていた」は、GitHub への秘密コミットと並ぶ定番インシデント。

## 3. 出所：そのイメージは誰が作ったか

`FROM` に書いた1行は、そのイメージ作者にアプリの土台を委ねる行為。

- ベースイメージは Docker Official / Verified Publisher / ベンダー公式レジストリに限定（[08-03](../08_コンテナレジストリ/08-03_Dockerhub.md)）
- タグは動く。すり替えが懸念される文脈ではダイジェスト固定＋署名検証（cosign）まで（[08-01](../08_コンテナレジストリ/08-01_イメージタグ付けのベストプラクティス.md)）
- 組織としては「承認済みベースイメージを社内レジストリに置き、FROM はそこからのみ」という統制（ゴールデンイメージ方式）が定石

## 優先順位

全部一度にはできないので、効果順に：①CI にスキャナを入れて Critical で fail ②.dockerignore と secret の注入方式を直す ③最小ベースイメージへの移行 ④定期リビルドの仕組み化 ⑤署名・ポリシー強制。①②は今日入れられて、事故の大半をカバーする。
