# ランタイムセキュリティ

イメージがどれだけクリーンでも、実行のさせ方が雑ならそこから崩れる。ランタイムセキュリティの問いは一つ：**このコンテナが乗っ取られたとき（アプリの脆弱性は防げない前提）、攻撃者はどこまで行けるか**。答えは実行時オプションの積み重ねで決まる。

## 脅威モデル：コンテナ内 root → ホスト root への道

アプリの RCE 脆弱性でコンテナ内に侵入された、と仮定する。攻撃者の次の目標はコンテナエスケープ（ホストの掌握）か、横移動。その通り道を1つずつ塞ぐのがランタイムセキュリティ：

| 通り道 | 塞ぎ方 |
|---|---|
| コンテナ内で root として活動 | `USER` 指定で非 root 実行 |
| カーネル機能の悪用（ケーパビリティ） | `--cap-drop=ALL` ＋必要分だけ `--cap-add` |
| setuid バイナリでの昇格 | `--security-opt no-new-privileges` |
| FS 改ざん・マルウェア設置 | `--read-only --tmpfs /tmp` |
| docker.sock 経由でホスト掌握 | ソケットをマウントしない（最重要級） |
| リソース枯渇（DoS） | `--memory` `--cpus` `--pids-limit`（[02-02](../02_基盤技術/02-02_cgroups.md)） |

まとめると、堅いコンテナの run はこうなる：

```bash
docker run -d \
  --user 10001:10001 \
  --cap-drop=ALL \
  --security-opt no-new-privileges \
  --read-only --tmpfs /tmp \
  --memory=512m --pids-limit=100 \
  myapp
```

## 絶対にやらないことリスト

- **`--privileged`**：全ケーパビリティ＋全デバイスアクセス。隔離を自分で外すスイッチで、エスケープは自明になる。「これで動いたから」は権限で問題を踏み潰しただけ
- **`-v /var/run/docker.sock:...` の安易なマウント**：コンテナからデーモンを操作できる＝新しい privileged コンテナを起動できる＝**ホスト root と等価**。CI ツールや監視ツールが要求してくる定番だが、本当に必要か・代替（DinD ではなく kaniko、ソケットプロキシ等）がないかを毎回疑う
- **`--network host` の常用**：ネットワーク分離を放棄し、ホストの全ポートに直接触れる

## ビジネス側への言語化

「コンテナだから隔離されていて安全なんでしょ？」と聞かれたときの答え：コンテナの隔離はカーネル共有の上に成り立っており、**設定次第で紙にも壁にもなる**。上記の設定は追加コストほぼゼロで入れられる保険で、入れない理由が特にない。ECS/Kubernetes ならタスク定義・securityContext で同じ項目を宣言でき、「本番ワークロードは非 root・privileged 禁止」をポリシー（OPA/Conftest 等）で強制するのが組織としての着地点になる。

実行中の検知（Falco 等によるランタイム監視、GuardDuty Runtime Monitoring）はこの次の層の話で、まず上記の「攻撃面を減らす」が先。
