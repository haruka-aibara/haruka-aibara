# なぜコンテナが必要か

「手元では動くのに、サーバーだと動かない」。OS のバージョン違い、ライブラリの有無、環境変数、微妙に違う設定——環境差異は再現困難バグの最大の温床で、コンテナはこの問題への回答として普及した。

## コンテナ以前の世界

コンテナ以前、アプリの配布物は「コード＋手順書」だった。手順書には「Python 3.x を入れて、これらのパッケージを入れて、この設定ファイルを置いて…」とあり、実行環境はサーバーごとに人が組み立てていた。この方式の問題：

- **手順書は腐る**：書いた時点の OS・ミドルウェアが前提。半年後には再現しない
- **サーバーが「秘伝のタレ」化する**：長年の手作業が積もり、誰も完全には再現できない
- **開発と本番がズレる**：微妙な違いが「手元では動く」バグを生む
- **同居アプリが干渉する**：同じサーバーの別アプリとライブラリバージョンが衝突する

## コンテナが変えたこと

コンテナは「**実行環境ごと**アプリを1個の不変なイメージに焼き固めて配る」方式に変えた。

- 手順書は Dockerfile という**実行可能なコード**になり、腐ればビルドが失敗して即分かる
- 開発・CI・本番で**バイト単位で同じもの**が動く。「手元では動く」の大部分が消える
- 依存はイメージ内に閉じるので、同居アプリと干渉しない
- 起動が秒未満なので、「壊れたら直す」ではなく「**消して作り直す**」運用ができる——スケールアウトも障害復旧もデプロイも、全部「新しいコンテナを起動する」に統一される

最後の点が本質で、コンテナはインフラを「ペットから家畜へ」（1台ずつ世話する対象から、置き換え可能な単位へ）変えた。Kubernetes や ECS のようなオーケストレーションも、この「使い捨てできる単位」があって初めて成立している。

## VM ではダメだったのか

VM でも環境の固定はできる（イメージ化）。ただし VM イメージは GB 単位で起動に分単位かかり、「アプリ1個の配布単位」としては重すぎた。コンテナは MB 単位・秒未満起動で、**アプリの粒度**に合った初めてのパッケージングだった、という位置づけ（詳細は [01-03](01-03_ベアメタルvsVMvsコンテナ.md)）。
