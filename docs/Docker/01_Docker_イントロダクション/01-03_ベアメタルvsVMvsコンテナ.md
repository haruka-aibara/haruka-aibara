# ベアメタル vs VM vs コンテナ

「コンテナがあるなら VM はもう要らないのでは」——実際にはクラウドのコンテナは大抵 VM の上で動いており、3層は競合ではなく積み重なっている。それぞれ何を分離していて、何と引き換えにしているかを整理する。

## 3つの違いは「どの層を共有するか」

| | ベアメタル | VM | コンテナ |
|---|---|---|---|
| 分離の単位 | 物理マシン | 仮想ハードウェア＋ゲストOS | プロセス |
| カーネル | 専有 | ゲストごとに専有 | **ホストと共有** |
| 起動時間 | 分 | 分 | 秒未満 |
| オーバーヘッド | なし | あり（ハイパーバイザ＋ゲストOS） | ほぼなし |
| 隔離の強さ | 物理的に完全 | 強（ハードウェアレベル） | 中（カーネルレベル） |
| 密度（1台あたり） | 1 | 数十 | 数百〜 |

- **ベアメタル**: OS が物理ハードウェアを直接使う。性能を1%も無駄にしたくない用途（DB専用機、HPC）や、ライセンス・規制上の理由で残る
- **VM**: ハイパーバイザが仮想ハードウェアを見せ、その上でゲスト OS が丸ごと動く。カーネルレベルで別マシンなので隔離が強い
- **コンテナ**: カーネル共有のプロセス隔離（[01-01](01-01_コンテナとは何か.md)）。軽くて速いが、隔離はカーネルの実装に依存する

## 実際は「VM の上でコンテナ」が標準

EC2 上の ECS/EKS、GKE、AKS——クラウドのコンテナ基盤は VM の上にコンテナを重ねた構成が標準。理由は役割分担にある：

- **VM がテナント間の境界**：クラウド事業者は顧客同士の隔離をカーネル共有のコンテナに任せない。悪意ある隣人と共有するのはハイパーバイザまで
- **コンテナがアプリの配布・実行単位**：同一チーム内のワークロードを高密度に詰め込む

セキュリティの観点でもこの整理は重要で、「コンテナはカーネル共有」という性質上、**信頼できないコード同士の境界としてはコンテナ単体では不十分**というのが定説。だから Fargate や Lambda は、コンテナ相当の使い勝手を保ちつつ、実体は Firecracker という軽量 VM（microVM）でテナントを分離している——「起動はコンテナ並みに速く、境界は VM」という両取りの進化形。

## 使い分けの目安

- 自チームのアプリを配布・運用する単位 → コンテナ
- 信頼境界（別テナント、別顧客、任意コード実行）→ VM（または microVM／サンドボックスランタイム）
- 極限性能・特殊ハードウェア・ライセンス制約 → ベアメタル
