# イメージタグ付けのベストプラクティス

「本番で動いているイメージ、どのコードから作られたやつ？」に即答できないなら、タグ運用が壊れている。タグはただのラベルで、**同じタグを別のイメージに付け替えられる**——この可変性を理解していないと、再現性もロールバックも成立しない。

## latest 運用がダメな理由

```bash
docker pull myapp:latest   # 今日と明日で別物が落ちてくるかもしれない
```

- `latest` は「最新」ですらなく、単に「タグ省略時のデフォルト名」。push する側が明示的に動かさなければ古いまま
- デプロイ後に問題が起きても、**どのバージョンが動いているのか特定できない**
- ロールバックしようにも「前の latest」はもう存在しない

本番のデプロイ指定が `latest` になっているのは、バージョン管理をしていないのと同義。

## 実務のタグ設計

1つのイメージに複数タグを付けるのが基本形：

```bash
docker tag myapp myaccount/myapp:1.4.2          # セマンティックバージョン
docker tag myapp myaccount/myapp:1.4             # マイナーまで（1.4系の最新を追う人向け）
docker tag myapp myaccount/myapp:a1b2c3d         # git コミットSHA
```

- **git SHA タグ**：「このイメージはどのコードか」への完全な答え。CI で自動付与する
- **セマンティックバージョン**：人間向け。`1.4` のような「動くタグ」は利用者の追従ポリシーに合わせて提供
- **環境タグ（staging, prod）は「今どれが載っているか」の印**としては使えるが、付け替えられるので記録としては SHA に頼る

## 不変性が本当に必要なら：ダイジェスト指定とタグ免疫

タグは動くが、**ダイジェスト（イメージ内容の SHA256）は動かない**：

```bash
docker pull nginx@sha256:abc123...   # 内容をピン留め。完全に再現可能
```

Kubernetes のマニフェストや基盤イメージの FROM で「絶対に変わってほしくない」場合はダイジェスト指定が最終手段。ECR にはタグの上書きを禁止する設定（tag immutability）もあり、「1.4.2 が後から別物にすり替わる」ことをレジストリ側で防げる。すり替え検知はサプライチェーンセキュリティの論点でもあり、署名（cosign 等）まで踏み込む世界もある。

## ベースイメージを pull する側として

`FROM python:3.13-slim` の `3.13-slim` も動くタグで、再ビルドのたびに中身が更新されうる（セキュリティパッチが入る=良い面もある）。ビルドの完全な再現性が要る場合はダイジェスト併記（`python:3.13-slim@sha256:...`）で固定し、更新は Renovate 等で管理された PR として受け取る、が現代的な落とし所。
