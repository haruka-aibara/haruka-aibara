# 前提知識：ユーザとグループの権限

Docker では権限の知識がないと説明できない現象に最初からぶつかる。「sudo なしで docker コマンドが打てない」「バインドマウントしたファイルの所有者が root になって消せない」——どちらも Linux のユーザ・グループ・パーミッションの話。

## docker グループ＝実質 root、を理解して使う

Docker デーモンは root で動いており、そのソケット（`/var/run/docker.sock`）を触れる人は誰でもコンテナを起動できる。`docker` グループにユーザを足すと sudo なしで使えるようになるが：

```bash
sudo usermod -aG docker $USER   # 再ログインで反映
```

これは利便性と引き換えに、**そのユーザに実質 root 権限を渡す**操作でもある（ホストの / をマウントしたコンテナを起動すれば何でもできるため）。開発マシンでは普通にやる設定だが、「docker グループは sudoers と同じ重み」という感覚は持っておく。

## コンテナ内の UID はホストの UID そのもの

コンテナはユーザ空間を分離しているように見えて、**UID の数字はホストとそのまま共有している**。コンテナ内の root（UID 0）はホスト上でも UID 0。バインドマウントで root のコンテナがファイルを作ると、ホスト側に「root 所有のファイル」が生まれて消せなくなる——あの現象の正体はこれ。

```bash
docker run -u "$(id -u):$(id -g)" -v "$PWD":/work myimage   # 自分の UID で動かす
```

コンテナを root で動かさない理由（Dockerfile の `USER` 指定）も同じ理屈から来ている。
