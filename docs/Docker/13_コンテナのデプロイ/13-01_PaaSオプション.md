# PaaS オプション

イメージはできた。さてどこで動かすか。「Kubernetes を勉強してから」と構えるのは、多くのケースで過剰。**イメージを渡せば実行・スケール・HTTPS まで面倒を見てくれる PaaS** が、個人開発〜中規模サービスの現実解になっている。

## PaaS が肩代わりしてくれるもの

自前でコンテナを運用する場合、Docker の外側に必要なものが山ほどある：サーバーの調達とパッチ、リバースプロキシと TLS 証明書、ロードバランサ、オートスケール、ログ収集、デプロイの仕組み。PaaS はこれを「イメージ（かコードリポジトリ）を渡す」だけに圧縮する。

主な選択肢：

- **AWS App Runner / Google Cloud Run / Azure Container Apps**：クラウド各社の「コンテナを渡すだけ」系。特に Cloud Run は**リクエストがない時間はゼロにスケール**（課金もゼロ近く）が特徴で、この種のサービスの代表格
- **Fly.io / Render / Railway**：開発者体験重視の独立系。CLI 一発デプロイ、無料枠、Heroku 的な手軽さの後継
- **ECS + Fargate**：PaaS というよりマネージドオーケストレータだが、「サーバー管理なしでコンテナを動かす」という点で実務上この文脈に並ぶ。AWS 内で本格運用に育てる場合の受け皿

## 選び方の軸

- **既にいるクラウド**：組織が AWS なら App Runner か ECS/Fargate。権限・ネットワーク・監査を既存基盤に揃える価値は大きい
- **トラフィック特性**：間欠的（社内ツール、デモ）ならゼロスケールする Cloud Run 系が圧倒的に安い。常時高トラフィックなら常駐型と大差なくなる
- **制約の確認**：PaaS は「型にはまれば楽」の裏返しで、WebSocket の制限、実行時間上限、VPC 内リソースへの接続方法などの制約がある。はまらない要件が出てきたときが ECS/Kubernetes への卒業タイミング

## セキュリティの観点

PaaS は責任共有の線がさらに上に上がる（ホスト OS・ランタイムの管理は事業者側）。利用者側に残るのは**イメージの中身**（[10-02](../10_コンテナセキュリティ/10-02_イメージセキュリティ.md)）と**アプリ・認証設定**。「インフラを見なくていい」は「何も見なくていい」ではなく、脆弱性スキャンと秘密管理はどこで動かそうと自分の仕事として残る。
