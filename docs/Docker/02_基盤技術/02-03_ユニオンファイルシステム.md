# ユニオンファイルシステム

同じベースイメージのコンテナを100個起動してもディスクはほぼ増えない。`docker pull` の出力は数行に分かれて並列に進む。イメージに `rm` を書いてもイメージサイズが減らない——この3つの現象はすべて、イメージが**レイヤーの重ね合わせ**でできていることから来ている。それを実現する仕組みがユニオンファイルシステム（Docker の現行実装は **OverlayFS**）。

## 仕組み：読み取り専用の層を重ね、最上段だけ書ける

ユニオンファイルシステムは、複数のディレクトリ（層）を重ねて**1つのファイルシステムに見せる**カーネル機能。

- イメージの各レイヤーは**読み取り専用**。Dockerfile の命令（RUN、COPY…）ごとに1層できる
- コンテナ起動時、その上に**書き込み可能な薄い層**（コンテナレイヤー）を1枚だけ足す
- 読み取りは上の層から順に探し、書き込みはすべて最上段に行く

冒頭の現象はこれで説明がつく：

- **100コンテナでもディスクが増えない**：読み取り専用レイヤーは全コンテナで共有され、増えるのは各コンテナの薄い書き込み層だけ
- **pull が並列に進む**：レイヤー単位でダウンロードし、手元にある層はスキップする（`Already exists` の表示）
- **rm してもサイズが減らない**：下の層のファイルは消せないので、「消えたことにする印」を上の層に置くだけ。**レイヤーは足し算しかできない**

## 実務に効く帰結

**1. 秘密情報は「後のレイヤーで消しても」残る**

```dockerfile
COPY secret.key /tmp/     # この層に永久に残る
RUN use-key && rm /tmp/secret.key   # 見えなくなるだけ
```

`docker history` や各レイヤーの展開で取り出せてしまう。ビルド時の秘密は BuildKit の `--mount=type=secret` を使う（レイヤーに残らない）。

**2. サイズ削減は「同一 RUN 内で消す」**

```dockerfile
RUN apt-get update && apt-get install -y build-essential \
 && make && make install \
 && apt-get purge -y build-essential && rm -rf /var/lib/apt/lists/*
```

同じ RUN（＝同じ層）の中で消せばレイヤーに焼き込まれない。層をまたぐと手遅れ。より根本的にはマルチステージビルド（[07-03-01](../07_コンテナイメージのビルド/07-03_イメージサイズとセキュリティ/07-03-01_マルチステージビルド.md)）で解決する。

**3. コンテナ書き込み層への書き込みは遅くて消える**

書き込み層は copy-on-write（下の層のファイルを変更する際、まず上にコピーしてから書く）でオーバーヘッドがあり、かつコンテナ削除で消える。だからログは stdout へ、データはボリュームへ（[05_データ永続化](../05_データ永続化/)）が原則になる。

レイヤーキャッシュを効かせる Dockerfile の書き方は [07-02_効率的なレイヤーキャッシング](../07_コンテナイメージのビルド/07-02_効率的なレイヤーキャッシング/) を参照。
