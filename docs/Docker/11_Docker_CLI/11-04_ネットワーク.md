# Docker CLI：ネットワーク操作

bridge ネットワークの仕組み・コンテナ間通信・名前解決は [09章の extra 記事群](../09_コンテナの実行/) で詳しく扱っている。ここでは CLI での**調査**——「コンテナ同士がつながらないとき何を見るか」を軸にまとめる。

## 一覧と調査

```bash
docker network ls                     # ネットワーク一覧（bridge/host/none ＋自作）
docker network inspect mynet          # 接続中のコンテナ・サブネット・ゲートウェイ
```

「つながらない」調査の最初の一手は、**2つのコンテナが同じネットワークにいるかの確認**：

```bash
docker inspect api --format '{{json .NetworkSettings.Networks}}' | jq 'keys'
docker inspect db  --format '{{json .NetworkSettings.Networks}}' | jq 'keys'
```

別ネットワークにいれば届かないのが正常。また、**名前解決（`db` というホスト名で届く）が効くのはユーザー定義ネットワークだけ**で、デフォルトの bridge では効かない——「compose だと動くのに docker run で並べたら db が解決できない」の正体はこれ。

## つなぐ・切る

```bash
docker network create mynet               # ユーザー定義ネットワーク作成
docker network connect mynet api          # 実行中コンテナを追加接続（再起動不要）
docker network disconnect bridge api      # 切断
```

`connect` は動いているコンテナに後付けできるので、「調査用コンテナを対象と同じネットワークに入れて curl する」という切り分けができる：

```bash
docker run --rm -it --network mynet nicolaka/netshoot
# → dig db / curl http://api:8080/health / ss -tln などが一通り入った調査用イメージ
```

## 分離の設計として使う

ネットワークは到達性の制御でもある。compose で「web は frontend と backend 両方、db は backend のみ」と分ければ、**web が侵害されても db への直接経路はあるが、db はインターネット側ネットワークに存在しない**という段階的な分離が作れる。セキュリティグループのレイヤー分けと同じ発想をホスト内でやるイメージ。

## 掃除

```bash
docker network prune    # どのコンテナも接続していないネットワークを削除
```

compose の up/down を繰り返すプロジェクトでは `<プロジェクト名>_default` が溜まりがち。実害は少ないが、サブネット（172.x.0.0/16）を食い潰すと「新しいネットワークが作れない」エラーになることがある。
