# Docker CLI：ボリューム操作

ボリュームの概念と使い分け（ボリューム vs バインドマウント）は [05_データ永続化](../05_データ永続化/) にまとめてある。ここでは CLI での**管理・調査・掃除**——特に「消してはいけないデータを持っているのはどれか」を特定する操作を扱う。

## 一覧と調査

```bash
docker volume ls                    # ボリューム一覧
docker volume inspect pgdata        # 実体のパス（Mountpoint）等
docker volume create appdata        # 明示的に作成（run -v で自動作成もされる）
```

運用で一番大事な問いは「**このボリューム、どのコンテナが使っている（いた）のか**」。逆引きはこう：

```bash
docker ps -a --filter volume=pgdata   # このボリュームをマウントしているコンテナ
```

コンテナ側から見る場合は `docker inspect <container>` の `Mounts` セクション。無名ボリューム（64桁のハッシュ名）が大量にあるときは、`-v /data` のようにボリューム名を省略した run や、イメージの `VOLUME` 命令が犯人であることが多い。**残したいデータには必ず名前を付ける**のが管理の第一歩。

## 中身を覗く

ボリュームはコンテナにマウントしないと中が見えない。使い捨てコンテナで覗くのが定石：

```bash
docker run --rm -v pgdata:/data alpine ls -la /data
```

バックアップも同じパターンで取れる：

```bash
docker run --rm -v pgdata:/data -v "$PWD":/backup alpine \
  tar czf /backup/pgdata-$(date +%Y%m%d).tar.gz -C /data .
```

## 掃除：prune の前に必ず確認

```bash
docker volume prune     # どのコンテナにも使われていないボリュームを削除
```

**ボリュームの削除は不可逆で、バックアップがなければデータは戻らない**。しかも「停止中のコンテナが使っているボリューム」は prune 対象外だが、コンテナを `rm` した後のボリュームは「未使用」扱いになる——つまり「DB コンテナを作り直そうとして rm → prune」の流れでデータを飛ばす事故が構造的に起きやすい。prune の前に `docker volume ls` と上記の逆引きで中身を確認する癖をつける。
