# テスト

「テストは通るのに本番で落ちる」原因の一定数は、テスト環境が本番と違うことにある。DB をモックにしてテストしていたら、本物の PostgreSQL の型変換で落ちた——コンテナはこの「テスト環境の忠実度」問題への実用解を提供する。

## 依存サービスを本物で立てる

コンテナ以前、テストで DB や Redis を使うには共有のテスト環境を予約するか、モックで我慢するかだった。コンテナなら**本物をテストのたびに使い捨てで起動**できる：

```yaml
# compose.test.yml
services:
  test:
    build: .
    command: pytest -v
    depends_on:
      db:
        condition: service_healthy
    environment:
      DATABASE_URL: postgresql://test:test@db:5432/test
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: test
      POSTGRES_PASSWORD: test
      POSTGRES_DB: test
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U test"]
      interval: 2s
      retries: 15
```

```bash
docker compose -f compose.test.yml run --rm test
```

ポイントは `healthcheck` ＋ `condition: service_healthy`。これがないと「DB のプロセスは起動したがまだ接続を受け付けていない」タイミングでテストが走り、**たまに落ちる flaky テスト**になる。コンテナでのテストの不安定さの大半はこの起動待ちの握り損ね。

## Testcontainers：テストコードから直接コンテナを操る

compose を外に持つ代わりに、テストコード自身がコンテナを起動・破棄するライブラリもある：

```python
from testcontainers.postgres import PostgresContainer

def test_repository():
    with PostgresContainer("postgres:16") as pg:
        repo = UserRepository(pg.get_connection_url())
        ...
```

テストごとにまっさらな DB が立ち、終われば消える。ユニットテストの書き味のまま「本物の依存」でテストできるので、統合テストのハードルが大きく下がる。Java/Go/Python/Node など主要言語に移植されている。

## 「イメージそのもの」もテスト対象

アプリのテストとは別に、成果物であるイメージの検査も忘れずに：

- **脆弱性・秘密のスキャン**（trivy。[10-02](../10_コンテナセキュリティ/10-02_イメージセキュリティ.md)）
- **構造テスト**：期待したファイルがあるか、ユーザーが非 root か等を検査する container-structure-test というツールもある
- **スモークテスト**：ビルドしたイメージを実際に起動して /health を叩くだけでも、「イメージは作れたが起動しない」系（entrypoint のtypo、依存漏れ）を CI で捕まえられる

これらを CI にどう並べるかは [12-04_継続的インテグレーション](12-04_継続的インテグレーション.md) へ。
