# 継続的インテグレーション

コンテナ時代の CI の成果物は「テストが通ったコード」ではなく「**テストが通った、デプロイ可能なイメージ**」。CI パイプラインの設計は、このイメージをどう速く・安全に作るかの設計になる。

## 標準的なパイプライン構成

```
lint/test → build image → scan → push (SHAタグ) → deploy
```

GitHub Actions での骨子：

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      id-token: write     # OIDC でクラウド認証（後述）
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ env.REGISTRY }}/myapp:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

## CI を速くする急所：レイヤーキャッシュ

CI ランナーは毎回まっさらなので、何もしないと**毎回フルビルド**になる。ビルドが遅い CI の9割はキャッシュ未設定。

- `cache-from/cache-to: type=gha`（GitHub Actions のキャッシュにレイヤーを保存）や、レジストリをキャッシュ置き場にする `type=registry` を設定する
- キャッシュが効く Dockerfile の書き方（依存インストールとコードコピーの分離。[07-02](../07_コンテナイメージのビルド/07-02_効率的なレイヤーキャッシング/)）が前提。ここが悪いとキャッシュ設定しても無意味

## セキュリティ設計：CI はサプライチェーンの要衝

CI はコードと本番の間に立つ特権的な場所で、狙われどころ。押さえる点：

- **レジストリ認証は OIDC で**：長期キー（AWS のアクセスキー等）を GitHub Secrets に置かず、ジョブごとに短命トークンを発行する（AWS なら IAM ロール + OIDC 連携）。漏れて困る恒久クレデンシャルを CI から消せる
- **スキャンをゲートにする**：trivy 等を push 前に実行し、Critical で fail させる（[10-02](../10_コンテナセキュリティ/10-02_イメージセキュリティ.md)）
- **タグは SHA で**：デプロイまで含めて「どのコミットのイメージか」を追跡可能に（[08-01](../08_コンテナレジストリ/08-01_イメージタグ付けのベストプラクティス.md)）
- **docker.sock マウント型の CI ランナー構成は要注意**：ジョブがホストの Docker を触れる＝ジョブ間の分離が崩れる。マネージドランナーか、rootless ビルド（kaniko、BuildKit rootless）を検討

## テストとの組み合わせ

CI 内で compose や Testcontainers を使った統合テスト（[12-03_テスト](12-03_テスト.md)）を回す場合、GitHub Actions の ubuntu ランナーは Docker が最初から使えるのでそのまま動く。「ローカルで `docker compose run test` が通る＝CI でも同じコマンドで通る」という対称性を保っておくと、CI 設定のデバッグで消耗しない。
