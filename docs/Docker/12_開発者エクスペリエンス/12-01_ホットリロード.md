# ホットリロード

「コードを1行直すたびにイメージを再ビルドして再起動」——これをやっていると開発の待ち時間が地獄になる。コンテナで開発するなら、**コード変更が即座にコンテナ内へ反映されて、アプリが自動で再読み込みされる**環境（ホットリロード）を最初に作るのが投資対効果最大のセットアップ。

## 仕組み：バインドマウント＋ウォッチャー

2つの部品の組み合わせでできている：

1. **バインドマウント**でソースコードをコンテナに見せる（ビルドし直さなくても変更が即反映される）
2. **ファイル変更を検知して再起動/再読み込みするツール**をコンテナ内で動かす（Python なら uvicorn --reload、Node なら nodemon や vite、Go なら air など）

compose での典型形：

```yaml
services:
  api:
    build: .
    command: uvicorn main:app --host 0.0.0.0 --reload   # 開発時だけ reload 付き
    volumes:
      - ./src:/app/src        # ソースだけマウント
    ports:
      - "8000:8000"
```

ポイントは**ソースだけをマウントする**こと。プロジェクト全体（`.:/app`）をマウントすると、ホストの `node_modules` や venv がコンテナ内の依存を上書きして「ホストと環境が混ざる」事故が起きる。依存ディレクトリはイメージ内のものを使うよう、マウント対象を絞る（または volume で依存ディレクトリを覆う）。

## compose watch という新しめの選択肢

バインドマウントの性能問題（特に Mac。[03-01](../03_インストールとセットアップ/03-01_Docker_Desktop（Win・Mac・Linux）.md)）への対処も兼ねて、Compose には `develop.watch` が入った：

```yaml
services:
  api:
    build: .
    develop:
      watch:
        - action: sync        # ファイル変更を同期
          path: ./src
          target: /app/src
        - action: rebuild     # 依存定義が変わったら再ビルド
          path: requirements.txt
```

`docker compose watch` で起動すると、「コードは同期、依存変更は自動リビルド」を Docker 側が面倒見てくれる。マウントではなく同期なので Mac でも速い。

## 本番イメージと開発設定を混ぜない

reload ツールやマウント設定は開発専用。Dockerfile に焼き込まず、`compose.yml`（開発用オーバーライド）側に寄せる。「本番コンテナに --reload が残っていた」は性能とセキュリティ両方の観点で避けたい。
