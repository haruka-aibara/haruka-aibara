# RDS パラメータの監視は再起動待ちまでは追えない

RDS のパラメータを Config ルール（`modules/aws-config-custodian`、c7n の `db-parameter` フィルタ）で監視するとき、見えるのはパラメータグループの値まで。実際に DB で効いている値ではない。

- dynamic なパラメータ（`require_secure_transport` など）は変更がすぐ効くので、グループの値＝効いている値として扱ってよい
- static なパラメータは再起動するまで効かない。グループの値を直しても、再起動するまでは「COMPLIANT だが実際は古い値」になる
- 再起動されたかを追うのは現実的に厳しい。`ParameterApplyStatus: pending-reboot` はパラメータグループ単位の状態で、どのパラメータが再起動待ちかは分からない。全ルールの条件に入れると、関係ない static パラメータを変えただけで全部 NON_COMPLIANT になる。効いている値は DB に接続して `SHOW VARIABLES` しないと取れない

## 再起動待ちは追わないほうがよさそう

パラメータのルールはグループの値だけで判定するのがよさそう。値が正しくなければ、再起動待ちかどうかに関係なく NON_COMPLIANT にする（再起動すれば間違った値になるので）。

| | やり方 | わかること | 困ること |
|---|---|---|---|
| 理想 | パラメータのルールに加えて、再起動待ちも見るルールを置く | 両方 COMPLIANT なら、正しい値が確実に効いている | 再起動待ちはグループ単位でしか分からないので、関係ない static パラメータを変えるたびに NON_COMPLIANT になり、そのたびに確認することになる |
| 現実的 | パラメータのルールだけ（グループの値で判定） | 値が正しく設定されているか | static なパラメータを直してから再起動するまでの間は、実際にはまだ効いていなくても COMPLIANT になる |

関係ないアラートのたびに確認する運用は続かないので、現実的なほうが落としどころだろう。

static なパラメータを直したあとの再起動は、変更した人がやる前提にしておけば足りそう。

## 値が返らないパラメータにも注意

`DescribeDBParameters` は、RDS が値を決めていないパラメータについて `ParameterValue` を返さない。そのときは MySQL 本体の既定値で動いているが、c7n からは「値なし」に見える。本体の既定値が問題ない値のパラメータなら、YAML で「値なしも OK」（`value: absent`）を明示する。RDS がデフォルトパラメータグループで値を入れているものは値が返るので、そのまま判定される。
