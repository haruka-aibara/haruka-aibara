HTTP/3 と QUIC を図で理解する

TCP を捨てて UDP の上に載せ替えたプロトコル。HTTP/2 に残った「1パケット落ちると全部止まる」を消しにいった。

何が問題だったのか

HTTP/3 を検討し始めるきっかけは、たいてい性能改善の理想論ではなく苦情だ——「電車の中だとページが固まる」「モバイルだけ異様に遅い」。サーバのレイテンシもオリジンの応答も正常なのに、特定のネットワークからだけ体感が崩れる。

原因は HTTP/2 が全リクエストを1本の TCP コネクションに集約したことにある。TCP はバイト列の順序を保証するので、パケットが1つ落ちると、その後ろに届いたデータは無関係なストリームのものでも受信バッファに積まれたままアプリに渡らない。多重化したぶん、1つの損失が巻き込む範囲が広がった。

QUIC は何をまとめたのか

QUIC は TCP と TLS を1つのプロトコルに統合し、UDP の上に載せたもの。TCP がやっていた順序保証・再送・輻輳制御を、ストリーム単位で作り直して内側に持っている。HTTP/3 は「QUIC の上で HTTP を話すための仕様」でしかなく、実質の中身は QUIC 側にある。

なぜ UDP なのか。TCP を直せばいい話に見えるが、TCP は OS カーネルと世界中の中間装置（NAT・FW・ロードバランサ）に焼き付いていて、新しい挙動を足しても途中で落とされる。UDP は素通しされる単なる入れ物なので、その中身をユーザ空間で自由に定義できる。

IP が変わっても接続が切れない

もう一つ、モバイルで効く違いがある。Wi-Fi から回線に切り替わった瞬間にダウンロードがやり直しになる、動画が数秒固まる——あれは TCP が接続を「送信元 IP・ポート・宛先 IP・ポート」の4つ組で識別しているから起きる。IP が変われば、TCP にとっては別の接続でしかない。

ヘッダ圧縮は HPACK から QPACK へ

HTTP/2 の HPACK は「1回目に送ったヘッダを動的テーブルに登録し、2回目以降はその番号だけ送る」という仕組みだった。これは到着順が保証されていることを暗黙の前提にしている。QUIC ではストリームが順不同で届くので、そのままでは成立しない。

実際に HTTP/3 で通信が始まるまで

ここが運用で一番誤解されるところ。「HTTP/3 を有効にした」＝「全アクセスが HTTP/3 になる」ではない。 ブラウザは最初から UDP で話しかけたりしない。まず従来どおり TCP で繋ぎ、サーバから「うちは HTTP/3 も話せる」と教えられて初めて次回から試す。

運用で押さえること

  • 効くネットワークとそうでないネットワークがある：損失やネットワーク切替が起きる環境（モバイル・遠距離・混雑した Wi-Fi）が本命。低損失の回線やデータセンタ内では、ほとんど差が出ない。「HTTP/3 にしたのに速くならない」の答えはたいていここ。
  • 評価は平均値ではなく裾で見る：改善が出るのは条件の悪い一部のユーザなので、p50 を眺めていても動かない。p95 / p99 と、モバイル回線に絞ったセグメントで比較する。
  • UDP 443 の許可が要る：セキュリティグループ、NACL、オンプレのファイアウォール。TCP しか開けていない構成では、有効化しても静かに HTTP/2 のままになる。
  • 有効化は端点だけでよい：CDN やリバースプロキシで受ければ、オリジンとの間は HTTP/1.1 のままでかまわない。AWS なら CloudFront が HTTP/3 に対応している一方、ALB は対応していない（この種の対応状況は変わるので、導入前に最新のドキュメントで確認する）。
  • CPU コストは TCP より高い傾向：QUIC は暗号化とパケット処理をユーザ空間で行うため、カーネルの TCP スタックほど安くない。高トラフィックのオリジンで自前運用するなら、計測してから決める。

セキュリティ視点

HTTP/3 の導入判断が技術部門で止まらずセキュリティ側に回ってくる理由は、速度ではなく可視性にある。

中間装置から中身が見えなくなる

TLS over TCP なら、暗号化されていてもシーケンス番号やフラグ、ハンドシェイクの一部は経路上から観測できた。QUIC はトランスポートのヘッダまで暗号化するので、外から分かるのはごく一部のビットだけになる。既存の IDS・プロキシ・DLP が前提にしていた検査ポイントが消える。
「監視できないから UDP 443 を塞ぐ」という判断は現実によく採られる。塞いでもユーザからは何も壊れて見えない（HTTP/2 に落ちるだけ）ので、決めるなら意図的に決めて記録しておく。可視性を残したいなら、TLS の終端点を自分の管理下（CDN・リバースプロキシ）に置き、そこでログを取る設計にする。

0-RTT のリプレイ

0-RTT で送られるデータは、経路上で記録した攻撃者がそのまま再送できる。サーバ側から見ると正規のリクエストと区別がつかない。決済や更新系がこれに乗ると二重実行になりうるので、0-RTT を受け付けるのは冪等な操作に限る。プロトコルの欠陥ではなく「往復を1つ削る代わりに再送検知を諦めた」という交換条件なので、有効化するかは用途で判断する。

増幅反射 DDoS の踏み台

UDP なので送信元 IP を詐称できる。QUIC はこれを見越して、アドレス検証が済むまでは受信バイト数の3倍を超えて送り返してはならないという制限と、Retry パケットによる検証手段を持っている。逆に言えば、この制限を正しく実装していないサーバやライブラリは増幅の踏み台になる。自前で QUIC サーバを運用するならパッチ適用の対象として追う。

提案するときの言い方

技術的な言い方ビジネス側に伝わる言い方
HTTP/3 を有効化する電波の悪い場所やモバイル回線からのアクセスで、ページが固まる・読み込みが途中で止まる体験を減らせる
UDP 443 を許可しない通信内容を検査できない経路を作らない判断。ユーザ体験は現状維持で、劣化はしない
0-RTT を無効にする接続を数十ミリ秒速くする代わりに同じ注文が二重に通るリスクを取る、という取引を断る
