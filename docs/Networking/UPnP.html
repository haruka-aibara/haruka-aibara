UPnP — 誰でもルータに穴を開けられる仕組み

NAT の内側は外から繋がらない。その不便さを解消するために「LAN 内のアプリがルータに自分でポートを開けさせる」仕組みが作られた。 それが UPnP IGD で、設計上そこには認証がない。NAT が偶然もたらしていた防御を、LAN 内の任意のプロセスが人間の承認なしに剥がせる、というのがこのプロトコルの本質。

どんな場面で必要になるか

家庭やオフィスのルータは NAT（IP マスカレード）を挟んでいる。内側から外への通信は問題ないが、外から内への着信は受けられない。 ルータのグローバル IP 宛に届いたパケットを、どの内部ホストへ渡せばいいか分からないからだ。

ところが「外からの着信」を必要とするアプリは昔からある。

  • オンラインゲームで自分がホストになる、対戦相手から直接繋いでもらう
  • P2P ファイル共有、ビデオ会議や VoIP の直接接続（リレーサーバを経由したくない）
  • 宅内の NAS・IP カメラ・録画機を外出先から見る

解決策は本来「ルータの管理画面に入ってポートフォワーディングを手で設定する」。 だが一般利用者にこれを求めるのは現実的ではないし、アプリごとにポート番号も変わる。 そこで アプリが自分でルータに「このポートを開けてくれ」と頼む 仕組みが用意された。それが UPnP の IGD（Internet Gateway Device）機能だ。

UPnP は何のプロトコルか

UPnP（Universal Plug and Play）は、もともと LAN 内の機器を設定なしで発見・制御する ための仕様群だ。 ルータだけの話ではなく、プリンタ、NAS、メディアサーバ（DLNA）、テレビなども対象になる。 1999 年に UPnP Forum が策定し、同フォーラムは 2016 年に解散、仕様は現在 OCF（Open Connectivity Foundation）が引き継いでいる。

UPnP は次の 6 段階で構成される。この順序自体が機器とやり取りする手順になっている。

  1. アドレッシングDHCP でアドレスを取る。DHCP がなければ Auto-IP（169.254.0.0/16）で自分に割り当てる
  2. ディスカバリSSDP（UDP 1900、マルチキャスト 239.255.255.250）で「そこに誰かいるか」を探す
  3. ディスクリプション見つけた機器から HTTP でデバイス記述 XML を取得し、使えるサービスと制御 URL を知る
  4. コントロールSOAP（HTTP POST）でアクションを呼ぶ。AddPortMapping はここ
  5. イベンティングGENA の SUBSCRIBE で状態変化の通知を購読する
  6. プレゼンテーション機器がブラウザ向けの管理画面を提供する

① ディスカバリ：M-SEARCH を投げる

SSDP は HTTP に似た文法を UDP に載せたもの（HTTPU）。ルータを探すときはこう投げる。

M-SEARCH * HTTP/1.1
HOST: 239.255.255.250:1900
MAN: "ssdp:discover"
MX: 2
ST: urn:schemas-upnp-org:device:InternetGatewayDevice:1

応答はユニキャストで返り、LOCATION にデバイス記述 XML の URL が入っている。

HTTP/1.1 200 OK
CACHE-CONTROL: max-age=1800
LOCATION: http://192.168.1.1:5000/rootDesc.xml
ST: urn:schemas-upnp-org:device:InternetGatewayDevice:1
USN: uuid:2f402f80-da50-11e1-9b23-001788102201::urn:schemas-upnp-org:device:InternetGatewayDevice:1

機器側から NOTIFY を定期的にマルチキャストして自分の存在を広告する方向もある（ssdp:alive / ssdp:byebye）。

④ コントロール：ポートを開けさせる

デバイス記述 XML から WANIPConnection サービスの制御 URL を取り出し、SOAP で AddPortMapping を呼ぶ。これだけで穴が開く。 

POST /ctl/IPConn HTTP/1.1
HOST: 192.168.1.1:5000
CONTENT-TYPE: text/xml; charset="utf-8"
SOAPACTION: "urn:schemas-upnp-org:service:WANIPConnection:1#AddPortMapping"

<s:Envelope xmlns:s="http://schemas.xmlsoap.org/soap/envelope/">
  <s:Body>
    <u:AddPortMapping xmlns:u="urn:schemas-upnp-org:service:WANIPConnection:1">
      <NewRemoteHost></NewRemoteHost>
      <NewExternalPort>51413</NewExternalPort>
      <NewProtocol>TCP</NewProtocol>
      <NewInternalPort>51413</NewInternalPort>
      <NewInternalClient>192.168.1.42</NewInternalClient>
      <NewEnabled>1</NewEnabled>
      <NewPortMappingDescription>my app</NewPortMappingDescription>
      <NewLeaseDuration>0</NewLeaseDuration>
    </u:AddPortMapping>
  </s:Body>
</s:Envelope>

NewLeaseDuration が 0 は「無期限」。多くの実装がこれを受け入れるため、一度開いた穴はルータを再起動するまで残る。 GetExternalIPAddress でグローバル IP も聞ける。

問題は「認証がない」こと

UPnP には認証も承認もない。LAN 内から届いた SOAP 要求は、誰が出したものでも受け入れる という前提で設計されている。 「LAN の内側は信頼できる」という 1999 年当時の割り切りだ。

つまり、利用者が意図してインストールしたゲームと、メール添付から入り込んだマルウェアは、ルータから見て完全に同じ要求を出す。 ルータには両者を区別する材料がなく、記録も残さず、利用者に確認もしない。

ここから派生する被害は、大きく 3 方向ある。

1. LAN 内のマルウェアが自分で入口を作る

感染ホストが自分の RDP や SMB、あるいは仕込んだバックドアを外部公開できる。 利用者は「ルータで何も設定していないから外からは繋がらないはず」と思っているので、この状態に気づく機会がない。 C2 サーバへのアウトバウンド通信を監視していても、開いた入口そのものは検知に引っかからない。

2. WAN 側に UPnP が露出したルータが大量にある

SSDP や UPnP の HTTP は本来 LAN 側インターフェースだけで待ち受けるべきものだ。ところが実装バグや初期設定の誤りで WAN 側にも応答する製品が大量に出回った。 2013 年の Rapid7 の調査では、インターネットから UPnP のディスカバリに応答する機器が約 8,100 万台、 そのうち約 1,700 万台は UPnP のサービス制御まで外部から可能だった。 加えて UPnP SDK の libupnp にはバッファオーバーフローによるリモートコード実行の脆弱性があり（VU#922681）、多数の製品が影響を受けた。

2018 年に Akamai が報告した UPnProxy は、この露出を突いて外部からポートマッピングを注入し、 感染ルータを匿名プロキシとして中継に使うものだった。約 480 万台が SSDP に応答し、うち約 6.5 万台に実際に不正なマッピングが注入されていた。

3. SSDP リフレクション（増幅 DDoS）の踏み台になる

UDP は送信元 IP を詐称できる。攻撃者が被害者の IP を送信元に偽装した小さな M-SEARCH を、露出した UPnP 機器へばらまくと、 機器はサービス一覧を含む大きな応答を被害者に返す。増幅率は最大で約 30 倍とされる。

CVE-2020-12695（CallStranger）

2020 年に見つかった UPnP 仕様そのものの欠陥。イベンティングの SUBSCRIBE にある Callback ヘッダに任意の URL を指定でき、 機器がそこへ通知を送ってしまう。結果として、外部から機器を踏み台にした 内部ネットワークのポートスキャン、 データの持ち出し（DLP 回避）、増幅 DDoS が成立する。仕様レベルの問題のため、対策はベンダーのファームウェア更新待ちになった。

では、どうするか

対策の第一手は単純で、ルータの UPnP を無効にする。必要なポート開放は手動で設定する。 これで「アプリが勝手に開ける」経路は消える。ゲーム機など UPnP 前提の機器がある場合だけ、対象を絞って有効化する。

対象やること効くのは
ルータ（家庭・小規模拠点） UPnP / IGD を無効化。必要なものだけ手動ポートフォワード LAN 内マルウェアによる無断ポート開放
WAN 側インターフェース UDP 1900（SSDP）と UPnP の HTTP ポートを遮断。外部から届いていないかを確認する UPnProxy、外部からのマッピング注入、リフレクション踏み台化
企業ネットワーク UPnP は使わない前提にする。239.255.255.250 のマルチキャストをセグメント間で通さない 機器の意図しない相互発見、内部からの探索
機器のファームウェア libupnp / MiniUPnPd 由来の脆弱性を含むため更新を追う リモートコード実行、CallStranger
アプリ側の設計 着信を必要としない構成にする（アウトバウンド接続 + リレー、WebRTC の ICE/TURN 等） そもそもポート開放を不要にする

なお UPnP IGD:2 では、コントロールポイントが 自分以外の内部ホスト宛のマッピングを作れない よう制限が入った。 同種の目的には NAT-PMP（RFC 6886）や PCP（RFC 6887）という後発のプロトコルもあるが、 いずれも「LAN 内は信頼できる」という前提は大きくは変わっていない。根本的には IPv6 + 明示的なファイアウォールポリシーに寄せるほうが筋が良い。

ビジネス側にどう伝えるか

「UPnP を無効化しましょう」だけでは、なぜ今それをやるのかが伝わらない。何が起きるかを言い換える。

技術的な言い方意思決定者に伝わる言い方
ルータの UPnP を無効化する 今の設定だと、社内 PC がマルウェアに感染したとき、そのマルウェア自身が社外からの入口を作れてしまう。ルータの設定変更を人が承認する手順を回避されている状態です
WAN 側で SSDP を遮断する 自社の回線が、他社を狙った DDoS 攻撃の踏み台として使われる可能性があります。加害者側として名前が出ます
ポート開放は手動運用にする 外部に公開している入口の一覧を、人が把握できる状態に戻すということです

まとめ

項目内容
目的LAN 内の機器を設定なしで発見・制御する。ルータ向けの IGD では動的なポート開放
ディスカバリSSDP：UDP 1900、マルチキャスト 239.255.255.250、M-SEARCH / NOTIFY
制御SOAP over HTTP。AddPortMapping / DeletePortMapping / GetExternalIPAddress
設計上の弱点認証がない。LAN 内からの要求はすべて信頼する
代表的な悪用マルウェアによる無断ポート開放、UPnProxy、SSDP リフレクション DDoS、CallStranger
基本の対策UPnP の無効化、WAN 側での UDP 1900 遮断、ファームウェア更新

UPnP は「使いやすさのために認証を省いた」プロトコルの典型例だ。 NAT はセキュリティ機能として設計されたものではないが、事実上の防御として機能してきた。UPnP はその防御を、内側からなら誰でも外せるようにする。 そう捉えると、無効化がなぜ定番の推奨なのかが腑に落ちる。
