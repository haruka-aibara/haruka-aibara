UDP

TCP から確認応答も再送も順序制御も取り去った、8 バイトだけのプロトコル。それでも使われる理由。

TCP の親切がコストになる場面

TCP は接続を確立し、届いたか確認し、順番を直し、混雑すれば速度を落とす。ありがたい機能だが、その全部に時間とメモリのコストがかかる。

DNS の問い合わせを考えてみる。送る内容はドメイン名 1 つ、返ってくるのは IP アドレス 1 つ。本題は 1 往復で終わるのに、その前に 3 パケットの接続確立をするのは明らかに割に合わない。失敗したら問い合わせ直せばいい。

そういう場面のために、UDP は「宛先アプリを識別する」以外の機能をほぼ持たない。ヘッダはわずか 8 バイト。

使い分けの基準

TCPUDP
接続確立3 ウェイハンドシェイクなし（いきなり送る）
到達保証確認応答と再送で保証なし
順序保証並べ直すなし
ヘッダ20 バイト8 バイト
1 対多できないブロードキャスト・マルチキャストが使える
主な用途Web・メール・ファイル転送・SSHDNS・DHCP・音声/映像・SNMP・syslog・QUIC

選ぶ基準は「欠けたら困るか」ではなく、「欠けたときに再送が間に合うか」。ライブ映像は欠けても困るが、再送が届くころには再生時刻を過ぎているので意味がない。だから UDP を選ぶ。

セキュリティ上の注意：UDP は接続確立がないため送信元 IP を詐称しやすい。これを悪用したのが反射増幅型 DDoS で、送信元を被害者の IP に偽って DNS や NTP に問い合わせを投げ、増幅された応答を被害者に集中させる。
自組織のサーバが踏み台にならないよう、DNS はオープンリゾルバにしない、NTP の monlist を無効にする、といった設定が必要になる。詳しくは DDoS 枯渇型と反射増幅型。
