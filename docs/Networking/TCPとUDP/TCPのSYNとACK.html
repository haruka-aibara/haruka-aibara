TCP の SYN と ACK

「つながらない」の切り分けは、この 3 往復のどこで止まったかを見るところから始まる。

いきなりデータを送らない理由

相手が起動しているか、そのポートで待ち受けているか、通信可能な状態かは、送ってみるまで分からない。相手が落ちているのに大量のデータを送り続けても無駄になる。

そこで TCP は、データを送る前に「送るよ」「いいよ」「じゃあ送る」の 3 つのやりとりで互いの準備を確認する。これが 3 ウェイハンドシェイク。ここで使われる目印が SYN（接続したい）と ACK（受け取った）というフラグ。

止まった場所で原因が絞れる

パケットキャプチャを見れば、どこで止まったかがそのまま原因の切り分けになる。

観測される状態考えられる原因
SYN を送っても何も返らない（再送が並ぶ）経路上のファイアウォールやセキュリティグループが黙って破棄している。宛先が存在しない
SYN に対して RST が返るホストには届いているが、そのポートで何も待ち受けていない
SYN + ACK は返るが ③ の後で止まる接続はできている。アプリ側の処理が遅い、または戻りの経路に問題

「タイムアウト」と「接続拒否（Connection refused）」でエラーメッセージが違うのは、上の 1 行目と 2 行目の違いがそのまま出ているため。

切断は 4 回のやりとり

接続を閉じるときは FIN フラグを使う。ただし TCP は双方向なので、それぞれの向きを別々に閉じる。「こちらはもう送りません」を互いに言い合うので、FIN → ACK → FIN → ACK の 4 パケットになる。

セキュリティとの接点：SYN を送るだけで ③ の ACK を返さない通信を大量に投げると、サーバは「接続待ち」の状態を大量に抱えたままメモリを消費する。これが SYN フラッド攻撃。
また、開いているポートを調べるポートスキャンも、この応答の違い（SYN+ACK が返るか RST か）を利用している。詳しくは ポートスキャンの 4 種 を参照。
