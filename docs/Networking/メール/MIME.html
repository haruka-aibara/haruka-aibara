MIME — 英数字しか運べないメールで、日本語と添付を送る

中身が何で、どう変換してあるかをヘッダで宣言する。いまは HTTP でも同じ仕組みが使われている。

何が問題なのか

SMTP は 1982 年の規格で、運べるのは7ビットの英数字テキストだけという前提で作られている。日本語も、画像も、実行ファイルも、そのままでは通らない。

プロトコルを作り直すのは現実的ではない。そこでメールの本文の中に「これは何のデータで、どう変換してあるか」を書いておき、受け取った側が元に戻すという約束を追加した。これが MIME（Multipurpose Internet Mail Extensions）。

2つのヘッダを覚えれば足りる

ヘッダ何を言っているか値の例
Content-Typeこれは何のデータか（種類／サブ種類）text/plain、image/png、application/pdf
Content-Transfer-Encoding7ビットに収めるためにどう変換したかbase64、quoted-printable、7bit

変換の方式は主に2つ。バイナリには Base64、大部分が英数字で一部だけ非 ASCII が混じるテキストには quoted-printable（該当文字だけを =E3 のような形に置き換える）が使われる。

メールの外へ広がった

「データの種類を文字列で表す」という部分だけが独立して、いまや至るところで使われている。HTTP の Content-Type ヘッダがまさにそれで、ブラウザが受け取ったものを画像として描くのか、HTML として実行するのかは、この値で決まる。MIME タイプ、メディアタイプという呼び方はここから来ている。

「宣言」でしかない、という点が攻撃に使われる

Content-Type は送る側が自己申告しているだけで、中身と一致している保証はない。ここを突く攻撃が2種類ある。
1つは拡張子との不一致。image/jpeg と宣言された添付の実体が実行ファイル、という手口はマルウェア配布の定番。
もう1つがMIME スニッフィング。古いブラウザは「宣言が間違っていても中身から判断してあげる」という親切な挙動を持っていたため、画像としてアップロードされたファイルが HTML として解釈され、スクリプトが動いた。これを止めるのが X-Content-Type-Options: nosniff ヘッダで、ファイルをアップロードさせるサイトでは付けておく。
