Base64 — バイナリを「文字しか通らない場所」に載せる

3バイトを4文字に置き換えるだけの変換。暗号ではないので、見つけたら中身は読めると考える。

何が問題なのか

メール本文、JSON の値、HTTP ヘッダ、設定ファイル。これらはテキストしか置けない場所で、画像や証明書のようなバイナリをそのまま入れると壊れる。制御文字が混じって処理系が誤動作したり、改行コードが勝手に変換されたりするからだ。

そこで、安全に通ることが分かっている64種類の文字だけを使って、どんなバイト列でも表せるようにする。それが Base64。

どこで出会うか

  • メールの添付：MIME の Content-Transfer-Encoding: base64（MIME）
  • 証明書の PEM 形式：-----BEGIN CERTIFICATE----- に挟まれた部分は、バイナリの証明書を Base64 にしたもの
  • HTTP の Basic 認証：Authorization: Basic dXNlcjpwYXNz
  • JWT：ドットで区切られた3つの部分が、それぞれ Base64URL で符号化されている
  • データ URL：HTML や CSS に画像を直接埋め込む形

URL やファイル名に使うときは + と / が問題になるため、それぞれ - と _ に置き換えた Base64URL という変種が使われる。JWT で見かけるのはこちら。

Base64 は暗号化ではない

いちばん多い誤解がこれ。Base64 に鍵は存在せず、誰でも一瞬で元に戻せる。設定ファイルのパスワードが Base64 になっているのを見て「暗号化されている」と判断してはいけないし、自分でそう実装してもいけない。
Basic 認証がまさにその例で、利用者名とパスワードを : で繋いで Base64 にしただけ。HTTPS でなければ、そのまま読める形でパスワードが流れているのと変わらない。
逆に調査側から見れば、これは道具になる。マルウェアの通信やフィッシングのメールで長い英数字の羅列＋末尾の = を見つけたら、デコードすれば中身が読める。
