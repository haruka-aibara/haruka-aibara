SOAP — 組織をまたいで手続きを呼び出すための、厳密な封筒

中身も、宛先も、エラーの返し方も XML で決めきる。REST に置き換わった後も、決済や行政の連携では現役。

何が問題なのか

自社のシステムから取引先のシステムの処理を呼びたい。言語もプラットフォームも違い、担当者も別の会社にいる。この状況で「どういう形式で送れば、どういう形式で返ってくるのか」を口頭やメールで合わせていくと、必ず食い違いが出る。

SOAP の発想はすべてを機械可読な形式で決めきってしまうこと。メッセージの構造は XML で規定し、そのサービスがどんな操作を持ち、どんな型の値をやり取りするかは WSDL という定義ファイルで公開する。定義ファイルを読み込めばクライアントのコードが自動生成される——これが 2000 年代の企業間連携で求められたもの。

メッセージ自体に署名・暗号化できる（WS-Security）

HTTPS は1区間の通信を守る。だが企業間連携では、メッセージが中継サーバやメッセージキューをいくつも経由することがあり、途中で平文に戻る。

SOAP では Header に XML デジタル署名や暗号化を入れられるため、メッセージそのものが端から端まで守られる。経由地が信用できなくても成立する、という点が金融や行政の要件に合った。この仕組みを WS-Security と呼ぶ。

なぜ REST に置き換わったのか

SOAPREST（JSON）
メッセージXML。冗長で人手では読みにくいJSON。軽く、そのまま読める
定義WSDL で厳密に決めるOpenAPI などで記述するが、必須ではない
実装の手軽さ専用のライブラリと生成ツールが要るcurl1行で試せる
向く場面組織をまたぐ厳密な契約、多段経由、トランザクションWeb・モバイル向けの一般的な API

Web とモバイルの世界では「軽くてすぐ試せる」ことの価値が圧倒的に大きく、REST が主流になった。一方で相手が数年変わらず、仕様の食い違いが金銭事故に直結する領域——決済ネットワーク、保険、行政システム、EDI——では、いまも SOAP が動いている。レガシー統合の案件でこれに出会うことは今後もある。

XML を受け取る側の定番の脆弱性

SOAP に限らず XML を解析するエンドポイントには、XXE（XML 外部実体参照）という古典的な穴がある。XML の仕様には外部ファイルを読み込む機能があり、これを有効にしたまま解析すると、送りつけられた XML に /etc/passwd を読ませたり、内部ネットワークへ通信させたりできる。
対策は明快で、パーサの設定で外部実体の解決を無効にする。ライブラリによっては既定で有効なままなので、明示的に切る。
