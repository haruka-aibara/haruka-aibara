ファイアウォールと DMZ 構成をゼロから理解する

構成図の上で、その通信はどこまで進んで、どこで止まるのか。

何が問題なのか

午後試験ではまずネットワーク構成図が渡される。ファイアウォール、DMZ、WAF、プロキシ——機器の名前はどれも知っている。それでも「この通信は遮断されるか」という設問に手が止まる。機器名を覚えても、通る／止まるの判断はできないからだ。

判断に要るのは1つだけ。その機器はパケットのどこまで見ているか。見えていないものは止められない。逆に見えている範囲なら、あとはルール次第で止まる。この一点で構成図を読み直す。

ペリメータセキュリティモデルと、崩れた前提

境界（ペリメータ）に関門を置き、その内側は信頼する——これがペリメータセキュリティモデル。長らく前提だったが、いまは成立しない場面が多い。

  • 守る資産が内側にない：業務データが SaaS やクラウドに出た
  • 利用者が内側にいない：リモートワーク、社外持ち出しの端末
  • 境界は内側から開けられる：メール添付や改ざんサイト経由でマルウェアが端末に入れば、通信は内側から外へ出ていく。外側ファイアウォールは「内→外」を広く許可しているので、そのまま通る

だから境界防御をやめるのではなく、境界で止まらないものを内側でも見る構成にする。多層防御であり、ゼロトラストもこの延長にある。

DMZ を置く理由

公開サーバは不特定多数からの接続を受ける以上、いつか侵害されうる。問題はその後だ。公開 Web サーバが内部 LAN と同じセグメントにいれば、そこを踏み台に内部のファイルサーバへ横移動できてしまう。

そこで公開サーバだけを別セグメントに隔離し、DMZ→内部は原則遮断、業務上必要な最小限だけ許可する。DMZ は「陥落しないための区画」ではなく、陥落する前提で被害を閉じ込める区画。この読み方ができると、設問の「DMZ に置くべきサーバはどれか」がほぼ機械的に解ける——外部から接続を受けるものは DMZ、受けないものは内部。

パケットフィルタリング：静的と動的

ファイアウォールの土台はパケットフィルタリング。送信元／宛先の IP アドレス、ポート番号、方向を見て通す・落とすを決める。問題になるのは戻りの通信だ。

内部端末（192.0.2.10:52341）から外部の Web サーバ（203.0.113.5:443）への通信を許可したとする。応答は「203.0.113.5:443 → 192.0.2.10:52341」で返ってくる。静的フィルタリングはルールが固定なので、この戻りを通すには外部→内部の高位ポート（1024〜65535）を開けっぱなしにするしかない。ここが穴になる。「ACK フラグが立っているものは戻りとみなして通す」という設定もあるが、ACK を立てただけの偽装パケットを通してしまう（ACK スキャンが成立する）。

動的フィルタリング、すなわちステートフルインスペクションは、行きの通信を見てコネクションテーブルに記録し、その記録に対応する戻りだけを一時的に通す。行きの記録がなければ戻りも通らない。TCP のフラグやシーケンス番号の整合性も見るので、いきなり届いた SYN/ACK や ACK は落ちる。現在のファイアウォールはこちらが標準。

ここが判断の分かれ目

ステートフルインスペクションが判断しているのは「対応する行きの通信があるか」であって、中身が正当かどうかではない。内部から出ていった通信の応答である限り、それが何であっても通る。

通信を3つ追う

アプリケーションゲートウェイ／プロキシ

プロキシは通信を一度終端し、自分が代理でつなぎ直す。パケットを素通しせず中身を組み立て直すので、GET /admin という URL、User-Agent、ダウンロードされたファイル種別まで見える。だから「業務に不要なカテゴリのサイトを落とす」「利用者 ID ごとにログを残す」ができる。このログが残ること自体が、侵害後の調査で決定的になる。

WAF：ポジティブモデルとネガティブモデル

SQL インジェクションを考える。宛先 IP は正しい、ポートは 443、TCP の状態も正常、HTTP としても文法的に正しい。異常なのはパラメータの中身だけだ。L3/L4 しか見ない機器では原理的に検知できない。HTTP のボディまで見る WAF が、唯一の検知点になる。

方式やり方性質
ネガティブモデル
（ブラックリスト）		攻撃パターンのシグネチャに一致したら遮断導入は楽。未知の攻撃や、エンコードを変えた回避には弱い
ポジティブモデル
（ホワイトリスト）		正常なリクエストの形（パラメータ名・型・長さ）を定義し、外れたら遮断未知の攻撃にも効く。アプリの仕様把握と、変更のたびの更新が要る。仕様が固い API 向き

WAF で防げないもの：他人の ID を指定すると他人のデータが見えるといった認可の欠陥や業務ロジックの穴は、リクエスト単体が完全に正常なので判定できない。TLS を復号していない経路の中身も見えない。そして WAF を迂回してオリジンサーバへ直接アクセスされれば、そもそも通らない。WAF は時間を稼ぐ手段であって、脆弱性の修正の代わりにはならない。

なお、検知に振り切った機器として IDS/IPS も同じ位置に入るが、検知方式（シグネチャ型・アノマリ型）は別トピック。

パーソナルファイアウォール

端末そのものに置くファイアウォール。境界に置いたものとの決定的な違いは、同一セグメント内の通信は境界の機器を通らないという点にある。1台が感染して隣の端末へ横移動するとき、その通信は外側 FW も内側 FW も経由しない。止められるのは端末側だけ。加えて、端末を社外に持ち出した時点で、境界の機器はもう経路上にいない。
