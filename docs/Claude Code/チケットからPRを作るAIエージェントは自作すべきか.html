チケットから PR を作る AI エージェントは自作すべきか

Jira のチケットを置くと AI が実装して draft PR を作り、Slack に知らせる。この流れを自前で組んで動かしてみたら、部品のほぼすべてに既製品があった。

自作したくなる場面

チケット管理は Jira、コードは GitHub、連絡は Slack。どれも使っているのにつながっていない。AI にコードを書かせられるようになった今、「チケットを置いたら PR まで勝手にできる流れ」を GitHub Actions と Claude Code で組みたくなる。

実際に組むと、Jira Automation から GitHub Actions を起動し、Claude が実装、別の Claude がレビュー、CI を待って Slack に知らせる、までは数日で動く。問題はその後で、「なぜこれを自作するのか」に答えられなくなる。

部品ごとに既製品と並べる

比べるのは「できるか」ではなく「保守する量」

自作すれば何でもできる。だから「既製品ではできない」は理由にならない。比べるべきは、同じことを自分で組んだときに何を持ち続けることになるかだ。

「Slack からマージできる」も理由にならない

既製品に無さそうな機能を足せば、自作する理由になるか。たとえば Slack のボタンでマージできるようにする。だが人が判断して押すなら、差分と CI が並んでいる GitHub で押すほうがいい。押す場所を変えても、判断する人の手間は減らない。

自作が意味を持つ条件

残る問いは 1 つだけ。

既製品が決めてくれない、自分の環境固有の判断を自動化しているか。

たとえば「ドキュメントだけの変更は、CI と AI のレビューが通れば人を通さずマージする」「Terraform の変更は plan に削除が含まれていたら止める」。これは、マージすると何が起きるかを知っている自分にしか決められない。こうした判断を持たないなら、既製品を使うほうが素直だ。

それでも作って残るもの

自作した経験は、既製品を選ぶときの見る目になる。

確かめることなぜ
AI が動く場所に、書き込めるトークンがあるかチケットは第三者が書ける。本文に紛れた指示に AI が乗せられても、書けなければ被害が出ない
CI やワークフローの設定を AI が変えられるか変えられると、検査そのものを外せてしまう
チケットの本文を指示として読むか、データとして読むか上と同じく、紛れ込んだ指示への耐性
いつ知らせるかPR ができた時点ではまだ完成していない。CI が終わってから知らせてほしい
