Jira のチケットから自動で PR を作る仕組み

この仕組みは撤去した。使わないこと。 実際に組んで動かしてみた結果、部品のほぼすべてに既製品（GitHub Copilot のクラウドエージェント、Atlassian Rovo Dev、GitHub for Jira など）があり、自作して保守し続ける理由が薄かった。同じことをしたいなら既製品を使うほうがよい。判断の経緯は チケットから PR を作る AI エージェントは自作すべきか。この記事は、仕組みの考え方（権限の分け方など）の記録として残している。以下のファイルへのリンクは撤去前のコミットを指す。

チケットをスプリントに入れるだけで、Claude Code が実装し、別の Claude がレビューし、CI が終わった draft PR が Slack に届く。

どんな場面で困るか

いまは Claude Code のアプリに頼めば PR は作れる。困るのはその手前と後ろだ。チケットを切っても実装は別の場所で始まり、チケットの状態は人が手で動かし、PR ができたかどうかは自分で見に行く。Jira・GitHub・Slack を個別には使っているのに、つながっていない。

欲しいのは「AI に頼む手間」を減らすことではなく、チケットを置いたら、あとは判断が要る場面だけ人に回ってくる流れ。自分から頼む作業を自動化しても価値は薄い。

全体の流れ

各サービスの役割と、Jira キーでつなぐ考え方

サービスごとに役割を 1 つずつだけ持たせる。

サービス役割
Jira状態の唯一の置き場所
GitHubコード・PR・CI と、エージェントの実行場所（GitHub Actions ＋ anthropics/claude-code-action）
Slack人への通知と、判断の入口

サービスをまたいで同じ作業を追えるように、Jira キーを相関 ID として図の下段のすべてに埋める。GitHub for Jira を入れていれば、ブランチ名と PR タイトルのキーを見て課題に PR が自動でぶら下がる。つなぎ用のデータベースは要らない。

エージェントに書き込み権限を渡さない

いちばん手軽なのは Claude に gh pr create までやらせることだが、それは書き込めるトークンをエージェントに渡すことになる。チケットは第三者が書けるので、本文に紛れた指示にエージェントが乗せられる前提で組む。そこでワークフローを 3 つのジョブに分け、ジョブの間で渡すのはパッチ 1 枚だけにする。

わざわざジョブを分けるのは、同じ作業ディレクトリで push すると、エージェントが仕込んだ .git/hooks や .git/config がトークンを持った状態で実行されうるから。パッチなら中身は差分だけで、まっさらなチェックアウトに当て直せる。

起動側も同じ考え方で、Jira Automation に置く PAT は Actions: write だけ。workflow_dispatch はこれで足りるので、漏れてもワークフローを起動できるだけでコードは書けない。PR は draft で作り、マージは人がする。

入口はステータスではなく未開始スプリント

「AI 実装」というステータスに移したら起動、が素直に見える。ただステータスの追加は Jira のワークフロー変更で、大きな組織では管理者への申請が要る。スプリントならプロジェクトの中で利用者の権限だけで作れる。

そのスプリントは開始しない。未開始ならバーンダウンやベロシティに混ざらない。Automation は「スプリント」欄の変更をトリガーにし、JQL でスプリント ID が一致するときだけ起動する（名前は変えられるうえ重複しうるので ID で見る）。

サブスクで動かすか、Bedrock で動かすか

Claude のサブスク（既定）Amazon Bedrock
課金定額の範囲に収まる従量課金
資格情報claude setup-token の OAuth トークン（約 1 年有効）を secret に置くOIDC で IAM ロールを引き受ける。長期のキーを置かない
注意利用上限を手元の Claude Code と共有する使うモデルだけを IAM で許可する

個人で回すならサブスクが安い。枠が足りないときや、長期のトークンを GitHub に置きたくないときに Bedrock へ切り替える。

チケットの質がそのまま PR の質になる。 エージェントが読むのはチケットの説明文だけ。触る場所・やること / やらないこと・検証できる受け入れ条件を書かないと、それらしいが的外れな PR が届く。
