# リテラル

シェルスクリプトのバグの相当数は「クォートの選び間違い」に行き着く。変数が展開されると思ったらされない、逆に展開されてほしくないのに展開される、空白でファイル名がちぎれる。シェルにおける「リテラル（値の書き方）」の話は、実質クォートの話。

## 3つの書き方と展開のルール

```bash
name="world"

echo hello           # クォートなし：動くが空白や特殊文字で事故る
echo "hello $name"   # ダブルクォート：変数展開される → hello world
echo 'hello $name'   # シングルクォート：一切展開されない → hello $name
```

使い分けの原則はシンプルで：

- **変数を含むなら "ダブル"**：`"$var"` のように、変数は常にダブルクォートで包む
- **1文字も解釈させたくないなら 'シングル'**：正規表現、awk のプログラム、`$` を含む文字列など
- **クォートなしは「単語1個の定数」だけ**：`ls -l` のオプションのような、空白も特殊文字も含まないもの

「awk や sed に渡すパターンはシングル、シェル変数を埋め込みたい部分だけダブル」と覚えると、`awk -v user="$USER" '$1 == user'` のような合わせ技も読み解ける。

## なぜ変数をダブルクォートで包むのか

```bash
file="monthly report.txt"
rm $file      # rm monthly report.txt → 「monthly」と「report.txt」2つを削除しようとする
rm "$file"    # rm "monthly report.txt" → 意図通り
```

クォートなしの変数は**空白で分割され、glob（* など）が展開される**。上の例は消したいファイルと違うものを消す事故に直結する。shellcheck が SC2086 で執拗に警告してくるのはこれ。「$ を見たら " で包む」を機械的に守るのが一番安い保険。

## 数値と真偽値：シェルには「型」がない

シェルの値はすべて文字列で、`25` も「25という文字列」。数値として扱われるのは `(( ))` や `-gt` など算術の文脈に入ったときだけ。真偽値のリテラルも存在せず、**真偽は終了コード（0 = 真）で表す**のがシェルの流儀。`true` / `false` はリテラルではなく「終了コード 0 / 1 を返すコマンド」というのが正確な理解。

## 複数行のリテラル：ヒアドキュメント

設定ファイルの生成などで複数行を書くならヒアドキュメント。

```bash
cat <<EOF > /etc/myapp/config.yml
env: $DEPLOY_ENV
log_level: info
EOF
```

デリミタを `<<'EOF'` とシングルクォートで書くと、中身の `$` が展開されなくなる。「テンプレとして変数を埋めたいか、書いたまま出したいか」で使い分ける——ルールはクォートと同じ。
