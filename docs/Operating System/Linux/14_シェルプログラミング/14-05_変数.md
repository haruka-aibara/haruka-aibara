# 変数

「スクリプト内では動くのに、そこから起動した子プロセスで設定が見えない」「= の前後にスペースを入れたらエラー」——シェル変数まわりのつまずきは、代入の構文と export の仕組みの2点に集中している。

## 代入と参照

```bash
APP_DIR="/opt/myapp"     # = の前後にスペースを入れない（入れるとコマンド扱いされる）
echo "$APP_DIR"          # 参照は $ を付けてダブルクォートで包む
echo "${APP_DIR}_backup" # 名前の境界が曖昧なときは ${} で明示
```

`APP_DIR = "/opt/myapp"` と書くと「APP_DIR というコマンドに引数を渡した」と解釈されてエラーになる。他言語から来た人が最初に必ず踏む罠。

コマンドの出力を変数に入れるのは `$( )`：

```bash
today=$(date +%Y%m%d)
host_count=$(wc -l < hosts.txt)
```

## export：子プロセスに見せるかどうか

シェル変数はデフォルトで**そのシェル限り**。スクリプトから起動したコマンド（子プロセス）には引き継がれない。引き継ぐには export する——これが「シェル変数」と「環境変数」の違いのすべて。

```bash
DB_HOST="localhost"      # このシェルだけ
export DB_HOST           # 以後、子プロセスにも引き継がれる（環境変数になる）
DB_HOST=prod-db ./app    # このコマンド1回だけ環境変数を渡す書き方
```

「.env を読んだのにアプリから見えない」「sudo したら変数が消えた」（sudo は環境を意図的にリセットする）は、この境界の理解で説明がつく。なお環境変数の一般論は [03-02_環境変数](../03_シェルとその他基礎/03-02_環境変数.md) を参照。

## システム変数は上書きしない

`PATH`, `HOME`, `PWD`, `IFS` などシェル・OSが使う変数は最初から存在する。自分の変数には別名を付ける——特に `PATH` を雑に代入して壊すと、以後すべてのコマンドが「not found」になる。慣習として**自分の変数は小文字か、プロジェクト接頭辞付き大文字**（`MYAPP_ENV` など）にすると衝突しない。

## スクリプトを堅くする小技

```bash
readonly CONFIG="/etc/myapp/config.yml"   # 定数は上書き禁止に
local tmp_file                            # 関数内変数は local を付けてグローバル汚染を防ぐ
: "${DEPLOY_ENV:?DEPLOY_ENV を設定してください}"   # 必須変数のチェックを1行で
echo "${LOG_LEVEL:-info}"                 # 未設定ならデフォルト値
```

最後の2つはパラメータ展開と呼ばれる機能の一部で、「未設定なら死ぬ/デフォルトを使う」が if 文なしで書ける。設定値を環境変数で受け取るスクリプトの冒頭に `:?` チェックを並べておくと、設定漏れが実行の最初で分かる。
