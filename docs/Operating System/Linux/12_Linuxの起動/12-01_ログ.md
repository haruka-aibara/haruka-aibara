# ログ（起動時・カーネル）

サーバーを再起動したら上がってこない、ディスクをつないだのに認識されない、突然プロセスが殺された。アプリのログには何も残らないこの種の問題は、**カーネルと起動プロセスのログ**を見に行く必要がある。

## dmesg：カーネルのリングバッファ

カーネルは自分のメッセージ（ハードウェア認識、ドライバ、OOM Killer など）をメモリ上のリングバッファに書いている。それを覗くのが dmesg。

```bash
sudo dmesg -T          # -T で人間が読めるタイムスタンプに
sudo dmesg -T -w       # リアルタイムで追う（USB挿抜やディスク接続の確認に）
sudo dmesg -T -l err,warn   # エラーと警告だけ
```

現場でよくある使いどころ：

- **ディスクをアタッチしたのに見えない** → `dmesg -w` しながらアタッチすると、認識された瞬間のデバイス名が流れる
- **プロセスが突然死んだ** → `sudo dmesg -T | grep -i "out of memory"`。OOM Killer の犯行なら誰をなぜ殺したかがここに残る
- **ディスク I/O エラーの疑い** → `dmesg | grep -i "I/O error"`。ハードウェア起因の障害はアプリログより先にここに出る

リングバッファは有限なので、古いメッセージは押し出されて消える。あとから調べる用途には次の journalctl を使う。

## 起動シーケンスのログは journalctl -b

systemd 環境では起動時のログ（どのサービスがどの順で上がり、何が失敗したか）はジャーナルに集約されている。

```bash
journalctl -b              # 今回のブートのログ全部
journalctl -b -p err       # 今回のブートのエラーのみ
journalctl -b -1 -p err    # 前回のブートのエラー（「再起動前に何があったか」）
journalctl -k              # カーネルメッセージのみ（dmesg 相当を時間指定で掘れる）
```

「再起動したら上がってこない→レスキューモードで入って `journalctl -b -1` 」が、起動不能調査の定石。前回ブートのログを見るには永続化が必要な点に注意（`/var/log/journal/` が存在すること。詳細は [09-03_サービスログの確認](../09_サービス管理（Systemd）/09-03_サービスログの確認.md)）。

起動が遅いときの調査には専用コマンドがある：

```bash
systemd-analyze            # 起動にかかった総時間
systemd-analyze blame      # サービスごとの所要時間ランキング
```

## ログレベルの読み方

カーネルログには重要度（emerg > alert > crit > err > warning > notice > info > debug）が付いている。調査ではまず `err` 以上に絞って全体を眺め、当たりがついたら絞りを外して前後の文脈を読む、という順番が効率的。
