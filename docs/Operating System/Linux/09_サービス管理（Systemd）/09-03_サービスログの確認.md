# サービスログの確認

`systemctl status` で `failed` と分かった。次は「なぜ落ちたか」。昔ながらの `/var/log/` 配下を探しにいく前に、systemd 管理下のサービスなら journald が答えを持っている。

systemd はサービスの stdout/stderr と起動・停止などのライフサイクルイベントをすべてジャーナル（バイナリ形式のログ）に集約している。アプリが自前のログファイルを持っていなくても、標準出力に吐いてさえいれば journald 側に残っているのがポイント。

## 特定サービスのログを見る

```bash
journalctl -u nginx
```

`-u`（unit）でサービスを絞るのが基本形。これを知らないと全サービス混在の巨大なログを目視で漁ることになる。

## 調査でよく使う絞り込み

**直近だけ見たい**（落ちた直後の調査はまずこれ）:

```bash
journalctl -u nginx -n 50        # 末尾50行
journalctl -u nginx -e           # ページャで末尾から開く
```

**時間で絞る**（「昨夜の障害」のような調査）:

```bash
journalctl -u nginx --since "2026-07-11 21:00" --until "2026-07-11 22:00"
journalctl -u nginx --since today
```

**リアルタイムで追う**（restart しながら挙動を見るとき）。`tail -f` のジャーナル版:

```bash
journalctl -u nginx -f
```

**エラーだけ見たい**:

```bash
journalctl -u nginx -p err       # err 以上の重要度のみ
```

## 「前回ブート時に何があったか」

再起動を挟むと調査しづらくなるログ調査で、ジャーナルはブート単位の絞り込みができる。

```bash
journalctl -u nginx -b       # 今回のブート以降
journalctl -u nginx -b -1    # 前回のブート
```

「再起動したら直った（が原因不明）」の事後調査で `-b -1` は重宝する。ただしデフォルト設定ではジャーナルが `/run`（揮発性）にしか残らないディストリビューションもある。再起動をまたいでログを残したいなら `/var/log/journal/` ディレクトリを作成しておく（存在すれば journald が永続化する）。
