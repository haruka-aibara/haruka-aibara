# SSH

リモートのサーバーを操作する手段は実質 SSH 一択。毎日使うものなのに「つながる設定を一度作ったら触らない」になりがちで、鍵管理・設定ファイル・セキュリティ設定を押さえているかどうかで日々の効率とサーバーの安全性が両方変わる。

## 基本と鍵認証

```bash
ssh user@203.0.113.10
```

パスワード認証は総当たり攻撃の的になるので、実務は**公開鍵認証**が前提。鍵ペアを作り、公開鍵をサーバーに置く：

```bash
ssh-keygen -t ed25519                    # 鍵ペア生成（現在の推奨アルゴリズム）
ssh-copy-id user@203.0.113.10            # 公開鍵をサーバーの ~/.ssh/authorized_keys へ
```

秘密鍵（`~/.ssh/id_ed25519`）は絶対にサーバーに置かない・共有しない。「サーバー間で SSH したいから秘密鍵をサーバーにコピー」は典型的なアンチパターンで、agent forwarding（`ssh -A`）か ProxyJump で解決する。

## ~/.ssh/config に書けば毎回のオプション地獄から解放される

踏み台経由・ポート指定・鍵指定を毎回打つのは無理がある。クライアント設定に書く：

```
Host prod-web
    HostName 10.0.2.15
    User deploy
    IdentityFile ~/.ssh/id_ed25519
    ProxyJump bastion.example.com    # 踏み台経由を1行で
```

以後 `ssh prod-web` だけでつながる。ProxyJump は「踏み台に入ってから ssh を打ち直す」を自動化しつつ、通信は end-to-end で暗号化されたままという優れもの。

## サーバー側を固める：/etc/ssh/sshd_config

インターネットに露出した SSH ポートには、常時スキャンとブルートフォースが来ている（`journalctl -u ssh` を見ると実感できる）。最低限の設定：

```
PasswordAuthentication no    # 鍵認証のみに
PermitRootLogin no           # root 直ログイン禁止。sudo 経由に
```

変更後は `sudo sshd -t` で構文チェックしてから `sudo systemctl reload ssh`。**設定を壊すと次から入れなくなる**ので、リロード後も今のセッションを閉じずに別ターミナルで接続確認するのが作法。

初回接続時に出る「fingerprint を信頼するか」の確認は、接続先が本物かを人間が検証する唯一のポイント。以後は `~/.ssh/known_hosts` に記録され、フィンガープリントが変わると警告が出る——サーバーを作り直した覚えがないのにこの警告が出たら、中間者攻撃の可能性を疑うのが正しい反応。

なお AWS では SSM Session Manager のように「22番を一切開けずにシェルを取る」選択肢があり、新規設計ならポートを公開しない構成のほうが筋がいい。
