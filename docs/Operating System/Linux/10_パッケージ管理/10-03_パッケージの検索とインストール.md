# パッケージの検索とインストール

「あのツールを入れたいが、パッケージ名が分からない」。コマンド名とパッケージ名は一致するとは限らない（例: `dig` コマンドは Ubuntu では `dnsutils`、RHEL 系では `bind-utils` に入っている）。まず探して、確かめてから、入れる——この3ステップを押さえる。

## 1. 探す

```bash
# Debian/Ubuntu
apt search dig

# RHEL/Fedora
dnf search dig
dnf provides '*/dig'   # 「このファイルを含むパッケージ」を逆引き
```

`dnf provides`（apt なら `apt-file search`）は「コマンド名からパッケージ名を逆引き」できるので、冒頭の dig 問題はこれで解決する。ちなみに Ubuntu では、未インストールのコマンドを打つと「apt install ○○ で入ります」と教えてくれることも多い。

## 2. 入れる前に確かめる

検索結果から候補を見つけたら、入れる前に中身を確認する癖をつける。似た名前のパッケージを取り違えるのを防げる。

```bash
apt show dnsutils    # 説明・バージョン・依存関係を表示
dnf info bind-utils
```

## 3. 入れる

```bash
# Debian/Ubuntu（先にインデックス更新）
sudo apt update && sudo apt install dnsutils

# RHEL/Fedora
sudo dnf install bind-utils
```

依存パッケージは自動で解決される。追加で何が入るかはインストール前に一覧表示され、確認を求められる（自動化スクリプトでは `-y` で確認を飛ばす）。

## ソースからビルドしなくていい、が原則

チュートリアルによっては `./configure && make && make install` でソースから入れる手順が書かれていることがあるが、パッケージがあるならパッケージで入れる。理由は入れるときではなく**その後**にある：

- パッケージ管理外のファイルは `apt upgrade` の対象にならず、脆弱性が出ても放置される
- どこに何を撒いたか記録が残らないので、きれいにアンインストールできない
- 「このサーバーに何が入っているか」の棚卸し（[10-04](10-04_インストール済みパッケージの一覧.md)）から漏れる

ソースビルドが正当化されるのは、パッケージが存在しない・特殊なビルドオプションが必要、といった場合に限る。
