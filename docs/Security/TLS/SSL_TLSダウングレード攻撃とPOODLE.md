# SSL/TLS ダウングレード攻撃と POODLE — なぜ「使われていない古いバージョン」を切る必要があるのか

脆弱性診断や SSL Labs で「SSLv3 が有効」「TLS 1.0 が有効」と指摘される。あるいは顧客のセキュリティチェックシートに「SSL 3.0 を無効化していますか」という欄がある。

ここで最初に湧く疑問はだいたい同じ。

> うちのユーザーのブラウザは全部 TLS 1.2 で繋いでいる。サーバが古いバージョンも「受け付けられる」だけで、実際には使われていない。なぜ問題なのか。

この「実際には使われていないから安全」という直感を壊すのがダウングレード攻撃である。攻撃者は、**両者が本来もっと強いものを使えるにもかかわらず、弱いほうを選ばせる**ことができる。そして弱いほうに落ちた瞬間、そこには POODLE のような既知の攻撃が待っている。

## TLS はどうやってバージョンを決めているか

クライアントとサーバは、通信を始める前にどのバージョン・どの暗号スイートを使うか合意する。

```
Client                                Server
  │  ClientHello                         │
  │   「TLS 1.2 まで話せる」              │
  │   「使える暗号スイートはこれとこれ」    │  ──→
  │                                      │
  │                        ServerHello   │
  │              「じゃあ TLS 1.2 で」    │  ←──
  │              「暗号スイートはこれ」    │
```

**両者が対応している中で最も高いバージョンが選ばれる**。ごく素直な仕組みだが、ここに構造的な弱点がある。

**このやり取りは、暗号化される前に行われる。** 暗号化するための取り決めをしている最中なのだから当然だが、結果として ClientHello / ServerHello は経路上で丸見えかつ書き換え放題ということになる。

ダウングレード攻撃とは、この合意プロセスに介入して、本来より弱い設定を選ばせる攻撃の総称である。

## 用語の整理

「ダウングレード攻撃」「バージョンロールバック攻撃」「POODLE」は並列の攻撃名ではない。包含関係がある。

| 用語 | 位置づけ |
|---|---|
| ダウングレード攻撃 | 上位概念。ネゴシエーションに介入して弱い設定を選ばせる攻撃全般 |
| バージョンロールバック攻撃 | そのうち **プロトコルバージョン** を落とすもの（TLS 1.2 → SSL 3.0 など） |
| FREAK / Logjam | そのうち **暗号スイート** を落とすもの（輸出規制時代の 512 bit RSA / DH に落とす） |
| POODLE | ダウングレードそのものではなく、**落とした先（SSL 3.0）で使える攻撃** |

つまりバージョンロールバックは「ドアをこじ開ける手口」、POODLE は「開いたドアの先でやること」。この2つはセットで語られる。POODLE の正式名 **Padding Oracle On Downgraded Legacy Encryption** に "Downgraded" が入っているのはそのためである。

## 手口1：ハンドシェイクの書き換え — 実は素朴には成功しない

まず思いつくのは、中間者が ClientHello の「TLS 1.2 まで話せる」を「SSL 3.0 まで」に書き換える方法。

だが TLS はこれを検知できる。ハンドシェイクの最後に交換する **Finished メッセージ**が、それまでにやり取りした全ハンドシェイクメッセージのハッシュを、確立した鍵で保護した値になっている。途中で1バイトでも書き換えられていれば、クライアントとサーバで計算結果が食い違い、接続は落ちる。

なので中間者による直接の書き換えは、**接続を壊すことはできても、盗聴可能な状態にはできない**。

ただしこれは歴史的にはそうではなかった。SSL 2.0 にはこのハンドシェイク保護がなく、書き換えがそのまま通った。SSL 3.0 はその反省から、RSA 鍵交換で送る PreMasterSecret の中にクライアントが提示したバージョン番号を埋め込み、サーバ側で照合できるようにしている。1996 年に Wagner と Schneier が指摘した古典的な「バージョンロールバック攻撃」は、まさにこの対策が入る前の話である。

**試験でこの用語が出たら、まずこの SSL 2.0 / 3.0 時代の文脈を指していると考えてよい。**

## 手口2：フォールバックを悪用する — こちらが本命

では現実に POODLE はどうやって SSL 3.0 まで落としたのか。答えは、**ブラウザに自分から下げさせる**である。

当時のブラウザには互換性のための挙動があった。TLS 1.2 でハンドシェイクを試みて失敗すると、「相手はバージョンネゴシエーションを正しく実装していない古いサーバなのだろう」と判断し、**バージョンを1段下げて接続し直す**。それでも駄目ならまた下げる。TLS 1.2 → 1.1 → 1.0 → SSL 3.0 と落ちていく。俗にダウングレードダンスと呼ばれる。

攻撃者がやることは、暗号を破ることでも、ハンドシェイクを偽造することでもない。

**TCP 接続を切るだけ。**

```
1回目  Client ─ TLS 1.2 で接続試行 ──→  ✂ 攻撃者が RST
2回目  Client ─ TLS 1.1 で接続試行 ──→  ✂
3回目  Client ─ TLS 1.0 で接続試行 ──→  ✂
4回目  Client ─ SSL 3.0 で接続試行 ──→  Server「SSL 3.0 ですね、いいですよ」
```

4回目のハンドシェイクは**改ざんされていない正規のもの**なので、Finished による検知は当然働かない。クライアントが自分の意志で SSL 3.0 を選んだからだ。

ここが「サーバで古いバージョンを有効にしたまま放置してはいけない」理由である。サーバが SSL 3.0 を受け付ける限り、この4回目が成立してしまう。逆に言えば、**サーバが SSL 3.0 を拒否していれば、攻撃者がいくら接続を切っても落ちる先がない。**

## 落ちた先で何が起きるか — POODLE

SSL 3.0 まで落ちると、CBC モードのパディング検証の甘さを突ける。

CBC は平文をブロック長（AES なら 16 バイト）の倍数にそろえる必要があるため、末尾にパディングを詰める。ここで SSL 3.0 と TLS 1.0 以降には決定的な差がある。

| | パディングの中身 |
|---|---|
| SSL 3.0 | **規定なし。最後の1バイト（パディング長）しか検証しない** |
| TLS 1.0 以降 | 中身も規定され、検証される |

SSL 3.0 は、パディング部分に何が入っていようとチェックしない。最後の1バイトだけを見て「そこに書かれたバイト数だけ捨てる」という動作をする。

攻撃者はこれを利用する。

1. 被害者のブラウザから、**最終ブロックがすべてパディングになる**ような長さのリクエストを送らせる
2. その最終ブロックを、解読したい暗号文ブロック（Cookie が入っているブロック）とすり替える
3. サーバは復号して最後の1バイトを見る。それがたまたま 15（16 バイト分のパディングを表す値）なら、そのブロックを丸ごと捨てて MAC 検証に進み、**残りは無傷なので検証は通る**
4. 通ったか落ちたかは、応答を見れば分かる

つまりサーバが「パディング長が正しいかどうか」を答えてくれる装置（**オラクル**）になっている。成功確率は 1/256 なので、平均 256 回試せば平文 1 バイトが判明する。あとはリクエスト長を 1 バイトずつずらして同じことを繰り返せば、Cookie が端から順に割れていく。

狙いは **セッション Cookie の窃取＝セッションハイジャック**である。暗号鍵は最後まで一切割れていないのに、目的は達成されてしまう。

### 成立条件は厳しいのか

必要なのは2つ。

- **中間者の位置**（通信を切ったり観察したりできる）
- **被害者のブラウザで攻撃者の JavaScript を動かせること**（同じリクエストを数万回送らせるため。Cookie はブラウザが自動で付けてくれる）

単独で見ればハードルが高そうだが、**公衆 Wi-Fi ではこの2つが同時に満たせる**。経路上にいるのだから、被害者が開いた HTTP のページに JavaScript を注入すればいい。「カフェの Wi-Fi でネットバンキングにログインする」という、まさに絵に描いたようなシナリオで刺さる。

### 「SSL 3.0 を切ったから安心」ではない

POODLE には TLS 版がある（CVE-2014-8730）。一部の実装が、TLS でも SSL 3.0 と同じくパディングの中身を検証していなかった。この場合、**ダウングレードなしで TLS 1.2 のまま同じ攻撃が成立する**。

こちらはプロトコル仕様ではなく実装のバグなので、対処はパッチ適用。診断で「TLS でも POODLE」と出たら、プロトコル設定ではなくミドルウェアのバージョンを見る。

## 対策

### 本筋：SSL 3.0 を無効化する

POODLE は SSL 3.0 の**仕様そのもの**の欠陥である。パディングの中身を検証しないと決めているのはプロトコルなので、パッチでは直らない。**切る以外に対処がない。**

RFC 7568 が SSL 3.0 を、RFC 8996 が TLS 1.0 / 1.1 を、それぞれ正式に非推奨としている。今から新規に構築するなら TLS 1.2 以上に固定するのが当然の出発点で、悩む余地はない。

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
```

AWS なら ALB / CloudFront のセキュリティポリシーを TLS 1.2 以上のものにする。

### 過渡期の措置：TLS_FALLBACK_SCSV

とはいえ、当時はクライアント側の古い実装を切り捨てられない事情があった。そこで導入されたのが **TLS_FALLBACK_SCSV**（RFC 7507）。

クライアントがフォールバックで再接続するとき、「これは自発的な再接続です」という印を ClientHello に含める。サーバはそれを見て、**「自分はもっと上のバージョンを話せるのに、なぜ下がってきた？」** と気づき、`inappropriate_fallback` で接続を拒否できる。

ダウングレードダンスの穴を塞ぐ仕組みだが、あくまで古いバージョンを残したまま延命するための措置である。

### 構造的な解決：TLS 1.3

TLS 1.3 では、ダウングレード検知がプロトコルに組み込まれた。TLS 1.3 対応サーバが 1.2 以下でネゴシエートするとき、ServerHello の Random の末尾 8 バイトに決められた値（`DOWNGRD` + 1 バイト）を埋め込む。この Random はサーバの署名で保護されるため中間者は偽造できず、クライアントは「本当は 1.3 を話せる相手なのに落とされた」と検知して接続を中断する。

加えて、バージョン交渉自体が `supported_versions` 拡張に移され、レガシーなバージョンフィールドは固定値になった。中間層の機器が古い挙動をしても交渉が壊れないようにするための設計変更である。

## 提案するときの言い換え

「SSLv3 を無効化しましょう」だけでは、なぜ今それをやるのかが伝わらない。

| 技術的な言い方 | ビジネス側に伝わる言い方 |
|---|---|
| SSL 3.0 / TLS 1.0 を無効化する | 公衆 Wi-Fi 利用者のログインセッションが盗まれる経路を塞ぐ。設定変更だけで済み、追加コストはゼロ |
| ダウングレード攻撃対策 | 「古い方式は受け付けるだけで使っていない」は通用せず、攻撃者は使わせることができる |
| 非推奨プロトコルの棚卸し | 顧客のセキュリティチェックシートや PCI DSS で必ず問われる項目。指摘されてから直すと商談が止まる |

なお実務上の論点は「切るべきか」ではなく **「切ったときに誰が繋がらなくなるか」** にほぼ集約される。アクセスログからネゴシエートされた TLS バージョンを集計し、影響範囲を数字で出してから提案するのが順序として正しい。ALB なら `ssl_protocol` がアクセスログに出るので、そこを見れば済む。

## 試験で問われるところ

- **バージョンロールバック攻撃**：より弱いバージョンを使わせる攻撃。SSL 3.0 は PreMasterSecret にバージョン番号を埋めて検知する
- **POODLE**：SSL 3.0 の CBC パディングが検証されないことを突くパディングオラクル攻撃。対策は SSL 3.0 の無効化（パッチでは直らない）
- **ダウングレードの成立経路**：ハンドシェイクの改ざんではなく、クライアントのフォールバック挙動を利用する
- **TLS_FALLBACK_SCSV**：フォールバックであることをサーバに伝えて拒否させる仕組み
- 混同しやすい他の CBC 系攻撃：**BEAST**（IV が予測可能）、**Lucky 13**（MAC 検証のタイミング差）。POODLE は「パディングの中身を見ていない」が原因、と原因で区別する

CBC・パディング・IV まわりの前提は [AESとブロック暗号モード](./AESとブロック暗号モード.md) に整理してある。
