# なぜ SSL/TLS は TCP の上だと使いやすいのか

## 引っかかる場面

テキストや試験の解説に、こういう一文がさらっと出てくる。

> SSL/TLS はトランスポート層（TCP）の上で動作するため、利用しやすい。

読んだ瞬間は「そうか」で通り過ぎるが、後で人に説明しようとすると詰まる。

- 暗号化するだけなら UDP の上でもできるはずでは？
- 「利用しやすい」って、誰にとって、何が楽なのか？
- 実際 DTLS や QUIC は UDP の上で TLS を使っている。じゃあ TCP じゃなくてもいいのでは？

この記事は、この一文を自分の言葉で説明できる状態にすることがゴール。

---

## 結論を一言で

**TLS が下に要求するものと、TCP が提供するものがぴったり一致していて、なおかつ TLS が上に見せる顔も TCP と同じだから。**

入口と出口の形が同じなので、**TCP とアプリの間に「差し込む」だけで済む**。上も下も作り変えなくていい。これが「利用しやすい」の中身。

```
[アプリ (HTTP)]          ← バイトストリームを read/write したい
      ↕                     ここのインターフェースは変わらない
[   TLS   ]              ← バイトストリームを read/write させてくれる
      ↕                     ここのインターフェースも変わらない
[   TCP   ]              ← バイトストリームを read/write させてくれる
      ↕
[   IP    ]
```

TLS の名前そのものが Transport Layer Security ＝「トランスポート層のセキュリティ」で、TCP を前提にしていることが名前に出ている。

以下、これを「下向き」と「上向き」の 2 方向に分けて詰める。

---

## 下向きの話：TLS は TCP に何を丸投げしているか

### TLS レコードには順番を示す番号が入っていない

TLS は通信を「レコード」という単位に区切って暗号化する。TLS 1.2 のレコードヘッダは 5 バイトしかない。

```
ContentType     (1 byte)   ← handshake / application_data など
ProtocolVersion (2 byte)
length          (2 byte)
--------------------------------
（暗号化された中身）
```

**シーケンス番号がない。** ではどうやって順番を管理しているかというと、送信側・受信側がそれぞれ手元で 0 から数えるカウンタを持っている。この番号は**回線に流れない**（暗黙のシーケンス番号）。

そしてこのカウンタは、単なる管理用の数字ではなく暗号処理の入力そのものになる。

- TLS 1.2：MAC（改ざん検知用のタグ）を計算するときの入力に 64 ビットのシーケンス番号を含める
- TLS 1.3：AEAD の nonce を「静的 IV XOR シーケンス番号」で作る

つまり **1 個でも抜けたり順番が入れ替わったりすると、送信側と受信側でカウンタがずれ、復号・検証が失敗する。** TLS はこれを「通信エラー」ではなく「攻撃」とみなして、fatal alert を出して接続を切る。TLS 側に再送も並べ替えも存在しない。

### これは手抜きではなく、TCP を信じることで得ている贅沢

一見すると危うい設計だが、逆に考えるとこうなる。

TCP は「送った順に、欠けなく、重複なく届く」を保証してくれる。この前提があるなら、TLS はシーケンス番号を**送る必要がない**。そして送らずに暗号計算に混ぜ込むだけで、以下が自動的に手に入る。

| 攻撃 | なぜ検知できるか |
|---|---|
| レコードの削除 | 以降のカウンタがずれて検証失敗 |
| レコードの挿入 | 同上 |
| レコードの並べ替え | 同上 |
| 過去のレコードの再送（リプレイ） | 同上 |

**TCP の順序保証を土台にしたことで、TLS は「暗号化と認証」だけに専念できている。**

順序以外にも丸投げしているものがある。

- **再送**：ハンドシェイクは何往復もするやり取りだが、パケットが落ちても TCP が勝手に再送してくれる。TLS にタイマーは要らない
- **分割・再組立**：TLS レコードは平文で最大 16KB（2^14）まで許される。MTU を超えるサイズだが、TCP がセグメントに割ってくれるので TLS は MTU を一切気にしなくていい
- **コネクションの寿命**：TCP コネクション 1 本 = TLS コネクション 1 本。開始と終了がそのまま対応する

## 反例で確かめる：UDP でやろうとすると何が増えるか（DTLS）

「TCP だと楽」を実感する一番の近道は、TCP を外した DTLS を見ること。TLS をほぼそのまま UDP に載せるために、以下を**全部自前で足す羽目になった**。

**レコードヘッダが 5 バイト → 13 バイトに膨らむ**（DTLS 1.2）

```
type            (1)
version         (2)
epoch           (2)   ← 追加：鍵が切り替わった世代の番号
sequence_number (6)   ← 追加：暗黙にできないので明示的に送る
length          (2)
```

順序が保証されないので、番号を回線に載せるしかない。TCP の上で節約できていた 8 バイトが、そのまま復活する。

**ハンドシェイクメッセージにも番号と分割情報が要る**

```
TLS  のハンドシェイクヘッダ : msg_type(1) + length(3)                     = 4 バイト
DTLS のハンドシェイクヘッダ : + message_seq(2) + fragment_offset(3)
                              + fragment_length(3)                        = 12 バイト
```

`fragment_offset` / `fragment_length` があるのは、**MTU を超える証明書チェーンを自分で分割して、受信側で自分で組み立て直す**必要があるから。TCP ならタダでやってくれていた仕事。

**さらに実装しなければならないもの**

- ハンドシェイクの再送タイマー（応答が来なければ自分で再送、バックオフも自前）
- リプレイ検知のウィンドウ（受信済みシーケンス番号のビットマップ管理）
- 送信レコードが MTU に収まるようサイズを制御する仕組み
- 「順序が狂ったら即切断」ができないので、遅れて届いたレコードを許容する挙動

**この差分がまるごと「TCP の上ならやらなくていいこと」**。ここが「TCP 上だと利用しやすい」の実体だ。

### QUIC はもっと極端

QUIC は UDP の上で動くが、TLS をそのまま載せ替えることはできなかった。**再送・順序制御・フロー制御をトランスポート自身に作り直し、その上で TLS のハンドシェイクを QUIC の中に統合する**という設計になっている（RFC 9000 / RFC 9001）。

つまり「TLS を UDP に持っていく」には、**TCP が持っていた機能を別の形で作り直すしかなかった**。TLS が TCP にどれだけ依存していたかの、これ以上ない証拠になる。

## 上向きの話：既存プロトコルを書き換えずに済む

もう一方の「使いやすさ」は、アプリ側から見たもの。

### TLS も「バイトストリーム」の顔を上に見せる

TCP を使うアプリは `connect()` して `write()` / `read()` する。TLS を挟んだアプリは `SSL_connect()` して `SSL_write()` / `SSL_read()` する。**扱う対象は同じ「順序が保証されたバイトの流れ」のまま。**

だから、その上に乗っているアプリケーションプロトコルを**一切変更せずに**暗号化できた。

| 平文 | TLS 化 | プロトコル自体の変更 |
|---|---|---|
| HTTP (80) | HTTPS (443) | なし |
| SMTP (25) | SMTPS (465) | なし |
| IMAP (143) | IMAPS (993) | なし |
| LDAP (389) | LDAPS (636) | なし |

HTTPS は「HTTP の暗号版プロトコル」ではなく、**HTTP をそのまま TLS の上で喋っているだけ**。ここが腹落ちすると「アプリケーションプロトコルに依存しない」という説明文の意味が変わる。

### STARTTLS ができるのも TCP のおかげ

ポートを分ける方式のほかに、**同じポートで平文で始めて途中から TLS に昇格する** STARTTLS がある（SMTP 587、IMAP 143、LDAP 389 など）。

これが成立するのは、TCP コネクションが「1 本の途切れない連続したストリーム」だから。**同じ接続を維持したまま、途中から流すバイトの意味を切り替えられる。** UDP のようにパケットが独立していると、この「途中から」が難しくなる。

### IPsec との対比：導入の手間が段違い

同じ暗号化でも、IP 層でやる IPsec は OS のカーネルやネットワーク機器側の対応が必要になる。TLS は**ユーザー空間のライブラリ（OpenSSL など）で完結する**。

つまり **アプリ開発者だけの判断で導入できる**。この「関係者の少なさ」も「利用しやすい」の重要な成分だ。

---

## 「利用しやすい」の裏返し：TCP の弱点をそのまま引き継ぐ

セキュリティの観点では、ここまでとセットで押さえておきたい。**TCP に乗っかった結果、TCP の性質もそのまま引き継いでいる。**

**TCP ヘッダは平文のまま守られない**
接続先の IP・ポート番号、パケットのサイズやタイミングといったメタデータは TLS の保護範囲外。誰がどこに繋いだかは見える。SNI（接続先ホスト名）も長らく平文だった（ECH で対処中）。

**接続を切る攻撃が刺さる**
攻撃者が RST や FIN を偽装すると TCP 接続が落ちる。TLS 側から見ると通信が途中で終わる。これを「データの終わり」とアプリが誤認すると **truncation attack** になる。だから TLS には終了を明示する `close_notify` があり、**それ無しで切れた場合を異常として扱う**必要がある。

**RTT が積み上がる**
TCP の 3 ウェイハンドシェイクが終わってから TLS のハンドシェイクが始まる。TLS 1.2 なら合計 3 RTT かかる。TLS 1.3 で 2 RTT（再開時 0-RTT）まで縮んだが、この直列構造こそ QUIC がハンドシェイクを統合した理由の一つ。

**バージョン交渉は TCP が守ってくれない**
「どの TLS バージョンで話すか」の交渉は TLS のハンドシェイクの中で行われ、まだ暗号化されていない。ここを書き換えられるのがダウングレード攻撃（POODLE など）。TLS 1.3 は ServerHello の random 末尾 8 バイトに目印（downgrade sentinel）を仕込んで検知できるようにした。

## 提案者としての言語化

技術的な事実を、判断材料として伝える形に置き換えるとこうなる。

| 技術的な言い方 | 相手に届く言い方 |
|---|---|
| TLS はトランスポート層とアプリ層の間に挟まる | 既存の通信プログラムを書き換えずに暗号化できる。HTTPS 化はアプリの作り直しではなく、証明書と設定の作業に近い |
| TLS は TCP の順序保証に依存している | 音声・映像・IoT など UDP を使う通信は同じやり方では暗号化できず、DTLS など別の仕組みと追加の実装コストが要る |
| TLS は TCP ヘッダを保護しない | 「TLS を入れたから通信は全部見えない」は誤り。誰がどこに繋いだかの記録は残るし、逆に言えば通信先の監視は TLS を入れても続けられる |

## 自分の言葉で言うための骨格

**15 秒版**

> TLS は「順番通りに欠けなく届く」ことを前提に作られていて、TCP がそれをちょうど提供する。しかも TLS 自身も上には TCP と同じバイトストリームの顔を見せるので、TCP とアプリの間に挟むだけで済む。だから既存プロトコルを書き換えずに暗号化できた。

**60 秒版**

> TLS はデータをレコードに分けて暗号化するけど、レコードに順番を示す番号を入れていない。送受信それぞれが手元で数えたカウンタを、そのまま MAC や nonce の計算に混ぜている。だから 1 個でも抜けたり順番が入れ替わったりすると復号に失敗して接続が切れる。これが成立するのは TCP が順序と再送を保証しているからで、TLS はその上で暗号化だけに専念できている。
>
> 実際、同じことを UDP でやろうとした DTLS は、シーケンス番号を明示的に送り、ハンドシェイクの再送タイマーと分割・再組立とリプレイ検知を全部自前で持つ羽目になった。その差分が「TCP だと楽」の中身。
>
> もう一つは上向きで、TLS が上に見せるインターフェースも TCP と同じバイトストリームだから、HTTP や SMTP を 1 行も変えずに HTTPS・SMTPS にできた。しかもユーザー空間のライブラリで完結するので、IPsec と違ってアプリ側だけで導入できる。

**突っ込まれたとき用**

- 「UDP でもできるのでは？」→ できるが DTLS になる。TCP がやっていた再送・順序制御・分割を全部自前で作り直す必要がある
- 「QUIC はどうなの？」→ TLS をそのまま UDP に載せたのではなく、トランスポート側に信頼性を作り直した上で TLS ハンドシェイクを統合した。TCP 依存の裏返しの証拠
- 「TLS を入れれば安全？」→ TCP ヘッダとメタデータは平文のまま。接続を切る攻撃やバージョンのダウングレード交渉も別途対策が要る
