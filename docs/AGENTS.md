# エージェント作業ガイド

このリポジトリを扱う AI コーディングエージェント向けの共通ルールです。Claude Code / Codex / Gemini CLI など、特定ツールに依存しない指示はここを正とします。

## プロジェクト概要

技術的な学びやナレッジをトピック別にまとめた個人リポジトリ。コードを書くプロジェクトではなく、学習メモ・記事・スニペットの蓄積が目的。

## リポジトリ構造

**トップレベルはフラット。1階層目はトピック名そのもの**（例: `Terraform/`, `Kubernetes/`, `Python/`, `Amazon Web Services/`）。

`Provisioning/Terraform/` のような分類ディレクトリは**作らない**。「Terraform は Provisioning か IaC か Infrastructure か」は正解が複数あって推論で復元できず、置き場所を記憶に頼る羽目になるため。トピック名なら検索する文字列と一致する。

- **新しいトピックは分類せず、トピック名のディレクトリをトップレベルに作る**
- **トップレベルのディレクトリ名は英語**（`Presentations/`, `Cyber Attacks/`, `AI and Machine Learning/`）。単語区切りはスペース。2階層目以降は日本語でよい（`AI and Machine Learning/生成AIパスポート/`）
- 各トピック内はファイル名で分類（番号プレフィックスを付ける場合もあるが必須ではない）
- 番号付きサブディレクトリで章立てする場合もある（例: `Terraform/01_Terraformのイントロダクション/`）
- 記事が1本でもトピック名のディレクトリに置く（リポジトリ直下に記事ファイルを直接置かない）
- 目次は `index.html`。GitHub API からツリーを動的に取得するのでパスのハードコードはなく、ディレクトリを増減しても手を入れる必要はない

## 記事を書くときのルール

- 日本語で書く
- 無駄に長くしない。読む側の時間を尊重する
- 新しいトピックはトピック名のディレクトリをトップレベルに作る（「リポジトリ構造」参照）
- 記事末尾には必ず `## 参考` セクションを置き、参照した公式ドキュメント・ブログ等のリンクを列挙する
- 公開リポジトリなので、会話で共有された個人の状況・前提（知識レベル、配属先、関わっている案件など）は記事に反映しない。同じ場面に置かれた誰でも読めるトーンで書く
- 外部学習サイトへの「準拠」「に沿った」という表現は使わない。学習リソースとして単にリンクを紹介するのは可

### 書き方のスタイル

**「現場でこういう問題が起きたとき、これで解決できる」という構成で書く。**

読み手が「あ、自分がいま困ってるのと同じ場面だ」と気づけることがゴール。公式ドキュメントの言葉の言い換えにならない。

- **冒頭は問題・場面から入る**: どういうときに困るのか、なぜこれが必要なのかを最初に書く
- **機能の説明はその後**: 構文・使い方は「問題を解決する手段」として位置づける
- **コード例は場面ベース**: 「こういうときにこう書く」という形にする。網羅的なサンプルより、実際に書く場面に近いものを選ぶ

**NG 例**（公式ドキュメントの言い換え）:
> 「data ブロックは既存リソースを参照する仕組みです」→ 構文の説明へ

**OK 例**（問題・場面ベース）:
> 「Terraform は自分が管理しているリソースしか知らない。でも手動で作った VPC や別チームが管理している Route53 など、管理外のリソースを参照したい場面がある。それを解決するのが data ブロック」

### 想定読者は「そのトピックを知らない人」（重要）

**デフォルトの読者は、そのトピックをまだ知らない人。指定がなければ常にこれ。**

記事のゴールは「読んだ人がその機能を最低限使えるようになること」。**それを満たしたら終わり。**中級者向けの落とし穴・応用・関連機能は、この記事の仕事ではない。

自己チェックは1問だけ：

> **「これを知らない人が読む前提で、この情報要るか？」**

「知っておくと役に立つ」は残す理由にならない。要らないなら削る。

#### 典型的な書きすぎパターン（全部 NG）

AI は放っておくと網羅性重視で盛る。以下は初学者向け記事に入れない：

- **評価タイミング・内部挙動の話**（例：`data` が plan で読まれるか apply で読まれるか、`known after apply` の発生源）
- **まれなエラーの原因分析**（例：`try()` で握りつぶせない理由）
- **他機能との使い分け・比較の節**（例：`data` の記事に `import` / `terraform_remote_state` の判断フロー）。たいてい別記事にすべき内容
- **バージョン差分・非推奨情報**（例：プロバイダ v6 でこの属性が非推奨）
- **他の章に既にあるトピックの再解説**。1行触れてリンクを張るだけにする
- **毎回のセキュリティ節**。後述の「セキュリティ記事での追加視点」は**セキュリティが主題の記事のための指針**であって、全記事にセキュリティ節と言語化テーブルを付ける意味ではない

これらは消すのではなく、**必要なら「◯◯の落とし穴」として別記事に切り出す。**

#### 分量の目安

- **本文（図・コードを除く）1500文字程度**。超えたら削れないか疑う
- **図は2〜3点**。思いつくたびに足さない
- **「最初に知っておくこと」的な注意書きは2〜3個まで**

例外は「ゼロから理解する」形式の記事だけ（後述の専用テンプレートに別の目安がある）。それ以外はこの目安に従う。

#### 参考：この基準で書いた記事

`Terraform/16_データソース/16-02_データソースを図で理解する.html`
構成は「何が問題なのか＋図 → 書き方＋図 → よくある例 → 注意2つ → 参考」だけ。迷ったらこの粒度に合わせる。

### HTML で書くとき

**「〇〇の解説を HTML で作って」と言われたら、この節の内容で作る。形式を確認し直さない。** 「markdown でよくないか」と聞き返すのも不要——HTML 指定は「図で理解を早めたい」の意味だと解釈し、図が主役の構成にする。時間軸・入れ子構造・レイヤの重なりなど、図にできる切り口を自分で見つけて描く。

指定がないときに自分で選ぶなら、判断は「図が要るか」の一点。見出し・段落・表・リストしか使わないなら markdown で書く（CSS を被せただけの HTML は markdown の劣化版）。

書くときのルール：

- **図は inline SVG を手書きする**。外部ライブラリ・CDN・画像ファイルは使わない。1ファイルで完結させる（ダウンロードしてそのまま開ける状態）
- **図が主役、文章は図の補助**。図を入れたぶん文章は削る。図の内容を文章で言い直さない
- **`figcaption` には図に描けない補足を書く**。図のキャプションが図の説明の繰り返しになっているのは無駄
- **色は `:root` の CSS 変数で定義し、`prefers-color-scheme` でダーク対応**。SVG 内も `fill="var(--c1)"` で参照する。図の色数は4〜5色まで
- **本文の構成ルールは markdown 記事と同じ**（問題・場面から入る、末尾に `## 参考`）
- **実例**: `Networking/HTTP2.html`。順番待ち vs 多重化を同じ時間軸に並べる、入れ子構造をそのまま入れ子の矩形で描く、といった作り

出来上がりの確認は、ファイルをそのままレンダリング表示して見せる（トークンを使わない）。Artifact 化は共有用の URL が欲しいときだけ。

### 「ゼロから理解する」記事のテンプレート

**「〇〇をゼロから理解する を HTML で作って」「ゼロから理解する形式で」と言われたら、この節の型で作る。構成を確認し直さない。**

通常の記事（前節まで）とは別枠。**土台から積み上げる長編**で、そのトピックの本線になる1本。同じトピックに要点まとめの個別記事がある場合は、こちらが本線・個別記事は詳細としてリンクで棲み分ける。

**リファレンス実装**（この3本に粒度を合わせる。迷ったら開いて見る）:
- `Networking/ネットワーク仮想化/VXLANをゼロから理解する.html`
- `TLS/TLSハンドシェイクと証明書検証をゼロから理解する.html`
- `Web Application Security/セッション管理と入力の扱いをゼロから理解する.html`

#### 構成（この順で固定）

1. **`## この記事の目的`** — 「解説記事を読んで途中で分からなくなった経験はありませんか」→「読解力の問題ではない。多くの記事は〈中級者向けの前提〉から始まるから」→「そこでこの記事はあえて遠回りする。〈いちばん手前の話〉から始めて5ステップで進む」の3段。ゴールは用語を覚えることではなく自分の言葉で説明できること、と書く
2. **ロードマップ**（`.rmbox` + `.rm`）— 5ステップの一覧。末尾に「STEP N までは全部前提知識。本題は STEP 5 だけだが、そこに至る4ステップがないと理解できない」旨の `.cap`
3. **`## STEP 1` 〜 `## STEP 5`** — 各見出しの直後に進捗ナビ（`.rm`、済んだステップは `.done` に `✓`、現在は `.now`）
4. **`## まとめ：そのまま使える説明テンプレート`** — 30秒版・2分版を `blockquote` で。2分版は「30秒版に足す分」として書く
5. **`## よくある誤解`** — 2〜3個。`h3` 見出し＋数行
6. **`## 次の一歩`** — 意図的に触れなかった話を箇条書き。既存記事へのリンクを張る
7. **`## 参考`**

#### 積み上げの設計（ここが本体）

- **STEP 1 は「そのトピックの手前」から始める**。VXLAN なら MAC アドレス、TLS なら「通信ははがき」、セッション管理なら「HTTP は前回を覚えていない」。本題そのものは STEP 5 だけ
- **各ステップの末尾に確認問題**（`.quiz` + `<details>`）。**次のステップへの橋渡しに使う**のがコツ。「ここまでで防げるか？」→「防げない。なぜなら〜」→ 次の STEP へ、という形にする。答えのない考察問題を1つ混ぜてもよい
- **前提の順序を守る**。後の STEP でしか説明しない概念を先に使わない（例：`HttpOnly` は XSS を、`SameSite` は CSRF を説明した後に置く）。既存記事をこの形に書き直すときは、**節の順序組み替えが変更の本体になることが多い**
- 各ステップで**1つの疑問を解いて、次の疑問を作る**。ステップ間が「そして次は」でつながっているだけなら積み上がっていない

#### 分量

前節の「本文1500文字程度・図2〜3点」は**適用しない**。この形式の目安は:

- 本文 4000〜6000文字、**5〜7図**、確認問題5〜6個
- ファイルサイズは 40〜70KB に収まる（日本語 UTF-8 は1文字3バイトなので、この数字は見た目より小さい）。超えたら図か節を削る

#### 見た目

CSS はリファレンス実装からそのままコピーする（`.rm` / `.rmbox` / `.quiz` / `figure` / `.note` / `blockquote` / `.tw`）。色変数・ダーク対応・inline SVG のルールは前節と同じ。

### セキュリティ記事での追加視点

セキュリティ系の記事を書くときは、以下の視点を意識する。

**「そのアクションのトリガーは何か？」を常に問う**

例：「Athena でログを調査したい」のトリガーは現実には侵害後の後追い調査。それを正直に書いた上で「だから侵害前にやっておくべきことは何か」に繋げる。ツールの説明ではなく、**いつ・なぜそれが必要になるか**から入る。

**提案者としての言語化を添える**

技術的な正しさだけでなく、ビジネス側に伝わる言い方も添える。

| 技術的な言い方 | ビジネス側に刺さる言い方 |
|---|---|
| CloudTrail を有効化する | 「誰が何をしたか」の記録がないと、インシデント時に原因調査も証拠収集もできない |
| GuardDuty を有効化する | 社内リソースへの不正アクセスを24時間監視する仕組みを月数万円で入れられる |

**用途が決まっていないツールを入れる提案はしない**

「早めに入れておけばログが溜まる」は根拠にならない。何に使うかが決まってから導入を提案する（シェルフウェア問題）。

## エージェントの記憶・メモ運用

- 会話をまたいで残すべき情報は、ツール固有のユーザーメモリではなくリポジトリ内のファイルに残す
- 全エージェントに共通する作業ルール・判断軸・既存コンテンツ情報はこの `AGENTS.md` に追記する
- 特定ツールだけに必要な注意は、そのツール向けファイル（例: `CLAUDE.md`）に最小限だけ書く
- 追記する内容は、次回以降も具体的に役立つ情報に限る
  - 既存コンテンツの状況（何がどこにあるかの1行のみ。記事の要約・背景は書かない）
  - ツールの既知バグや運用上のハマりポイント
  - ユーザーの好みや判断軸（記事スタイル・提案の視点等）
  - 繰り返し出てくる質問への定番回答

## やらないこと

- コードの実行環境やビルドの設定（このリポジトリにはない）
- 英語で書く必要はない
- 過度な装飾やフォーマット統一の強制

## ユーザーの好み・判断軸

- **資格コンテンツの置き場所**：`Certifications/` のような横断バケツは作らない。試験範囲がそのままトピックになるもの（`IPA/`）はトップレベル、特定トピックの資格はそのトピック配下に資格名のディレクトリを置く（`AI and Machine Learning/生成AIパスポート/`）
- **日本語話者のみが触る前提のリポジトリ設計では日本語を優先**：ADR のステータス等、慣習的に英語で書かれる定型語も日本語（有効/失効）にする。翻訳レイヤーを挟まない
- **AI 開発フローの検討は単一アカウント前提を好む**：マルチアカウント分離・SCP 等の組織側整備に踏み込まず、単一アカウントで完結する形を優先。AI は AWS に接続せず PR 作成まで、マージ・apply 以降は人間、という分担が基本線
- **通知設計は最小主義**：人間のチャンネルに流すのは「対応必須の新規検出」と「意図したリマインド」だけ。定期サマリ・ハートビート・カテゴリ外の情報は流さず、パイプラインの死活確認は CloudWatch 等の機械側に分離する
- **アーキテクチャ検討では敵対的セルフレビューを求める**：構成要素ごとに「本当に要るか」を問い、削れるものは削る方向で詰める（例：TrustedAdvisor 通知でイベント駆動レーン・週次サマリを廃止した経緯）

## ユーザーの立場・学習スタンス

ユーザーは **AWS セキュリティ DevOps エンジニア**。本業の専門領域はクラウドセキュリティだが、隣接領域（量子コンピュータ・AI・新興技術など）も**「専門家レベルではないが、知らないと話についていけない」程度には押さえておきたい**というスタンス。

このため、新興技術トピックを学ぶ際は以下を意識する：

- **深く広くではなく、浅く広く** の学習リソースを優先して提案する（数十時間の本格コースより、概念把握+業務接点が分かる短めの教材）
- **セキュリティ業務との接点を常に添える**。例：量子コンピュータなら耐量子暗号（PQC）・現行暗号への影響・AWS の PQC 対応状況など、本業に効く切り口を必ずセットで示す
- 「教養として知っておく」と「業務で使う」の境界を意識して、どちらの目的の学習かを確認してから提案する
