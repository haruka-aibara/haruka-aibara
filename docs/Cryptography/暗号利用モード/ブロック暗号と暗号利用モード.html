ブロック暗号と暗号利用モード — AES-256-CBC の後半は何か

アルゴリズムを決めたあとに、もう一段の選択が残っている。

何が問題なのか

「暗号は AES を使う」と決めても、設定ファイルやライブラリでは AES-256-CBC AES-128-GCM のような文字列を書かされる。AES と 256 は分かるとして、最後の 3〜4 文字は何を選んでいるのか。ここが分からないままコピペすると、AES を使っているのに中身が推測できる状態を作ってしまうことがある。

ブロック暗号は「決まった長さの箱」1個ぶんしか暗号化できない

AES や DES のようなブロック暗号は、固定長のデータを同じ長さのデータに変換する装置でしかない。AES なら 16 バイト入れて 16 バイト出てくる。それだけ。実際に暗号化したいファイルや通信は 16 バイトぴったりではないので、どう切り分けて、切ったブロックをどう繋ぐかを別に決める必要がある。この決めごとが暗号利用モード（block cipher mode of operation）。

モードの違いは「隣のブロックの影響を受けるか」

代表的な 3 つを並べると、違いは一目で分かる。

モード性質いま選ぶか
ECBブロックごとに独立して暗号化選ばない
CBC前の暗号文と XOR してから暗号化。IV が必要既存システムで見る。新規なら避ける
OFB鍵ストリームを作って XOR。パディング不要新規なら CTR を使う
CTRカウンタから鍵ストリームを作る。並列処理できる可
GCMCTR に改ざん検知を統合（AEAD）これを選ぶ

ECB / CBC / OFB は「暗号化しかしない」

これら 3 つが守るのは中身の秘密だけで、途中で書き換えられたことは検知できない。復号は成功してしまうので、アプリ側は改ざんされた平文をそのまま受け取る。実運用ではこれが事故になるため、いまは暗号化と改ざん検知を 1 つにまとめた AEAD（AES-GCM、ChaCha20-Poly1305）を使う。ECB / CBC / OFB を学ぶのは、既存システムの設定を読んだり、上のような古い方式が残っている理由を判断したりするため。
