ECB モード — 一番素直に書くと、これになってしまう

「AES で暗号化した」のに中身が読める、が起きる理由。

何が問題なのか

自前で暗号化を書くとき、素直に考えると「データをブロックに切って、順番に暗号化する」という実装になる。これが ECB モード（Electronic CodeBook、電子符号表）。ライブラリによっては指定を省略するとこれが選ばれる（Java の Cipher.getInstance("AES") は AES/ECB/PKCS5Padding）。つまり、悪意なく、知らないうちに ECB になる。

そして ECB は、AES のような強い暗号を使っていても平文の構造を暗号文に残す。

同じ平文ブロックは、必ず同じ暗号文ブロックになる

鍵が同じなら、ブロック暗号は「同じ入力 → 同じ出力」という決まった対応表として振る舞う。ECB はブロックを 1 つずつ独立にこの表に通すだけなので、平文に繰り返しがあれば、暗号文にもまったく同じ位置に繰り返しが現れる。

ブロックの並べ替えにも気づけない

ブロックが独立しているということは、暗号文のブロックを入れ替えたり、別のところからコピーしてきて貼っても、復号は成功するということでもある。「振込先＝A、金額＝1000」という電文の該当ブロックを、過去に観測した別の電文のブロックと差し替える、といった改ざんが成立する。復号側は正常な平文を得るので、何も検知できない。

ECB は選ばない。指定を省略しない。

ECB が正当化できるのは「平文が 1 ブロック以下で、かつ完全にランダムな値」（鍵そのものの暗号化など）くらい。実務では常に明示的にモードを書くのが対策になる。AES とだけ書かない、AES/GCM/NoPadding のようにモードまで指定する。既存コードのレビューでは、モード指定のない暗号化 API 呼び出しを探すのが手っ取り早い。

ECB の「同じ平文が同じ暗号文になる」問題を、前のブロックを混ぜることで消したのが CBC モード。モード全体の位置づけは ブロック暗号と暗号利用モード にまとめた。
