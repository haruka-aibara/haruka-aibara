カミンスキーアタックと DNSSEC

DNS の応答が本物かどうかを、DNS 自身は確かめられない。その穴と、その穴を塞ぐ仕組み。

何が問題なのか

DNS キャッシュに嘘の情報が載ると、そのリゾルバを使う利用者全員が偽サイトに誘導される。利用者は正しいドメイン名を入力していて、フィッシングメールも踏んでいない。それでも行き先が違う。

なぜ載せられるのか。DNS は UDP の 1 往復で完結する設計で、応答が本物であることを保証しているのはトランザクション ID（16 ビット）と宛先ポートが一致することだけ。署名も暗号化もない。攻撃者が本物の権威サーバより先に、この 2 つを当てた偽応答を届けられれば、リゾルバはそれを信じてキャッシュする。

従来のキャッシュポイズニングと、その歯止め

カミンスキーアタック（2008 年、CVE-2008-1447）

Dan Kaminsky が示したのは、この TTL の歯止めを無効化する方法だった。新しい実装バグではなく、DNS プロトコルの設計そのものに対する攻撃なので、特定のソフトだけの問題では済まなかった。

当座の対策：ソースポートのランダム化

2008 年に各実装が一斉に出したパッチの中身は、問い合わせの送信元ポートをランダムにすることだった。攻撃者が当てるべき組み合わせが TXID の 16 ビットだけから、TXID ＋ ポートの約 32 ビットに広がる。総当たりのコストが数万倍になる。

ただしこれは確率を下げただけ

推測を難しくしているのであって、「偽応答を見分けている」わけではない。時間と帯域をかければ今でも成立しうるし、実際にその後も派生手法が報告されている。応答が本物かを検証する仕組みが別に要る——それが DNSSEC。

DNSSEC — 応答に署名して、ルートまで遡って検証する

DNS の応答に電子署名を付け、受け取った側（リゾルバ）が検証する仕組み。秘密鍵を持たない攻撃者は正しい署名を作れないので、偽応答は検証で落ちる。

DNSSEC が保証しないこと

ここを取り違えると、入れたのに期待した効果が出ない。

保証する保証しない
応答が正規のゾーン管理者から出たものであること（出所の認証）通信内容の秘匿。クエリも応答も平文のまま。「誰が何を引いたか」は経路上から見える。暗号化したいなら DoH / DoT という別の仕組み
途中で改ざんされていないこと（完全性）ドメインの持ち主が善良であること。フィッシングサイトも自分のドメインに DNSSEC を設定できる
「そのレコードは存在しない」という応答の正しさ（NSEC / NSEC3）可用性。むしろ署名の期限切れや鍵の不整合で引けなくなる事故がある

NSEC は「存在しないこと」を証明するために隣接する名前を返す仕組みだが、これを順に辿るとゾーンの中身が全部列挙できてしまう（ゾーンウォーキング）。名前をハッシュ化して返す NSEC3 はその対策。

運用で押さえること

  • 署名には有効期限がある。切れると、そのドメインが丸ごと引けなくなる。鍵の更新（ロールオーバー）と再署名は継続的な運用作業になる
  • 自前で運用しないほうが安全なことが多い。Amazon Route 53 などのマネージド DNS は署名と鍵管理を引き受けてくれる
  • 権威側で署名しても、リゾルバ側が検証しなければ意味がない。両側が揃って初めて効く。Google Public DNS や Cloudflare の 1.1.1.1 は検証する

提案するときの言い方——「DNSSEC はフィッシング対策ではありません。正規のドメイン宛のアクセスを、経路上で別の場所に付け替えられないための仕組みです。効くのは、利用者が正しいドメインを入力しているのに違うサーバに繋がる、という一番気づきにくい攻撃に対してです」。
