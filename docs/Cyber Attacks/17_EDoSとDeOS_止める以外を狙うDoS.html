EDoS と DeOS — 止める以外を狙う DoS

サービスは動いているのに攻撃が成立している状態と、止まったまま二度と戻らない状態。

何が問題なのか

DoS 対策の議論は、たいてい「サービスを止めさせない」という前提で組み立てられる。ところが目的が違う攻撃が 2 つある。片方は止めずに金を払わせる、もう片方は止めたうえで戻れなくする。どちらも「可用性を守る」という枠組みだけでは、検知にも復旧計画にも引っかからない。

EDoS — 落ちないことが攻撃になる

Economic Denial of Sustainability（経済的な持続不可能性）。

オンプレの時代、負荷が上限を超えればサービスは落ちた。クラウドではオートスケールが効いて落ちない——代わりに請求額が伸びる。可用性は 100% のまま、事業として続けられなくなる。

攻撃側から見れば手軽だ。サービスを落とすほどの規模はいらない。課金単位に効く操作を淡々と繰り返せばいい。

予算アラートは対策ではない。AWS Budgets の通知は「起きたことを知る」だけで、課金は止まらない。止めるための制御を別に置く必要がある。

  • 入口で減らす：CloudFront を前段に置く（オリジンへの到達自体を減らす）、AWS WAF のレートベースルール、Bot Control、フォームには CAPTCHA
  • 上限を持たせる：Lambda の予約済み同時実行数、API Gateway のスロットリング、SQS 経由での平準化
  • 気づける形にする：AWS Cost Anomaly Detection でコストの異常検知を可用性監視と同列に置く

設計時の問いは 1 つ——「認証なしで叩けて、叩くたびに課金が発生する経路はどれか」。ここに上限がなければ EDoS が成立する。

DeOS — 復旧させないことが目的

Destruction of Service。Cisco が 2017 年中期サイバーセキュリティレポートで提示した呼び方で、復旧手段そのものを破壊する攻撃を指す。

背景にあるのは同年の WannaCry と NotPetya（Nyetya）。特に NotPetya は身代金を要求する体裁をとりながら、実際には復号できない構造になっていた。金銭目的に見えて、目的は破壊だった。

DeOS への備えは、突き詰めると 1 つの質問に答えられるかどうか

「侵害された管理者権限で、バックアップまで消せるか？」——消せるなら、それはバックアップではなくコピーの一種でしかない。

よくある状態DeOS 想定での見直し
本番と同じ IAM 権限でスナップショットを削除できるAWS Backup の Vault Lock（コンプライアンスモード）で削除自体を不可能にする。S3 なら Object Lock
バックアップが本番と同一アカウント・同一リージョンにある別アカウント（できれば別リージョン）へコピー。アカウントを取られた時点で全損になる構成を避ける
復旧手順書はあるが、実行したことがない年 1 回でも実際に復元まで通す。試していない手順は「無い」と同じ

提案するときの言い方——「バックアップを取っているかではなく、攻撃者が管理者権限を取ったあとでもバックアップが残るかで見てください。ここの差が、数時間の停止で済むか事業データを全部失うかの分かれ目です」。
