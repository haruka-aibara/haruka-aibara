POODLE 攻撃 — 「復号できたか」の返事だけで Cookie を盗む

鍵は破らない。サーバが返す成功／失敗を数千回観測するだけ。

何が問題なのか

2014 年に公表された POODLE（Padding Oracle On Downgraded Legacy Encryption）は、SSL 3.0 で保護された通信から、セッション Cookie を 1 バイトずつ復元する攻撃。名前のとおり 2 つの部品でできている。

  • 通信を SSL 3.0 に落とす（バージョンロールバック攻撃）
  • SSL 3.0 の CBC パディングの緩さを突く（パディングオラクル攻撃）

SSL 3.0 は 1996 年の規格で、2014 年当時すでに誰も積極的に使っていなかった。それでも影響が大きかったのは、互換性のために有効なまま残されていたから。使っていない機能が有効なだけで攻撃が成立する、という典型例になっている。

SSL 3.0 のパディングは中身が検証されない

CBC モードではブロック長に足りないぶんを詰め物で埋める。TLS 1.0 以降は詰め物の中身にも決まりがあり、復号側が検証できる。ところが SSL 3.0 は最後の 1 バイト（詰め物の長さ）以外は「任意の値でよい」と定めた。つまり復号側は、長さバイト以外を一切見ない。

オラクルとは「答えを教えてくれる存在」

この攻撃で攻撃者が得ている情報は「復号に成功したか、しなかったか」の 1 ビットだけ。鍵も平文も返ってこない。それでも、暗号文を自分で作って何度も試せる状況では、この 1 ビットの積み重ねが平文の復元に繋がる。復号の成否を外に見せる仕組みは、それ自体が攻撃の材料になる——これがパディングオラクルという考え方で、POODLE 以外にも Lucky 13 など同じ構図の攻撃がある。

TLS でも成立した実装があった（POODLE against TLS）

TLS 1.0 以降はパディングの中身も検証すると仕様で決まっている。ところが一部のロードバランサや TLS アクセラレータがその検証を実装していなかったため、TLS 1.2 の通信でも同じ攻撃が成立した（CVE-2014-8730 ほか）。「SSL 3.0 を無効にしたから安全」で終わらせず、機器側のパッチ適用まで確認する必要があった事例。

どうするか

  • SSL 3.0 を無効にする。これが唯一の根本対策で、修正パッチのようなものは存在しない。プロトコル仕様そのものの欠陥なので、直す方法がない。
  • TLS_FALLBACK_SCSV に対応する。互換性の都合で SSL 3.0 を残さざるを得ない場合、少なくとも「ロールバックさせられて落ちた」状態を検知して拒否できるようにする。
  • CBC 系の暗号スイートから AEAD に移行する。AES-GCM や ChaCha20-Poly1305 は改ざんを検知してから復号するため、パディングオラクルの構図自体が成り立たない。
