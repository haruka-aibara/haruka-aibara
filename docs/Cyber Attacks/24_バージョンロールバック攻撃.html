バージョンロールバック攻撃 — 通信を邪魔するだけで、古い規格に落ちる

攻撃者は暗号を破らない。ハンドシェイクを失敗させるだけでいい。

何が問題なのか

クライアントもサーバも TLS 1.2 に対応している。それなのに、実際の通信が SSL 3.0 で確立してしまうことがあった。原因は暗号の欠陥ではなく、ブラウザが良かれと思って実装していた再試行の挙動にある。

当時、TLS の新しいバージョンを提示すると応答を返せない古いサーバや中間機器が現実に存在した。そのままでは「繋がらないサイト」が生まれてしまう。そこでブラウザは、ハンドシェイクが失敗したら、バージョンを 1 つ下げて繋ぎ直すという救済策を入れた。仕様にはない、互換性のための実装上の親切だった。

攻撃者から見れば、これは「ハンドシェイクを壊せば、相手が勝手に弱くなる」という意味になる。

落とした先で何をするか

SSL 3.0 に落とすこと自体が目的ではない。落とした先には、そのバージョン固有の弱点がある。SSL 3.0 の CBC パディングの検証が甘いことを突いて実際に平文を復元したのが POODLE で、ロールバックはその前提条件を作る手順だった。

どう塞いだか

  • TLS_FALLBACK_SCSV（RFC 7507） — 再試行であることを、暗号スイート一覧に紛れ込ませた特別な印としてサーバに伝える。サーバは「自分はもっと高いバージョンに対応しているのに、再試行として低いバージョンで来た」と気づけるので、その接続を拒否できる。再試行という挙動を消すのではなく、再試行だと申告させるという解き方。
  • TLS 1.3 のダウングレード検知 — サーバは ServerHello に含めるランダム値の末尾 8 バイトに、決められた印を埋め込む。クライアントはそれを見て「本当は 1.3 が使えるのに落とされた」と判定できる。ランダム値はハンドシェイクの署名対象なので、中間者は書き換えられない。
  • そもそも古いバージョンを無効化する — 落とす先がなければ成立しない。SSL 3.0 / TLS 1.0 / TLS 1.1 はすでに非推奨として無効化するのが標準。ブラウザ側の互換フォールバックも廃止された。

この構図はプロトコルの世界に繰り返し出てくる

「古い相手とも繋がるように」という互換性のための救済策が、攻撃者にとっての降格スイッチになる。HTTPS から HTTP へのダウングレードや、メールの STARTTLS を剥がす攻撃も同じ形。新しい規格を導入するときは、古いほうへ戻る経路をいつ閉じるかを設計に含めておく、というのが教訓になる。
