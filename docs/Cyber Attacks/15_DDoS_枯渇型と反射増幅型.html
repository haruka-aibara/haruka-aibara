DDoS の手法 — 枯渇型と反射増幅型

1人の攻撃者が、なぜ自分の回線幅を超えるトラフィックを出せるのか。

何が問題なのか

「サービスが落ちた。でも CPU もメモリも余っていた」——DoS 対策の入口でつまずくのはここ。DoS は「サーバを重くする攻撃」ではなく、有限なものを先に使い切る攻撃。何を使い切られたのかで、打つ手がまったく変わる。

接続テーブルを枯らす — TCP SYN Flood

TCP はデータを流す前に 3 ウェイハンドシェイクをする。サーバは SYN を受け取った時点で「途中まで確立した接続」を覚えておく必要があり、その保持領域（SYN バックログ）は有限。

攻撃者は SYN を送るだけ送って、最後の ACK を返さない。しかも送信元 IP を詐称するので、サーバの SYN/ACK は存在しない相手に飛び、返事は永遠に来ない。半開き接続がタイムアウトするまでの間にバックログが埋まり、正規ユーザの SYN が捨てられる。

対策は SYN Cookie。接続状態を保存する代わりに、必要な情報をハッシュ化して SYN/ACK のシーケンス番号に埋め込んで返し、ACK が返ってきた時点で初めて接続を作る。覚えないので、埋まりようがないという発想。Linux では net.ipv4.tcp_syncookies が既定で有効。CDN やロードバランサ（CloudFront、ALB/NLB など）を前段に置けば、そこで吸収される。

帯域を埋める — 反射と増幅

回線を埋めるには、攻撃者が自分の回線幅より大きなトラフィックを作らなければならない。そのための道具が反射（reflection）と増幅（amplification）だ。

  • 反射：送信元 IP を被害者に詐称してリクエストを投げる。応答は被害者に届く。攻撃元が隠れ、被害者から見ると無関係な第三者から攻撃されているように見える。
  • 増幅：そのとき要求より応答が大きいサービスを選ぶ。攻撃者の 1 Gbps が数百 Gbps になる。

Smurf — 反射増幅の原型

ICMP エコー要求の送信元を被害者に詐称し、サブネットのブロードキャストアドレス宛に送る。そのセグメントの全ホストが一斉に被害者へ応答を返す。ホストが 100 台いれば 100 倍。

今はほぼ成立しない。ルータがディレクテッドブロードキャストを既定で転送しなくなった（RFC 2644）ため。ただし「送信元を偽って、第三者に返させる」というアイデアはそのまま現在の攻撃に受け継がれている。

DRDoS — 同じ発想を一般化したもの

Distributed Reflection Denial of Service。Smurf の ICMP／ブロードキャスト依存を捨て、インターネット上に散らばった無数の UDP サービスを踏み台にする形に一般化したもの。反射増幅型 DDoS の総称としてこの名前が使われる。

NTP リフレクション — 増幅率が桁違いだった例

NTP の monlist は「直近に通信したクライアントを最大 600 件返す」管理用コマンド。要求は数十バイト、応答は数千バイトになる。増幅率 556.9 倍。2014 年に大規模攻撃が続発した（CVE-2013-5211）。対策は ntpd 4.2.7p26 以降への更新、または monlist の無効化。

踏み台にされない側の責任

反射増幅型は、受ける側の対策だけでは減らない

被害者側でできるのは「大量に届いたものを捌く」ことだけで、攻撃の総量は踏み台が何台あるかで決まる。世界中のオープンなサーバが減らない限り、この攻撃はなくならない。

  • BCP 38（Ingress Filtering）：自ネットワークから出ていくパケットの送信元 IP が自分の割当範囲かを検証し、外れていれば落とす。詐称パケットを発生源で止める。
  • UDP サービスを無防備に公開しない：DNS リゾルバ、NTP、memcached、SSDP。セキュリティグループ／ファイアウォールで送信元を絞る。
  • 帯域を埋める攻撃は自社設備で受け止めない：回線が埋まる攻撃に対して、回線の先にある機器の設定は無力。CDN や DDoS 緩和サービス（AWS Shield Advanced、Cloudflare など）で自社回線の手前で吸収する。

提案するときの言い方——「これはうちが攻撃されるかの話ではなく、うちが他社への攻撃の発射台にされるかの話です。オープンな NTP や DNS を放置すると、加害側として名前が出ます」。
