SSL/TLS ダウングレード攻撃 — 強い暗号に対応していても意味がない

「どの暗号を使うか」の相談は、暗号がかかる前に平文で行われる。

何が問題なのか

サーバもブラウザも最新の TLS に対応していて、強い暗号スイートを持っている。それでも実際に使われる暗号は、その場のネゴシエーションで決まる。そしてこのネゴシエーションは、まだ暗号がかかっていない状態で交わされる。

ここに中間者が入り、「弱い暗号にしか対応していないふり」をさせるのがダウングレード攻撃。サーバの設定に古い暗号スイートが 1 つ残っているだけで、最新のブラウザを使っていても、その弱い暗号で通信させられる。

やっていることは、選択肢の削除

実際に起きた事例

名称落とし先背景
FREAK（2015）512 ビットの EXPORT 用 RSA1990 年代の米国輸出規制で作られた弱い暗号スイートが、20 年後も実装に残っていた
Logjam（2015）512 ビットの DH 鍵交換広く共有された素数が使われていたため、事前計算で効率よく破れた
DROWN（2016）同じ鍵を使う SSLv2 サーバ別ポートで動く古いサーバが、TLS の通信を解読する材料になった

共通しているのは、「もう使っていないつもりの古い設定が有効なまま残っていた」こと。攻撃の新しさではなく、消し忘れが原因になっている。

どうするか

  • サーバ側で許可する暗号スイートを絞る。攻撃者が選べるのはサーバが提示できるものの中だけなので、弱いものを消せば選択肢がなくなる。EXPORT 系・RC4・DES/3DES・匿名 DH は無効にする。
  • TLS 1.3 を有効にする。TLS 1.3 は仕様のレベルで弱い暗号スイートを削除し、鍵交換も前方秘匿性のあるものだけに限定した。「設定で切る」のではなく「選択肢が存在しない」状態になる。
  • 設定を外から検証する。SSL Labs のようなツールで、実際に何が提示されているかを見る。設定ファイルの意図ではなく、サーバが実際に応答する内容を確認する。

暗号スイートではなく、バージョンを落とす攻撃もある

この記事は「どのアルゴリズムを使うか」を弱いものにする攻撃。これとは別に、TLS そのもののバージョン（TLS 1.2 → SSL 3.0）を落とさせる手口があり、そちらは バージョンロールバック攻撃。落とした先の SSL 3.0 を実際に解読するところまでやったのが POODLE。
