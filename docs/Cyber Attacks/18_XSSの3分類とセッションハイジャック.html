XSS の 3 分類とセッションハイジャック

「入力値をエスケープしましょう」で終わる説明では、なぜそこまで重要なのかが伝わらない。経路を最後まで追う。

何が問題なのか

XSS（クロスサイトスクリプティング）は、攻撃者の書いた JavaScript を、被害者のブラウザ上で、被害者が見ているサイトのオリジンとして実行させる脆弱性。「オリジンとして」の部分が効く——同一オリジンポリシーの内側に入り込むので、そのサイトの Cookie も localStorage も画面の中身も、全部読める。

攻撃者のゴールはたいていセッションの乗っ取り。パスワードを盗まなくても、ログイン済みという状態そのものを持っていける。

セッションハイジャックまでの流れ

HttpOnly を付けても XSS が無害になるわけではない

Cookie が読めなくても、スクリプトが動いている時点で被害者の権限で任意の操作を代行できる。パスワード変更、送金、メールアドレスの書き換え——Cookie を持ち出さずその場で実行するほうが、今はむしろ主流。HttpOnly は被害を狭める緩和策であって、根本対策は 1 の出力エスケープ。

Web ビーコン — 情報を外に運ぶ経路

1×1 の透明画像などを読み込ませ、そのリクエストそのものを情報伝達に使う仕組み。もとはメールの開封計測や Web 解析のための正規技術で、トラッキングピクセルとも呼ばれる。

3 つの分類 — 悪意のスクリプトがどこに存在するか

XSS は攻撃の効果ではなく、スクリプトがどの経路でブラウザに届くかで 3 つに分かれる。分ける実益は、対策する場所が変わる点にある。

種類典型的な入口直す場所
Reflected検索キーワードの再表示、エラーメッセージ、リダイレクト先の表示サーバ側の出力時エスケープ。テンプレートエンジンの自動エスケープを切らない
Stored掲示板・コメント・プロフィール。管理画面のログ表示も狙われる（管理者権限を取れる）
DOM Basedlocation.hash や location.search を JS が DOM に流し込む箇所、SPA のルーティングサーバ側では直せない。危険なシンクを使わない

DOM Based で言う「危険なシンク」は innerHTML / outerHTML / document.write / insertAdjacentHTML / eval あたり。文字列として表示したいだけなら textContent を使う。React や Vue の標準のバインディングは自動でエスケープするので、dangerouslySetInnerHTML や v-html を使わない限りは踏みにくい。

// 危険：URL の中身がそのまま HTML として解釈される
el.innerHTML = decodeURIComponent(location.hash.slice(1));

// 安全：文字列としてしか扱われない
el.textContent = decodeURIComponent(location.hash.slice(1));

最初に手を入れるなら

  • 出力エスケープ：HTML 本文・属性値・JavaScript 内・URL でエスケープの仕方が違う。フレームワークの機構に任せ、自前で書かない
  • セッション Cookie に HttpOnly と Secure と SameSite：3 つセットで付ける。設定 1 行で被害の幅が変わる
  • CSP：外部送信先とスクリプト実行元を制限する。まず Content-Security-Policy-Report-Only で流して、壊れないことを確認してから強制に切り替える
