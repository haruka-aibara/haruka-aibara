# スクラムマスターのセルフチェックリスト

スクラムイベントは一通り回っている。でも「うちのスクラム、これでいいの？」と聞かれると答えに詰まる。改善したい気持ちはあるが、どこから手をつけるべきか、そして**どこまでやれば十分なのか**が見えない——そういうときに定点観測として使うチェックリスト。

ゴール設定はこう：**全項目にチェックがつく状態 = チームが自己管理でき、改善が自走している状態**。そこまで行ったら、現実的にこれ以上のスクラムはほぼない。逆に言えば、チェックが外れている項目が次の打ち手になる。

---

## 使い方

- **一度に全部見ない**。月に1回、またはレトロスペクティブの後に1セクションずつ見るくらいの粒度でいい
- **チェックは「直近3スプリント連続でできている」でつける**。1回できただけの項目にチェックをつけると、リストが「できたことリスト」になって改善に使えなくなる
- チェックが外れた項目は「戻った」と正直に外す。人の入れ替わり・プロダクトのフェーズ変化でチェックは普通に外れる。それを検知するためのリスト

---

## 1. 土台：スクラムの構造が成立しているか

イベントの改善より先に、そもそもの構造を確認する。ここが崩れていると、イベントをいくら磨いても効果が出ない。

- [ ] スプリントは1か月以内の固定長で、期間を都度変えていない
- [ ] プロダクトゴールが存在し、チームの誰に聞いても同じ答えが返ってくる
- [ ] 毎スプリントにスプリントゴールがあり、「チケットの寄せ集め」になっていない
- [ ] Definition of Done が明文化され、全員が同じものを参照している
- [ ] Definition of Done が定期的に見直され、厳しくなる方向に更新されている
- [ ] プロダクトバックログは PO が一元管理し、優先順位が明確に並んでいる
- [ ] チームのワーキングアグリーメント（コアタイム・連絡手段・レビューの期待値など）が明文化されている

## 2. イベント：タイムボックスと中身

タイムボックスの原則（スクラムガイド 2020）：

| イベント | 1か月スプリントの上限 | 2週間スプリントの目安 |
|---|---|---|
| スプリントプランニング | 8時間 | 4時間 |
| デイリースクラム | 15分（スプリント長に関係なく固定） | 15分 |
| スプリントレビュー | 4時間 | 2時間 |
| スプリントレトロスペクティブ | 3時間 | 1.5時間 |

タイムボックスを守れているかはチェックの入口でしかない。各イベントが**本来の目的を果たしているか**までがチェック対象。

### スプリントプランニング

- [ ] タイムボックス内に終わっている（毎回延長していない）
- [ ] Why（なぜこのスプリントに価値があるか）→ What（何をやるか）→ How（どう進めるか）の3トピックが揃っている
- [ ] 休暇・割り込み対応・リファインメントを考慮したキャパシティで計画している
- [ ] 前スプリントの未完了アイテムが「自動で繰り越し」されず、再度優先順位を判断している
- [ ] プランニング終了時点で、全員がスプリントゴールを自分の言葉で説明できる

### デイリースクラム

- [ ] 毎日同じ時間・場所で開催し、15分以内に終わっている
- [ ] 進捗報告会ではなく「スプリントゴール達成のための再計画」の場になっている
- [ ] メンバー同士が話している（スクラムマスターや特定個人への報告になっていない）
- [ ] 障害（ブロッカー）が挙がったら、その日のうちにフォローが動いている
- [ ] スクラムマスターが不在でも同じ品質で成立する

### プロダクトバックログリファインメント

公式イベントではないが、プランニングの質はここで決まる。

- [ ] 次スプリント分の「準備完了（Ready）」なアイテムが常にストックされている
- [ ] リファインメントに使う時間がキャパシティの1割前後に収まっている（やりすぎていない）
- [ ] 見積もりが全員参加で行われ、見積もりのズレをきっかけに認識合わせが起きている
- [ ] 大きすぎるアイテムが、スプリントに入る前に分割されている

### スプリントレビュー

- [ ] タイムボックス内に終わっている
- [ ] 動くインクリメントをデモしている（スライドの読み上げになっていない）
- [ ] ステークホルダーが実際に参加し、フィードバックが出ている
- [ ] 出たフィードバックがプロダクトバックログに反映されている
- [ ] 承認会・進捗報告会ではなく、「次に何を作るか」を検討する場になっている

### スプリントレトロスペクティブ

- [ ] 毎スプリント実施している（忙しいときにスキップされていない）
- [ ] タイムボックス内に終わっている
- [ ] 全員が発言している（声の大きい人のターンになっていない）
- [ ] 個人の責任追及ではなく、プロセスと構造の話をしている
- [ ] フォーマットがマンネリ化していない（同じ手法の惰性リピートになったら変えている）
- [ ] 具体的なアクションが1〜2個に絞られ、担当者と確認タイミングが決まっている

## 3. 改善ループ：レトロの学びが消えていないか

レトロスペクティブをやること自体より、**そこで出た学びがどこに行くか**のほうが重要。ここが機能していないチームは「毎回同じ話をするレトロ」になる。

- [ ] レトロで決めたアクションが、次スプリントのバックログまたはボードに載っている
- [ ] 次のレトロの冒頭で、前回アクションの結果を必ず確認している
- [ ] 改善の実験には「何をもって成功とするか」が事前に決まっている
- [ ] 学び（うまくいった実験も、いかなかった実験も）がチームの誰でも見られる場所に記録されている
- [ ] その記録が新メンバーのオンボーディングで実際に参照されている
- [ ] 同じ問題が3回以上レトロに出てきたら、個別対処でなく構造要因（組織・体制・技術的負債）として扱っている
- [ ] チームを越えて役立つ学びが、組織（他チーム・ギルド・全社ドキュメント）に共有されている

## 4. 計測：改善が数字で語れるか

「良くなった気がする」で止まると、改善は続かない。

- [ ] ベロシティ以外のフロー指標（サイクルタイム・スループットなど）を見ている
- [ ] メトリクスが改善のために使われ、個人評価には使われていない（使われ始めたら数字は歪む）
- [ ] DORA メトリクス（デプロイ頻度・リードタイム・変更失敗率・MTTR）の少なくとも一部を追っている
- [ ] 改善アクションの前後で、指標がどう変わったかを確認している
- [ ] チームの健全性（モチベーション・心理的安全性）を定期的に測る仕組みがある（Squad Health Check など）

## 5. チーム：自己管理と心理的安全性

- [ ] 悪いニュース（遅延・障害・ミス）が早い段階で共有される
- [ ] 意見の対立が表面化し、建設的に処理されている（対立ゼロは「議論していない」兆候として扱う）
- [ ] 特定の人にしかできない作業が特定され、減らす取り組み（ペア作業・ドキュメント化）が動いている
- [ ] 改善の提案がスクラムマスター以外のメンバーからも出てくる
- [ ] チームが自分たちで作業の割り当てを決めている（誰かがアサインしていない）

## 6. 組織：チームの外側

チーム内が完璧でも、外側の障害を放置していたらスクラムマスターの仕事は半分しかできていない。

- [ ] インペディメント（障害）リストを管理し、状態を可視化している
- [ ] チーム内で解決できない障害を、組織の適切なレイヤーにエスカレーションしている
- [ ] スプリント途中の割り込み依頼をどう扱うか、ステークホルダーと合意したルールがある
- [ ] PO が優先順位を決める権限と、バックログに向き合う時間を実際に持っている（PO の代理判断をスクラムマスターがしていない）
- [ ] 他チーム・他部門との依存関係が可視化され、プランニング時点で考慮されている

## 7. スクラムマスター自身

スクラムマスターの最終目標は「自分がいなくてもチームが回る状態」を作ること。自分自身も定点観測の対象に入れる。

- [ ] 自分が不在でもイベントが同じ品質で成立する
- [ ] ティーチング（教える）・ファシリテーション（引き出す）・コーチング（問いかける）・何もしない（見守る）を、チームの成熟度に合わせて使い分けている
- [ ] 自分の仕事ぶりについて、チームから定期的にフィードバックをもらっている
- [ ] 社外・チーム外からのインプット（書籍・コミュニティ・他のスクラムマスターとの交流）を続けている

---

## 全部にチェックがついたら

それは「チームが自己管理でき、改善が自走し、学びが組織に還元されている」状態。スクラムとしてこれ以上を目指すのは現実的に厳しい——というより、目指す必要がない。スクラムマスターの介在価値が薄れた状態こそが成功なので、次のチーム・より難しい課題に軸足を移すタイミング。

ただし現実には、メンバーの入れ替わり・プロダクトのフェーズ変化・組織再編でチェックは外れていく。だからこのリストは「合格判定」ではなく、**外れた項目を検知して次の打ち手を決めるための定点観測**として使い続ける。
