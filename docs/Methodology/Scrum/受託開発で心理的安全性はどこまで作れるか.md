# 受託開発で心理的安全性はどこまで作れるか

スクラムの本を読むと、成熟したチームの姿として「弱さをさらけ出せる信頼」「感情も含めて率直に話せる場」が描かれる。しかし受託開発（SIer）の現場でこれを目指そうとすると、すぐ壁に当たる。顧客と受注者という上下関係の中で、開発側が「わかりません」「失敗しました」を気軽に口にできるわけがない——この違和感は正しい。ただし、半分は理論の読み込みすぎで、もう半分は受託の構造が本当に理論の前提を壊している。この記事はその切り分けをする。

## 理論が要求しているのは「顧客への感情開示」ではない

「弱さをさらけ出せる信頼（vulnerability-based trust）」の出典はレンシオーニの『あなたのチームは、機能してますか？』、心理的安全性の出典はエドモンドソンの研究（Google の Project Aristotle で広く知られた）だが、どちらも対象は**チーム内部**の話であって、顧客に対して感情を出せとは誰も言っていない。

スクラムのイベント設計自体がそうなっている。レトロスペクティブはチーム内輪の場、顧客と向き合う場はスプリントレビューと、開示の境界が最初から分かれている。だから「お客様の前で弱みを見せる」は、そもそもスクラム理論の要求ではない。

また、心理的安全性の定義は「対人リスクを取っても罰されないという信念」であって、感情の共有や仲良しクラブのことではない。本体は「それ、まずくないですか」と言えること。ここを取り違えると、目指すゴールが不必要に高くなる。

## それでも受託がきつい本当の理由

問題は、理論が想定する「チーム」の境界と、現実の契約の境界がねじれること。理論の前提はチーム全員の雇用主が同じであることだが、受託の現場では：

- **PO が顧客側にいる**。「チーム」の中に発注者・受注者の上下関係が走り、レトロとレビューの境界設計が最初から崩れている
- **プロパー＋BP（協力会社）の混成チーム**。同じデイリーに出ている人同士でも所属会社が違い、「わからない」「詰まっている」と言うこと自体が契約更新・単価査定のリスクになる
- **請負契約**では「弱みを見せる＝瑕疵の予兆」と受け取られかねず、防御的な報告が合理的行動になる

心理的安全性は「罰されないという信念」の問題だが、この構造では罰が**実在する**（契約が切られる）。信念の問題ではなく事実の問題なので、ファシリテーションや場づくりの工夫で解ける範囲を超えている。「うちのチームは心理的安全性が低い」と嘆く前に、それがスクラムマスターの力量の問題なのか構造の問題なのかを切り分けるべきで、後者ならスクラムマスターの努力不足ではない。

なおこれは日本固有の問題ではなく、欧米のコンサル・コントラクター文脈でも同じ緊張はある。ただ日本の多重下請け構造は「1つのチームに雇用主が3社いる」という状況を普通に作るので、程度としては最もきつい部類になる。

## 現実解は3段階

### 1. ゴールを下げる

感情の全開示ではなく、**作業上の弱さ**——わからない、詰まっている、この見積もりは自信がない——が言えるだけで、スクラムの実利（障害の早期発見、正直なベロシティ、遅延の早期共有）はほぼ回収できる。エドモンドソンの心理的安全性もここが本体で、感情面の開示はその先にあれば良い程度のもの。構造的に無理な満点を目指して消耗するより、実利が出る合格点を確実に取る。

### 2. 開示の境界を意図的に設計する

「誰に・何を・どこまで見せるか」を決めておく。たとえば：

- レトロスペクティブは開発側（受注側）だけで実施する
- 顧客への透明性は、レトロへの同席ではなくスプリントレビューと成果物で担保する
- 顧客側 PO がいる場合、PO に見せる情報（バックログ・進捗・リスク）と開発チーム内で処理する情報（個人の詰まり・チーム内の対立）を分ける

全員に全部オープンがアジャイルの理想形に見えるが、契約境界がある以上、境界設計はごまかしではなく運用である。むしろ境界を曖昧にしたまま「オープンにやろう」と言うほうが、メンバーに「どこまで言っていいのか」の判断を毎回押し付けることになり、結果として誰も何も言わなくなる。

### 3. 構造側を変えられるなら変える

請負より準委任・ラボ型契約のほうが「一緒に不確実性に向かう」建付けにしやすい。IPA のアジャイル開発版モデル契約も準委任を前提にしている。逆に言えば、請負一括の案件で心理的安全性を求めるのは構造的に無理筋で、そこは現場の努力ではなく契約の問題として提起すべき話。スクラムマスターにできるのは、この無理筋を「チームの雰囲気の問題」にすり替えず、構造の問題として言語化して上に上げることまで。

## スクラムマスターとしての観測ポイント

構造の限界を踏まえた上で、いまのチームがどこまで来ているかは次の順で見る。

1. 悪いニュース（遅延・障害・ミス）が早い段階で共有されるか——これが最低ラインかつ最大の実利
2. 「わからない」「自信がない」が見積もりやプランニングの場で出るか
3. 意見の対立が表面化するか（対立ゼロは「議論していない」兆候）
4. 感情面の開示——ここは構造が許す範囲でしか進まないので、1〜3 ができていないうちに目指さない

1〜3 は受託の構造下でも境界設計しだいで到達できる。4 だけが「相当きびしい」領域で、そこに未達でもチームとして失敗ではない。
