# スプリントレトロスペクティブのチェックリスト

タイムボックス：1か月スプリントで最大3時間（2週間なら1.5時間目安）。

- [ ] 毎スプリント実施している（忙しいときにスキップされていない）
- [ ] タイムボックス内に終わっている
- [ ] 全員が発言している（声の大きい人のターンになっていない）
- [ ] 個人の責任追及ではなく、プロセスと構造の話をしている
- [ ] フォーマットがマンネリ化していない（同じ手法の惰性リピートになったら変えている）
- [ ] プロダクトそのものへの評価・フィードバックはレビューで消化され、レトロに漏れ込んでいない
- [ ] 具体的なアクションが1〜2個に絞られ、担当者と確認タイミングが決まっている

レトロで決めたアクションのその後は[改善ループのチェックリスト](../ベストプラクティス/改善ループ.md)で見る。

## レトロで「プロダクトの話」が出たときの扱い方

スクラムの整理では、プロダクト（インクリメント）を検査する場はスプリントレビュー、レトロが検査するのはプロセス・相互作用・Definition of Done。だからレトロでプロダクトの出来の話が長く続くのは議題の置き場所としてはズレている。ただし「開発者はプロダクトの成果を喜ぶべきでない」という話ではない。2020年版スクラムガイドは PO も含めた一つのスクラムチームがプロダクトゴールに責任を持つ整理にしており、開発者が成果を自分ごととして喜ぶのはオーナーシップの現れとして歓迎すべきもの。成果に無関心なチームは、言われたものを作るだけのフィーチャーファクトリーに近づく。

実務での扱いは三段構え：

1. **問いを変換する**：プロダクトの話が出たら「その成果（または問題）を生んだ、私たちの働き方の要因は何か」と一段掘る。「顧客に好評だった」なら「早めにプロトタイプを見せた判断が効いた。次も再現するには？」とプロセスの話に着地させる
2. **変換できないなら退避する**：純粋なプロダクトフィードバックなら「それはレビューで扱う話題」としてバックログ行きにする
3. **頻発するならレビューを疑う**：本来レビューで消化されるべき話題がレトロに流れ込んでくるのは、レビューが機能していない（ステークホルダー不在・フィードバックが出ない・承認会化している）シグナル。直すべきはレトロではなくレビューの方
