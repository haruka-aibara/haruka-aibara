# ストーリー着手前の見通しが効く3つの場面

デイリースクラムで「順調です」しか出てこない。これは誰かがサボっているからではなく、**判定する基準がないから**であることが多い。

ある程度複雑なストーリーでは、進めながら学習が進む。だから「いま計画を変えるべきか」は、やっている本人にもチームにも判定できない。何が分かっていないかが分かるのが最後だったりする。3日溶かしても「こういうものかもしれない」と思えてしまう。

これを解くのに要るのは、進捗を細かく聞く仕組みではなく、**着手前に置いておく見通し**。「これがうまくいけば◯日目に××が動いているはず」を外に出しておくと、問いが変わる。

- 変えるべきか？ → **答えられない**
- 見込みとズレたか？ → **答えられる**

この見通しは、作った本人以外にも効く。実際に効くのは次の3つの場面。

## 1. 入って間もない人にとって、進め方の大まかな指標になる

新しく入った人がまず困るのは、技術そのものより「この規模の作業をどういう順番で、どれくらいのペースで進めるのが普通なのか」が分からないことだ。経験者は暗黙に持っているが、明文化されていない。

着手前の見通しがあると、それが**進め方のサンプル**になる。どこから手をつけるか、どこは後回しでよいか、何日目で何が動いていれば妥当なのか。

さらに効くのが「止まりどころの予告」で、**止まったときに言い出しやすくなる**。詰まりを申告できないのは、それが異常なのか普通なのかを判定できないから。「たぶんここで止まる」が事前に共有されていれば、「予告どおり止まりました」と言える。予告そのものが「止まるのは想定内だ」というメッセージになる。

予告が外れてもよい。予告と違う場所で止まったなら、それ自体が有用な情報になる。

## 2. プロダクトオーナーにとって、進捗の検査材料になる

PO が知りたいのは作業の詳細ではなく、**スプリントゴールが達成できそうか**だ。ところが毎日の口頭報告からはそれが読み取れない。「順調です」が3日続いた後で間に合わないと分かる、という失敗はここから来る。

着手時点の見通しがあれば、検査の対象がそこになる。「開始時にこう踏んでいた」に対して、いま実際どうなのか。ズレていれば、そのズレが議題になる。

このとき見るのは進捗率ではない。**基準線として置いた事実**（◯日目に××が動いている）が起きたかどうか。パーセンテージは主観が混ざるので検査に使えないが、動いているかどうかは誰が見ても同じ結論になる。

## 3. デイリースクラムで「進め方を変えるか」の議論ができる

デイリーが進捗報告会になるのは、報告以外に話すことがないからでもある。基準線があると、**話題が報告から判断に移る**。

このときデイリーの出力は3種類あると考えると扱いやすい。

1. **変える**（いま決める）
2. **まだ判断できない → いつ判断するかを決める**
3. **変えない**（見込みどおり）

肝は 2 が正当な出力だということ。複雑な作業で毎日「変えるべきか」を判断させるのは無理がある。「まだ分からない」で終わらせず、そこに**判断の期日か条件が付く**なら、デイリーは機能している。逆に報告会では 2 が出ない。「順調です」に丸められる。

だから健全性の基準は「毎回計画が変わっているか」ではなく、こう置ける。

> **「まだ判断できない」が言葉になって出てくるか。出たとき、いつ判断するかが決まるか。**

## 効かせるための注意

**精度を目的にしない。** 見通しは予定表ではなく、ズレを検出するための基準線。詳細な工数見積もりに寄せると、更新コストが勝って誰も見なくなる。

**未知をゼロにしない。** 未知を見つけて解消していく過程そのものが開発の中身なので、着手前に全部潰すとストーリーから学習が抜け、ただの作業指示になる。前倒しで動かすのは、依存先への確認や受け入れ条件など**自分たちの手では解けず待ちを生むもの**だけでよい。実装のやり方の未知は、手を動かして解くのが最速。

**たたき台として出す。** 特に AI に下書きさせる場合、最初に出た分解が基準になってチームから別案が出なくなる（アンカリング）。リファインメントに最初に持ち込むのは「未知」と「置いた仮定」だけにして、分解案はチームが自分で割った後に突き合わせるとよい。「置いた仮定」は、そのままプロダクトオーナーへの質問リストになる。

**基準線は2〜3点だけ置く。** 全サブタスクに日付を振ると管理表になり、更新されなくなって死ぬ。置くのは「薄くても縦に1本通っている日」と「未知が解消されている期限」で足りる。

## 運用

作るのはリファインメントの前。回すのはプロダクトオーナーではなく、**担当しそうな開発者かスクラムマスター**。PO が回すと「PO の計画」になり、開発側が受け取るだけの構図が固定される。

このリポジトリには、この見通しを作るための Claude Code スキルを置いてある（`.claude/skills/story-breakdown/`）。出力は「未知 → サブタスク → 止まりどころ → 基準線 → ズレの検出条件 → 置いた仮定」の順。

半期に一度の振り返りでこの運用の効果を見るなら、見積もり精度より先に**リファインメントで仕様確認に使った時間**と**着手後に発覚した未知の件数**が動くはずなので、そちらを先に見るとよい（[半期レトロスペクティブの想定シナリオ集](半期レトロスペクティブの想定シナリオ集.md)）。
