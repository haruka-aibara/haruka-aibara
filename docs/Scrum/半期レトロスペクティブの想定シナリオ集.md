# 半期レトロスペクティブの想定シナリオ集

スプリントレトロは直近2週間しか見ない。だから「じわじわリードタイムが伸びた」「メンバーが増えて意思決定の仕方が変わった」といった半年スケールの変化は、毎回スコープ外に落ちる。半期に1回の全体レトロはそれを扱う場だが、当日いきなり「半年を振り返って」と言っても記憶に残っている直近1か月の話しか出てこない。

そこで、**起きがちな場面をシナリオとして先に決めておき、そのシナリオで必要なデータを半期のあいだ溜めておく**。以下は10シナリオぶんの型。

## 合意形成の共通の型

シナリオ別の中身に入る前に、どのシナリオでも共通の流れ。

1. **データは前日までに配る**：当日は「データを読む時間」ではなく「解釈する時間」にする
2. **できたこと／できなかったことを出す**：人ではなく構造の話にする（誰が遅れたか、ではなく何が遅れを作ったか）
3. **改善アイデアを出し、半期でやる1〜2個に絞る**：3個以上決めた半期レトロはだいたい全部やらずに終わる
4. **やる／やらないをその場で決め、やらない理由も残す**：次の半期に同じ議論を最初からやらないため
5. **オーナーと確認タイミングを決める**：次のスプリントで着手なのか、1か月後に見直すのか、次の半期レトロまで寝かせるのか

---

## 1. チームに新メンバーが増えた

- **よくできた**：ドキュメントを見て自力で環境構築できた、最初のPRが1週間以内に出た
- **よくできなかった**：暗黙知の口伝が多く、特定の人にしか聞けない時間が長かった
- **集めるデータ**：オンボーディング所要日数（初コミット／初リリースまで）、新メンバーが詰まった質問のログ
- **改善アイデア**：詰まった質問をそのままドキュメントの目次にする、次の新メンバーがオンボーディング手順を更新する担当になる
- **合意形成**：新メンバー本人に「どこで詰まったか」を先に話してもらう。既存メンバーだけで議論すると「自分は困らなかった」に流れる

## 2. 大きなプロジェクトが完了した（無事リリース）

- **よくできた**：段階リリースで影響範囲を絞れた、期日を守れた
- **よくできなかった**：終盤に残業前提の帳尻合わせがあった、成功の要因が言語化されていない
- **集めるデータ**：当初見積もりと実績の差、スコープの増減履歴、終盤の残業・休日対応の量
- **改善アイデア**：うまくいった進め方を次のプロジェクトのテンプレートに落とす、終盤の追い込みが必要になった分岐点を1つ特定する
- **合意形成**：成功したプロジェクトほど「特に問題なし」で終わりやすい。再現したい要素を2つ挙げる、という問いにして議論を起こす

## 3. 新機能のリリースが完了した

- **よくできた**：フィーチャーフラグで段階公開できた、リリース後の問い合わせが少なかった
- **よくできなかった**：利用状況を測る仕組みを入れずにリリースし、効果が分からない
- **集めるデータ**：リリース後の利用率・継続率、想定した仮説と実際の差、リリース起因の問い合わせ件数
- **改善アイデア**：Definition of Done に「効果測定の指標が入っていること」を足す、使われなかった機能を落とす判断のタイミングを決める
- **合意形成**：作った側は成功と捉えがち。使われているかのデータを先に見せてから議論を始める

## 4. システム障害・トラブルを起こしてしまった

- **よくできた**：検知から一次対応までが速かった、ロールバックが機能した
- **よくできなかった**：原因調査に必要なログが残っていなかった、対応が特定の人に集中した
- **集めるデータ**：検知〜復旧の時間、ポストモーテムの再発防止策とその実施状況、同種インシデントの再発回数
- **改善アイデア**：再発防止策のうち未着手のものを1つだけ確実に終わらせる、対応手順を当番制で回して属人化を崩す
- **合意形成**：個別のポストモーテムは事象ごとに終わっている。半期レトロで見るのは**再発防止策が実際に実装されたかの通し率**で、その数字を出発点にする

## 5. リリースまでの時間が長い（長くなっている）

- **よくできた**：テストの自動化でリグレッション確認は短くなった
- **よくできなかった**：レビュー待ち・承認待ちの滞留が増え、着手から本番までが伸びた
- **集めるデータ**：リードタイム（着手〜本番）とその推移、工程別の待ち時間、PRのオープン期間分布
- **改善アイデア**：一番長い待ち工程だけを対象に手を入れる（レビュー担当のローテーション、承認フローの1段削減）、PRサイズの上限をチームで決める
- **合意形成**：「全部遅い」で終わらせないため、工程別の待ち時間を出して**最長の1工程に絞る**。半期で1工程だけ、が現実的なペース

## 6. 通常のレトロが「まあまあうまくいってる」で改善が出ない

- **よくできた**：スプリント内の運用は安定していて、大きな事故がない
- **よくできなかった**：安定に慣れて、半年前と比べた変化がほとんどない
- **集めるデータ**：半期のレトロアクション一覧と完了率、半年前と現在の指標比較（リードタイム、障害数、ベロシティの安定度）
- **改善アイデア**：「今のやり方を続けた場合、半年後・1年後に困ることは何か」を問う回にする（例は末尾の付録A・付録Bの呼び水リスト）、外部（他チーム・ステークホルダー）から見た評価を持ち込む
- **合意形成**：内側からは問題が見えない状態。**比較対象を外から持ってくる**（半年前の自分たち／他チームの数字）と、初めて差分が議題になる

## 7. チームメンバーが居心地悪そう

- **よくできた**：1on1で個別に拾えていた話がいくつかある
- **よくできなかった**：チームの場では本音が出ず、違和感が個人の中に留まっている
- **集めるデータ**：匿名アンケート（チームの雰囲気・発言のしやすさ）の推移、レトロでの発言量の偏り、有給取得率や離職・異動の兆候
- **改善アイデア**：発言順を固定して全員が話す形式にする、非同期で先に書いてから集まる（口頭の場で強い人に引っ張られない）
- **合意形成**：本人が特定される形で議題化しない。**匿名アンケートの集計結果を材料にして、個人ではなく傾向を扱う**

## 8. 心理的安全性が低い

- **よくできた**：技術的な議論は活発にできている
- **よくできなかった**：失敗やミスの共有が出てこない、「分からない」と言えていない
- **集めるデータ**：Edmondson の心理的安全性7項目のような定点アンケート、障害・ミスが自己申告で上がった割合、レトロで問題提起した人の分布
- **改善アイデア**：リーダーが先に自分の失敗を出す、失敗の共有に対する反応をルール化する（原因追及の前にまず情報提供への感謝）
- **合意形成**：「心理的安全性を上げよう」という抽象アクションは検証できない。**測る質問を1つ決めて、半期後に同じ質問で測る**ことまでを合意に含める。受託・多重階層での限界は[受託開発で心理的安全性はどこまで作れるか](受託開発で心理的安全性はどこまで作れるか.md)を参照

## 9. 意見の対立がある

- **よくできた**：技術選定で複数案が出て、比較のうえ決められたケースがある
- **よくできなかった**：対立が個人間の感情に転化した、決まらないまま棚上げされた論点が残っている
- **集めるデータ**：決まらずに持ち越されている論点のリスト、意思決定の記録（ADR等）の有無、同じ議論が再燃した回数
- **改善アイデア**：決め方を先に決める（誰が決定者か、いつまでに決めるか）、決定は記録して蒸し返しを防ぐ
- **合意形成**：対立そのものを解消しようとしない。**「決め方が無いこと」を問題として扱い、意思決定プロセスの合意を取る**。決定の記録は[ADRの要否をAIに判断させるリポジトリ設計](../ADR/ADRの要否をAIに判断させるリポジトリ設計.md)の考え方が使える

## 10. 部屋にいる象（誰も言い出したがらない前提）

- **よくできた**：象を避けたまま、目の前のスプリントは回せている
- **よくできなかった**：全員が問題だと分かっているのに議題にならない（触れると大ごとになる／改善コストが大きすぎる）
- **集めるデータ**：匿名で「触れられていないと思う問題」を集める、繰り返し出てくるが解決しない話題のリスト、その問題に起因する待ち時間・手戻りの実測
- **改善アイデア**：象そのものを解決しようとせず、影響を測るところまでを半期の目標にする（コストが数字になると初めて意思決定の土俵に乗る）
- **合意形成**：**言い出しっぺを個人にしない**のが要点。匿名で集めた項目をファシリテーターが読み上げる形にして、発言者ではなく場が議題を出したことにする。チームの外に決定権がある象は、レトロでは「誰にどう伝えるか」までを合意対象にする

## 付録A：呼び水リスト（状態編）

シナリオ6（改善が出ない）で使う「このまま続けたら半年後に困ってそう」の例。**「何か問題ありますか」では出てこないが、選択肢を並べると急に手が挙がる**。こちらはコード・環境・データなど**モノの状態**に寄せた項目（進め方そのものは付録B）。

使い方：関係しそうなカテゴリを2〜3個だけ選んで配る（全部は配らない・読み上げない）→ 当てはまるものに各自◯を付ける → 票が集まった上位3つだけを議題にする。項目はどれも「今は回っているが、続けると効いてくる」状態として書いてある。いま痛くないから議題に上がらない、というのがこのシナリオの本質。

### リリースとデリバリー

- リリース作業に手順書と当日の立ち会いが必要なままで、担当できる人が増えていない
- リリースの頻度が下がっていて、1回あたりの変更量が増え続けている
- 「まとめてリリースしたほうが安全」が定着し、小さく出す選択肢が消えている
- リリース判断の会議体が増えて、コードが完成してから本番まで日数が延びている
- ロールバック手順を試したのが半年以上前で、いま本当に戻せるか誰も確認していない
- 特定の曜日・時間帯にしかリリースできない制約が既成事実になっている
- リリースノートが誰にも読まれておらず、何が出たかを問い合わせで聞かれている
- リリース前チェック項目が増える一方で、減らす見直しをしたことがない
- 「念のため」の承認者が増え続け、承認待ちが最長の待ち工程になっている
- デプロイが夜間・休日に固定され、その時間に動ける人が限られている
- 段階リリース（カナリア・フラグ）の仕組みはあるが、実際は一斉公開に戻っている
- リリースを止める判断基準が明文化されておらず、毎回その場の空気で決めている

### コードと設計

- 「あとで直す」と言った箇所が、次の機能の土台になってしまっている
- 新機能を足すたびに条件分岐が増える構造で、影響範囲の見積もりが年々悪化している
- 誰も触りたがらないファイルがあり、その周辺の見積もりだけ倍になっている
- 一時対応のフラグ・回避コードが消されずに残り、本来の分岐が読めなくなっている
- コピペで増えた同じロジックが複数箇所にあり、片方だけ直すバグが出始めている
- ライブラリのバージョンを上げていない期間が長く、上げるコスト自体が上がり続けている
- 使われていない機能・画面が消せないまま保守対象に残っている
- フィーチャーフラグが消されずに溜まり、有効な組み合わせを誰も把握していない
- 設定値がコード・環境変数・管理画面に分散し、どれが効いているか調べないと分からない
- 命名や構造の流儀が人によって違い、レビューのたびに好みの議論になっている
- 自前で作った共通ライブラリのメンテナが実質1人になっている
- 移行途中で止まった新旧2つの実装が並走したままになっている
- エラー処理が握りつぶしになっている箇所があり、失敗が表に出ないまま進む
- 外部 API の仕様変更に弱い書き方をしていて、相手都合で壊れる余地が残っている

### テストと CI

- テストが落ちても「たぶんいつものやつ」で再実行する習慣がついている
- CI の実行時間が伸び、待ち時間を避けるためにローカル確認で済ませる人が出ている
- テストを書くのは余裕があるときだけ、が暗黙の運用になっている
- カバレッジは高いが、壊れても落ちないテストが増えている
- 手動テスト項目書が肥大化していて、リリースのたびに人手が要る
- 特定の環境でしか再現しないテスト失敗を、その環境を避けることで回避している
- 不安定なテストを一時的に無効化したまま、戻す期限を決めていない
- テストデータが古く、現在の本番データの形と合っていない
- E2E テストが壊れやすく、直す担当が決まっていないので放置されている
- CI が落ちたまま main にマージする例外運用が、常態になりつつある
- パフォーマンスの劣化を検知する仕組みがなく、遅くなったことに気づくのは苦情から
- CI の設定を触れる人が限られ、詰まると全員が待つ

### ブランチとレビュー

- レビュー依頼から着手までの待ち時間が伸びているが、誰も測っていない
- 1つの PR が大きく、レビューが「ざっと見て LGTM」になっている
- レビュー担当が固定で、その人の観点だけがコードの基準になっている
- 指摘が好みの議論に流れやすく、判断基準がドキュメント化されていない
- 長生きするブランチがあり、マージのたびにコンフリクト解消が大仕事になっている
- 「自分で書いて自分でマージ」が例外運用のはずが日常になっている
- レビューコメントが議論のまま終わり、結論がコードにも記録にも残っていない
- 承認だけ早く、指摘は後から個別 DM で伝えられている（記録に残らない）
- 差し戻しが失礼という空気があり、疑問を飲み込んでいる人がいる
- リンタ・フォーマッタで自動化できる指摘を、いまだに人間が指摘している
- レビュー対象がコードだけで、設計判断は誰の目にも触れずに入っている
- 緊急対応のときだけレビューを飛ばす運用があり、緊急の定義が緩んでいる

### 障害対応と運用

- アラートが多すぎて、鳴っていることが日常になっている（重要なものが埋もれる）
- 障害対応がいつも同じ2人に集まり、その2人の予定でリリース日が決まっている
- ポストモーテムの再発防止策のうち、実装まで到達した割合を誰も見ていない
- 監視項目が「入れた当時のまま」で、いまの構成と対応していない
- 手順書が更新されておらず、実際の手順は個人のメモにある
- オンコールの負荷が可視化されておらず、しんどさが個人の我慢で吸収されている
- 「再起動で直る」の裏側を調べないまま、同じ事象が定期的に起きている
- 障害の一次切り分けに必要な権限を持つ人が少なく、待ち時間が発生している
- 訓練（障害対応演習）を一度もやっていない、または前回が1年以上前
- 影響範囲の判定に時間がかかり、告知が後手に回る構造になっている
- 復旧優先で原因調査を打ち切り、同じ事象の再発時にまた最初から調べている
- 定常の手作業運用（月次のバッチ実行、手動での棚卸し）が残ったままになっている
- 障害の一次受けがサポート経由で、開発に届くまでにタイムラグがある
- 深夜対応の翌日に休む仕組みがなく、疲労が翌週まで持ち越されている

### 監視とログ

- 調査したいときに欲しいログが出ておらず、毎回コードを足してから再現している
- ログの保存期間が短く、気づいたときには消えている
- 監視ダッシュボードを開くのが障害時だけで、平常時の傾向を誰も知らない
- 監視が「落ちたら分かる」までで、遅くなったことは分からない
- しきい値が経験則で設定され、根拠を説明できる人がいない
- 通知先チャンネルが増えすぎて、どこを見ればよいか新メンバーに説明できない
- 外形監視がなく、ユーザー体感の異常に気づくのが問い合わせ経由
- ログに個人情報が混ざっているかどうかを、確認したことがない

### データとデータベース

- スキーマ変更のたびに手作業が入り、手順を知っている人が限られている
- 本番データを確認するのに、毎回誰かに依頼している
- 不要になったテーブル・カラムが消せないまま残っている
- バックアップは取っているが、リストアを試したことがない
- データ量の増加ペースを追っておらず、いつ限界が来るか分からない
- 集計・分析の SQL が個人の手元にあり、数字が人によって違う
- マスタデータの更新が手作業で、間違えたときに気づく仕組みがない
- 本番データのコピーを検証環境で使っており、マスキングの運用が曖昧
- 論理削除のフラグが増え、正しい抽出条件を知っている人が限られている
- データ移行の一時テーブルが残ったまま本番に置かれている

### 環境と開発体験

- 新メンバーの環境構築に数日かかる状態が、改善されないまま続いている
- 検証環境が1つしかなく、使う順番を人が調整している
- 検証環境と本番の差分が大きく、検証で通っても本番で落ちる
- ローカルで動かせない機能が増え、確認のたびに共用環境が必要になっている
- ビルドが遅く、待ち時間に別の作業に切り替えるコストが積み上がっている
- 誰かの環境だけで起きる問題を、その人が回避策で運用している
- 開発用の認証情報が個人の手元管理になっている
- 検証環境が落ちても誰も直さない期間があり、直せる人が特定の1人

### ドキュメントと属人化

- 設計の意思決定の理由がどこにも残っておらず、「なぜこうなっているか」に答えられる人が1人
- 新メンバーが最初に読む場所が決まっていない（人によって案内するリンクが違う）
- ドキュメントが古いことは全員知っているが、直す担当が決まっていない
- 運用ノウハウが個人のチャット DM に散っている
- 退職・異動が1人発生したら止まる領域が、はっきり分かっている（けど手を打っていない）
- 図が実態と合っておらず、説明のたびに口頭で補足している
- 議事録は残っているが、決定事項だけを引ける場所がない
- 顧客・他部署への説明資料が毎回作り直され、再利用されていない
- 「詳しい人に聞く」が最速の手段になっていて、その人の時間が細切れに削られている
- 手順のうち一部だけが自動化され、残りが口伝になっている

### チームと働き方

## 付録C：削る方向の改善アイデア（DevOps）

付録A・Bが「困りごとを見つける」ためのリストなら、こちらは**打ち手の例**。

改善案を出すと、たいてい「入れる」方向に偏る。ツールを足す、チェックを増やす、レビュー観点を追加する、通知を増やす。**足す改善は思いつきやすく、反対されにくく、そして効きにくい。** 開発効率を実際に動かすのは、たいてい削る方——工程・承認・待ち・手作業・重複・通知・分岐を減らすほう。

削る改善の見つけ方は、この3つの問いで足りる。

1. **これをやめたら誰が困るか、実際に確認したか**（想像で「困る人がいそう」と止めていないか）
2. **これは何を防ぐために入れたか。その事象はいまも起きるか**（過去の障害の名残が残っていないか）
3. **自動化する前に、そもそも要るか**（不要な作業を自動化すると、不要な作業が永久に残る）

削るときは、戻せる形で段階的に。**使われているか測る → 期限を切って予告する → 消す → 戻し方を残す。** この順を飛ばすと、削る改善そのものが信用を失って二度とできなくなる。

そして合意形成の注意：**削る改善は「入れる改善」より合意が要る。** 誰かの安心を削るから。「様子を見る期間つき」「戻す条件つき」で提案すると通りやすい。

### Git・PR 運用

- レビュー必須人数を2人から1人に下げ、2人必須は重要なディレクトリだけ CODEOWNERS で指定する
- PR テンプレートの項目を、実際に毎回書かれている欄だけに削る
- ブランチ命名規約のうち、自動化で参照していない部分を廃止する
- 長生きするリリースブランチをやめ、トランクベースに寄せてマージ作業を削る
- rebase 強制をやめて squash merge に統一し、手順を1つ減らす
- コミットメッセージ規約を、リリースノート生成に使う prefix だけに絞る
- スクリーンショット必須を UI 変更時だけに限定する
- 「WIP は下書き PR」以外のステータス運用ルールを廃止する
- 巨大 PR を分割する運用を入れるより先に、分割できない原因（リリース単位の粗さ）を削る
- マージ後の手動ブランチ削除をやめ、自動削除にする
- fork ベースの運用をやめ、ブランチ運用に寄せる（内部開発なら手数が減る）

### CI パイプライン

- 全ジョブを全 PR で回すのをやめ、変更パスに応じて絞る
- pre-commit と CI で二重に走る lint を、どちらか一方に寄せる
- E2E を全 PR から外し、マージ後とリリース前だけにする
- マトリクスビルドのうち、実際にサポートしていない組み合わせを削る
- `continue-on-error` で失敗が無視されているジョブを削除する（見ていない検査は無い検査）
- 依存インストールをキャッシュして毎回のダウンロードを削る
- 並列度を上げる前に、最も遅いジョブ1つの中身を削る
- タイムアウト未設定のジョブに上限を付け、無限待ちを削る
- 成果物の保存期間を短くして、待ち時間とストレージを削る
- 成功時の通知をやめ、失敗時だけにする
- 同じテストが複数ワークフローで走っている重複を削る
- セルフホストランナーとホステッドの二重管理をやめ、片方に寄せる
- 手動トリガのワークフローのうち、半年間実行されていないものを消す

### Terraform・IaC

- どこからも別の値で渡されていない変数を、ハードコードに戻して選択肢を削る
- 使われていない module / variable / output / locals を削除する
- 環境ごとにコピーされた tfvars の重複を、共通デフォルトに寄せる
- 一枚岩の巨大 state を分割し、plan の待ち時間を削る
- `count` と `for_each` の入れ子で読めなくなっている箇所を、素直な記述に戻す
- 手動作成リソースを import して、「コードと実物のズレ」を確認する作業自体を削る
- 毎回出る意味のない plan 差分を潰し、レビューでの読み飛ばしを削る
- `fmt` と `validate` を CI に入れて、レビューでの形式指摘を削る
- provider とモジュールのバージョンを固定し、予期しない差分の調査を削る
- workspace の多用をやめてディレクトリ分割に寄せ、どこに何があるかの記憶負荷を削る
- 自作の Terraform ラッパースクリプトを廃止して、素のコマンドに戻す
- リモート実行に寄せて「特定の人の手元からしか apply できない」を削る
- 環境差分をモジュールの分岐で吸収するのをやめ、環境ごとに素直に書く（分岐の読解を削る）
- 使っていないプロビジョナ・ローカル実行を削除する
- 削除保護や lifecycle の例外指定のうち、理由が失われているものを棚卸しする

### 承認とゲート

- 低リスク変更（ドキュメント、影響の閉じた設定）の承認を不要にする基準を作る
- 変更管理会議を「例外だけ諮る」形にし、定型は通過させる
- リリース判定会を廃止し、自動チェックの結果をもって判定とする
- 直列になっている承認を並列にする
- 「念のため」で入っている承認者を外す
- 承認者が実質1人の工程に代理を立て、休暇での停止を削る
- 緊急時の迂回手順を明文化し、非公式な迂回を正規化する
- 同じ内容を別のシステムで二重申請している箇所を1つにする

### 手作業

- 自動化を検討する前に「そもそもこの作業は要るか」を問う（不要な作業の自動化は永久化）
- 手順書のうち毎回同じ値を入れる箇所を、既定値にして入力を削る
- 環境構築を devcontainer やスクリプト1本にまとめる
- アカウント発行・権限付与・データ抽出をセルフサービス化する
- リリースノートの手作業を、PR / コミットからの生成に置き換える
- 手動の棚卸しをやめ、タグ必須化＋自動検出に置き換える
- 定期実行のバッチを手動起動している箇所をスケジュール実行にする
- 複数の場所に同じ設定を書いている二重管理を、1か所に寄せる
- 障害時の情報収集コマンド群を1つのスクリプトにまとめ、手打ちを削る

### 待ち時間

- レビュー待ちに上限時間を決め、超えたら別の人が入る
- 依頼を非同期で受け、着手予定を自動で返す（催促のための会話を削る）
- 環境の取り合いをやめ、PR ごとの使い捨て環境にする
- 他チームへの依頼が必要な操作を、権限委譲でセルフサービスにする
- ビルド待ちの間に別作業へ切り替えるコストを、ビルド短縮そのもので削る
- 承認待ちが最長工程なら、まずそこだけに手を入れる（他は触らない）
- 外部依存の返答待ちを、代替作業を用意して並行化する

### 環境

- 使われていない検証環境を落とす
- 常時起動をやめ、夜間・休日は停止する
- 本番同等でなくてよい環境のスペックを落とす
- 環境の数を減らし、段階を1つ削る（開発・検証・ステージング・本番の4段が要るか）
- 個人専用環境をやめ、使い捨てに寄せる
- 検証環境固有の設定差分を減らし、「検証では動いたのに」を削る

### 監視・通知・アラート

- 一度も対応したことがないアラートを削除する
- しきい値を実測に合わせ直し、常時鳴りを止める
- 通知チャンネルを統合し、どこを見ればよいかの判断を削る
- 見られていないダッシュボードを消す
- 定期サマリ通知をやめ、対応が必要なものだけ流す
- 同じ事象が複数経路で通知される重複を1つにする
- ログの保存期間を、実際に調査する期間に合わせる
- 監視項目のうち、いまの構成に存在しないものを削除する

### ドキュメント・報告

- 更新されていないドキュメントを消す（古い情報は無いより悪い）
- 手順書をコード化し、ドキュメントとの二重管理を削る
- 週次報告をダッシュボードのリンク1本に置き換える
- 同じ内容が複数の README に書かれている重複を1か所に集約する
- 会議のたびに作り直している資料を、常設ページの更新に変える
- 読まれていないテンプレートの節を削る

### コード・リソース・機能

- 使われていないフィーチャーフラグを削除する
- デッドコードを消す（残っている限り、読む時間を消費し続ける）
- 使われていない機能・画面を落として保守対象から外す
- 未使用の IAM ロール・セキュリティグループ・スナップショット・古い AMI を削除する
- 依存ライブラリのうち、実際に import していないものを外す
- 自前実装をマネージドサービスに寄せ、運用対象そのものを削る
- 設定項目のうち、既定値以外で使われたことがないものを廃止する
- 移行が終わった旧実装を消す（新旧並走の読解コストを削る）
- 使われていないバッチ・cron を止める

### テスト（消すのではなく層を移す）

- 同じことを確認している E2E とユニットの重複を、下の層に寄せる
- 外部依存をモックにできる統合テストを、速い層へ移す
- 自動テストと重複している手動テスト項目を削除する
- 不安定なテストを「直す・消す」のどちらかに決める（放置状態を削る）
- 実行されていないテスト（スキップのまま放置）を削除する
- カバレッジ目標の数字ではなく、落ちたときに原因が分かるかで残すものを選ぶ

### ツール・SaaS

- 同じ役割のツールが2つある状態を1つにする
- 使われていない SaaS を解約する
- 誰も見ていない連携・Webhook を削除する
- 独自スクリプトが標準ツールの機能を再実装している箇所を、標準に戻す
- 認証経路が複数ある状態を1つに寄せる

### 権限・セキュリティ運用（削っても弱くしない形で）

- 手動の権限申請を、期限付きの自動付与に置き換える（手間もリスクも減る）
- 恒久的な管理者権限を廃止し、必要時のみの昇格にする
- 一時的に開けたアクセス経路を棚卸しして閉じる
- 例外承認のうち、理由が失われているものを再申請に回す
- 退職者アカウントの手動削除を、人事システム連携に置き換える
- 誰も見ていない監査ログの出力を止め、見るものだけ残す（減らして見る）

### 会議・儀式（DevOps 側の定例）

- 目的を説明できない定例を1つ廃止し、1か月後に困ったか確認する
- 障害報告会を、記録の共有＋質問があるときだけの開催に変える
- リリース前の読み合わせを、チェックの自動化で置き換える
- 参加者が発言しない会議から、その人を外す（情報共有は記録で足りる）
- 進捗確認の定例を、ボードが正しく更新されている状態で置き換える

## 運用のコツ

- 10シナリオ全部を毎回やらない。半期のあいだに実際に起きた2〜3シナリオだけを選ぶ
- データは半期レトロの直前に集めない。**溜まる仕組みを先に作っておく**（アンケートは毎月、リードタイムは自動集計）
- 過去ではなく未来から考える形式に切り替えたいときは[フューチャースペクティブをゼロから理解する](フューチャースペクティブをゼロから理解する.html)を併用する
- 決めたアクションのその後は、通常の[改善ループのチェックリスト](スクラムマスターのセルフチェックリスト/ベストプラクティス/改善ループ.md)で追う。半期レトロで決めて半期レトロまで放置、が一番ありがち
