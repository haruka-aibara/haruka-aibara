# 前提知識：アプリケーションアーキテクチャ

「アプリをそのままコンテナに入れたら動きが変になった」——コンテナ化で詰まる原因の多くは Docker の使い方ではなく、**アプリ側がコンテナ前提の設計になっていない**こと。どういう設計だとコンテナに乗せやすいのかを先に知っておくと、遠回りしない。

## コンテナに乗せやすいアプリの条件

コンテナは「使い捨てできるプロセス」として扱われる。スケールアウトも障害復旧も「古いのを消して新しいのを起動」で行われるため、アプリ側に求められる性質が決まってくる：

- **状態を自分の中に持たない（ステートレス）**: セッションやアップロードファイルをローカルディスクに書くと、コンテナが消えたとき一緒に消える。状態は DB・オブジェクトストレージ・キャッシュ（Redis 等）へ外出しする
- **設定は環境変数で受け取る**: 環境ごとに設定ファイルを焼き込むとイメージが環境の数だけ必要になる。「同じイメージを設定だけ変えてどこでも動かす」が原則
- **ログは stdout に吐く**: ファイルに書くとコンテナごとに回収の仕組みが要る。標準出力に出せば `docker logs` やログドライバがそのまま拾う
- **SIGTERM で行儀よく終了する**: 停止＝SIGTERM なので、受けたら処理中のリクエストを終えて終了する実装になっているか

この考え方は「The Twelve-Factor App」として整理されており、コンテナ以前からあるが実質コンテナ設計の教科書になっている。

## 1コンテナ1プロセスと、プロセス構成の分解

「Web サーバーとアプリと cron を1コンテナに同居」はアンチパターンで、**役割ごとにコンテナを分ける**のが基本（スケール・更新・障害の単位が揃うため）。既存アプリをコンテナ化するときの実作業は、この分解——「このシステムは実はどんなプロセスの集合か」を洗い出すこと——から始まる。マイクロサービスまで行かなくても、この分解の感覚は必須。
