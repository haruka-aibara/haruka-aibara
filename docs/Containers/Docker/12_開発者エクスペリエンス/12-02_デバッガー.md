# デバッガー

コンテナ化した途端、いつもの「IDE でブレークポイント」が効かなくなって print デバッグに退化する——のはもったいない。アプリはコンテナの中、デバッガー（IDE）はホスト側という分断を埋める方法は確立されている。

## 型：デバッグサーバーをコンテナ内で開き、IDE から接続する

各言語のデバッガーは「リモートデバッグ」モードを持っている。コンテナ内でデバッグ用ポートを開き、ホストの IDE がそこに接続する構図。

Python（debugpy）の例：

```yaml
# compose.override.yml（開発時のみ）
services:
  api:
    command: python -m debugpy --listen 0.0.0.0:5678 --wait-for-client -m uvicorn main:app --host 0.0.0.0
    ports:
      - "127.0.0.1:5678:5678"   # デバッグポートはローカルのみに公開
```

VS Code 側は「Remote Attach」構成で localhost:5678 に接続すれば、コンテナ内のコードにブレークポイントが効く。Node（`node --inspect=0.0.0.0:9229`）、Go（dlv）、Java（JDWP）も同じ型。

2つの注意点：

- **パスのマッピング**：ホストの `./src` とコンテナの `/app/src` の対応を IDE に教える（VS Code なら `pathMappings`）。ここがズレるとブレークポイントが「未束縛」になる
- **デバッグポートを外に晒さない**：デバッガーは任意コード実行の口そのもの。`127.0.0.1:` 付きでバインドし、本番イメージには絶対に入れない

## VS Code Dev Containers：発想を逆転させる

「コンテナにデバッガーを繋ぐ」のではなく「**開発環境ごとコンテナの中に住む**」アプローチ。`.devcontainer/devcontainer.json` を置くと、VS Code がコンテナ内にサーバーを立てて、エディタ・ターミナル・デバッガーが全部コンテナ内で動く（ちなみにこのリポジトリ自体も devcontainer 運用）。

- チーム全員の開発環境が定義ファイルで揃う（「新人のセットアップが30分」の世界）
- デバッグはローカル開発と同じ操作感。リモートデバッグ設定が不要になる

## そもそもデバッガー以前の調査

「まず何が起きてるか」の段階なら、デバッガーより先に：

```bash
docker compose logs -f api       # ログ
docker exec -it api sh           # 中に入って状態確認（09章参照）
docker debug api                 # シェルすら無いイメージにデバッグツール一式を注入（Docker Desktop 機能）
```

distroless などシェルなしイメージの調査は `docker debug`（またはエフェメラルコンテナ的にツール入りイメージを同居させる手法）を知っていると詰まない。
