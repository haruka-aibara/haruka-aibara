# 名前空間（namespaces）

コンテナ内で `ps aux` すると自分のプロセスしか見えず、自分が PID 1 になっている。ホストでは何千番のプロセスなのに。この「別世界にいるような視界」を作っているのが Linux カーネルの **namespace（名前空間）**——コンテナの隔離の半分はこれ（もう半分は [cgroups](02-02_cgroups.md)）。

## 何を分けているのか

namespace は「カーネルが管理するリソースの見え方」を種類ごとに分離する。主なもの：

| namespace | 分離するもの | コンテナでの現れ方 |
|---|---|---|
| PID | プロセスID空間 | コンテナ内で自分が PID 1。他コンテナ・ホストのプロセスが見えない |
| NET | ネットワーク | コンテナごとに独自の IP・インターフェース・ルーティングテーブル |
| MNT | マウントポイント | コンテナごとに独立したファイルシステムツリー |
| UTS | ホスト名 | コンテナごとに別のホスト名 |
| IPC | プロセス間通信 | 共有メモリ等がコンテナ内に閉じる |
| USER | UID/GID の対応 | コンテナ内の root をホストの一般ユーザに写像できる（後述） |

重要なのは、これが**視界の分離であって、実体の分離ではない**こと。ホストから見ればコンテナのプロセスは普通に存在していて、`sudo ls -l /proc/<PID>/ns/` でそのプロセスがどの namespace に属しているかも見える。

## 手で触って実感する

Docker なしでも namespace は作れる。`unshare` コマンドで：

```bash
sudo unshare --pid --fork --mount-proc ps aux
# → PID 1 に自分だけが見える「ミニコンテナ」的な視界になる
```

コンテナが「特別な仮想化技術」ではなく「カーネル機能の組み合わせ」であることが体感できる。逆方向のコマンドが `nsenter` で、既存コンテナの namespace に入ってデバッグする（`docker exec` の親戚のような）用途に使える。

## セキュリティの視点：PID 1 と USER namespace

- **コンテナ内の PID 1** は特別な責務を持つ（シグナル処理・ゾンビ回収）。アプリが PID 1 に不向きな場合は `docker run --init` で軽量 init を挟む
- デフォルトの Docker では **USER namespace は使われておらず**、コンテナ内の root ＝ホストの root（UID 0 のまま）。エスケープ時の被害がそのまま root になる根拠がこれで、対策の第一歩が Dockerfile での `USER` 指定、より強い対策が userns-remap や rootless Docker になる
