# コンテナとは何か

コンテナを「軽いVM」と理解していると、いずれ説明のつかない現象にぶつかる。「コンテナの中で `ps` したらホストと同じカーネルバージョンだった」「ホストから コンテナ内のプロセスが普通に見えた」——VM ならありえないこれらは、コンテナの正体を知っていれば当たり前の話。

## 正体：視界と資源を制限された、ただのプロセス

コンテナとは、Linux カーネルの機能で**隔離されたプロセス**のこと。ゲスト OS もハイパーバイザもない。使われているのは主に2つのカーネル機能：

- **namespaces（名前空間）**: 見える世界を分ける。コンテナ内では自分が PID 1 に見え、自分用のネットワークインターフェースとファイルシステムツリーを持っているように見える——が、それは「視界」の話で、実体はホスト上の1プロセス
- **cgroups**: 使える量を分ける。CPU・メモリ・I/O の上限をプロセスグループ単位でかける

だからコンテナは：

- **起動が速い**（プロセスの起動と同じ。OS ブートがない）
- **オーバーヘッドがほぼない**（仮想化していない）
- **ホストとカーネルを共有する**（コンテナ内から `uname -r` するとホストのカーネルが見える。Windows 上で Linux コンテナを動かすには VM が必要になるのもこのため）

ホスト側から `ps aux` すれば、コンテナ内のプロセスは普通のプロセスとして一覧に出てくる。試しに見てみると「ただのプロセス」という実感が湧く。

## イメージとコンテナの関係

- **イメージ**: アプリと依存物一式を焼き固めた読み取り専用のテンプレート（クラスのようなもの）
- **コンテナ**: イメージから起動した実行中のインスタンス

1つのイメージから何個でもコンテナを起動でき、コンテナ内での変更はそのコンテナ限り（イメージは変わらない）。この不変性が「どこでも同じものが動く」の土台になっている。

## この理解が効いてくる場面

「カーネル共有のプロセス」という理解は、後の学習全部の土台になる。セキュリティ（カーネル共有＝VM より隔離が薄い）、リソース制限（cgroups の挙動）、トラブルシューティング（ホスト側から調査できる）——詳細は [02_基盤技術](../02_基盤技術/) と Linux 側の [コンテナ化](../../../Operating%20System/Linux/16_コンテナ化/) を参照。
