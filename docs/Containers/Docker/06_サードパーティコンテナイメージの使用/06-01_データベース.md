# サードパーティイメージ：データベース

開発環境の PostgreSQL、どう用意するか。ホストに直接インストールすると、バージョンの切り替えも複数プロジェクトの併用も面倒で、アンインストールも汚れる。公式イメージを使えば「必要なバージョンを起動して、終わったら消す」ができる——サードパーティイメージの恩恵が一番分かりやすいのが DB。

## 基本形：PostgreSQL を1コマンドで

```bash
docker run -d --name dev-db \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_DB=myapp \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16
```

押さえるポイント：

- **初期設定は環境変数で渡す**：ユーザ・パスワード・初期DB名。何が使えるかは Docker Hub のイメージ説明（README）に書いてある。**イメージを使う技術の半分は README を読む技術**
- **データはボリュームに**（`-v pgdata:...`）：コンテナの書き込み層はコンテナ削除で消えるため、データの置き場所（イメージごとに決まったパス）をボリュームにする。パスも README に書いてある
- **バージョンをタグで固定**（`postgres:16`）：`latest` だと再pull時に意図せずメジャーバージョンが上がり、データファイルの互換性で起動しなくなる事故がある

初期化 SQL を流したい場合は `/docker-entrypoint-initdb.d/` に .sql を置く（バインドマウントする）仕組みが公式イメージに用意されている。MySQL も Redis も同じ流儀。

## 使いどころの整理

- **開発環境**：本命。プロジェクトごとに compose で DB を立てる（[09-01_docker_compose](../09_コンテナの実行/09-01_docker_compose.md)）
- **CI**：テスト用 DB を毎回まっさらに起動できる。「CI ではモックではなく本物の PostgreSQL でテスト」が容易になった
- **本番**：コンテナで DB を動かすこと自体は可能だが、データの永続化・バックアップ・フェイルオーバーの運用を全部自分で背負うことになる。クラウドなら RDS などのマネージド DB に任せるのが標準的な判断（コンテナ運用の手間と障害リスクを引き受けてまで自前化する理由があるかで判断する）

## セキュリティの注意

`-p 5432:5432` は**全インターフェースで公開**なので、クラウド VM 上で無防備にやると開発 DB がインターネットに露出する（実際、無認証 Redis・MongoDB の露出はマイニングマルウェアの定番標的）。ローカル専用なら `-p 127.0.0.1:5432:5432` と書く癖をつける。
