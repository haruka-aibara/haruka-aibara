# Docker CLI：コンテナ操作

run・stop・logs・exec などの基本操作は [09_コンテナの実行](../09_コンテナの実行/) に個別記事がある。ここでは「**動いているコンテナがおかしいとき、何を打つか**」という調査目線でコマンドを整理する。

## 状態確認の階段

```bash
docker ps -a                # まず全コンテナの状態（-a で停止中も）
docker logs --tail 100 api  # 直近ログ。-f で追尾、-t でタイムスタンプ
docker inspect api          # 設定と状態の全部（JSON）
docker stats                # CPU・メモリ使用量のリアルタイム表示
docker top api              # コンテナ内のプロセス一覧（ホスト側から）
```

`ps -a` の STATUS 欄は情報の宝庫：

- `Exited (137)` → 128+9=SIGKILL。OOMKilled の可能性大 → `docker inspect api --format '{{.State.OOMKilled}}'`
- `Exited (1)` → アプリ自身のエラー終了 → logs を見る
- `Restarting (1) 5 seconds ago` → クラッシュループ中
- `Up 2 hours (unhealthy)` → プロセスは生きているがヘルスチェック失敗

## 中に入る・ファイルを出し入れする

```bash
docker exec -it api sh                      # シェルで入る（詳細は 09章）
docker cp api:/var/log/app/error.log ./     # コンテナ→ホストへファイル取得
docker diff api                              # イメージから何が変更されたか
```

`docker diff` は地味に強力で、「このコンテナ、イメージの状態から何が書き換わったか」が一覧できる。侵害調査の初動（見覚えのないバイナリが追加されていないか）や、「設定をコンテナ内で直接いじった犯人探し」に効く。

## 終了コードとシグナルの関係

```bash
docker stop api      # SIGTERM → 10秒待って SIGKILL
docker kill api      # 即 SIGKILL
docker inspect api --format '{{.State.ExitCode}}'
```

`stop` で毎回10秒待たされるコンテナは、アプリが SIGTERM を処理していない（PID 1 問題を含む。[00-04_シェルスクリプト](../00_前提条件/00-04_シェルスクリプト.md)）。放置すると graceful shutdown が効かず、デプロイのたびに処理中のリクエストを断ち切っていることになる。

## 掃除

```bash
docker container prune                     # 停止中コンテナを一括削除
docker rm -f $(docker ps -aq)              # 全コンテナ強制削除（開発機リセット用の劇薬）
```
