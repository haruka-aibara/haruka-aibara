UEFI — OS が起動する前の時間を、誰が守るのか

OS より先に動くマルウェアは、OS 上の対策ソフトからは見えない。だから起動の連鎖そのものを検証する。

何が問題なのか

アンチウイルスもログ監視も、OS が動いていて初めて機能する。ではOS より先に読み込まれる場所にマルウェアが居座ったらどうなるか——検査する側が、すでに乗っ取られた土台の上で動くことになる。「クリーンです」という結果自体が信用できない。

電源投入から OS が動き出すまでの数秒間は、こういう性質の空白地帯だった。ここを埋めるのが UEFI とセキュアブート。

UEFI は BIOS の置き換え

UEFI（Unified Extensible Firmware Interface）は、PC の電源投入直後に動くファームウェアの規格。従来の BIOS を置き換えたもので、2TB を超えるディスクからの起動、ネットワーク機能、モジュール化された構造といった実務上の利点がある。だがセキュリティの文脈で重要なのは、ここに署名を検証する仕組みが入ったこと。

検証するのか、記録するのか

似て非なる仕組みが2つある。

  • セキュアブート：署名を検証し、通らなければ止める。
  • 計測ブート（Measured Boot）：各段階のハッシュ値を計算し、TPM という専用チップに記録していく。起動自体は止めない。

記録が何の役に立つのかというと、後から「この端末は改ざんされていない状態で起動した」ことを外部に示せる。社内ネットワークへの接続時に端末の健全性を確認する、といった用途に使われる。Windows のディスク暗号化（BitLocker）が、構成が変わると回復キーを要求してくるのも、この記録が変化したことを検知しているため。

運用でぶつかるところ

署名のないものは動かない——これは仕様どおりの挙動だが、現場では障害として現れる。自前でビルドした Linux カーネル、署名のないドライバ、古い仮想化ソフト、一部の起動用 USB。
「動かないからセキュアブートを無効にする」で解決してしまうと、以後その端末は起動前の保護を失う。無効化を恒久的な対処にせず、署名済みのものに置き換えるか、自組織の鍵を登録する方向で解く。
また、署名済みでも脆弱性が見つかったブートローダは失効リスト（dbx）で拒否される。この更新が配布されると、古いブートローダを使っていた端末が突然起動しなくなることがあるので、大量展開の前に検証環境で確認する。
