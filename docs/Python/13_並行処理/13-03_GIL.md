# GIL

「CPU 8コアのマシンでスレッドを8本立てたのに、処理速度が1コア分しか出ない」——Python の並行処理で誰もが一度は困惑する現象で、原因が **GIL（Global Interpreter Lock）**。Python の並行処理の選択肢（スレッド／プロセス／asyncio）を正しく選ぶには、この制約の理解が出発点になる。

## GIL とは：Python バイトコードを実行できるのは常に1スレッド

CPython インタプリタは、内部状態（オブジェクトの参照カウント等）をスレッド競合から守るために、**プロセス全体で1つの大きなロック**を持っている。どのスレッドも Python コードを実行するにはこのロックを取る必要があり、つまり**スレッドを何本立てても、Python コードを同時に実行できるのは1本だけ**。

これが冒頭の現象の答え：CPU を使う処理（画像処理、集計、暗号計算）をスレッドで並列化しても、全スレッドが1つのロックを順番に取り合うだけで、合計スループットは1コア分のまま（ロックの取り合いでむしろ遅くなることさえある）。

## ではなぜスレッドが存在するのか：I/O 待ちはロックを手放す

重要な例外が I/O。**ブロッキング I/O（ネットワーク、ファイル、DB待ち）の間、スレッドは GIL を解放する**。だから「待ち」が主体の処理なら、スレッドは並行に働ける：

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=20) as pool:
    results = list(pool.map(fetch_url, urls))   # 20並行でダウンロード：ちゃんと速くなる
```

NumPy などの C 拡張が重い計算中に GIL を解放するのも同じ仕組みで、「NumPy の行列演算はスレッドで並列化が効く」という例外もここから来る。

## 実務の選択表

| 処理の性質 | 正解 | 理由 |
|---|---|---|
| I/O バウンド・並行数そこそこ | スレッド ([13-04](13-04_スレッディング.md)) | I/O 中は GIL が空くので並行に働く |
| I/O バウンド・並行数が大量 | asyncio ([13-02](13-02_非同期処理.md)) | スレッドより軽い |
| **CPU バウンド** | **マルチプロセッシング ([13-01](13-01_マルチプロセッシング.md))** | プロセスごとに GIL を持つ＝真の並列 |

「CPU バウンドにスレッド」だけが GIL に阻まれる組み合わせで、それ以外は道がある、と整理すると迷わない。

## 将来：GIL は外せるようになりつつある

長年「Python の宿命」だった GIL だが、PEP 703 が承認され、Python 3.13 から**フリースレッド版（GIL なしビルド）が実験的に提供**されている。エコシステム（C 拡張）の対応が要るため移行は数年がかりの計画だが、「GIL は永遠の制約」ではなくなった。当面の実務は上の選択表で考えつつ、この動向は知っておく価値がある。
