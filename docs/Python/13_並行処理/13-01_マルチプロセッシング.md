# マルチプロセッシング

100万件のログを解析するスクリプト、8コアのマシンで1コアしか使っていない——CPU バウンドの処理を本当に並列化したいなら、Python ではスレッドではなく**プロセス**を並べる。プロセスごとに独立したインタプリタ（＝独立した GIL。[13-03](13-03_GIL.md)）を持つので、コア数ぶんの真の並列が手に入る。

## 基本形：Pool / ProcessPoolExecutor

「リストの各要素に重い処理を適用」なら、これだけ：

```python
from concurrent.futures import ProcessPoolExecutor

def analyze(chunk):          # CPU を食う処理
    ...
    return result

if __name__ == "__main__":                      # ← 必須（後述）
    with ProcessPoolExecutor() as pool:          # デフォルトでコア数ぶんのプロセス
        results = list(pool.map(analyze, chunks))
```

`if __name__ == "__main__":` ガードは飾りではない。子プロセスは起動時に親モジュールを import するため、ガードがないと**子が孫を生み、孫が曾孫を生む無限増殖**になる（特に macOS/Windows のデフォルトである spawn 方式）。マルチプロセッシングの「おまじない」の中で最重要。

## スレッドと違う3つの前提

プロセスはメモリを共有しない。この一点から実務上の注意が全部導かれる：

1. **データはコピーして渡される**：引数と戻り値は pickle 化されてプロセス間を移動する。**巨大なデータを渡すと、シリアライズのコストで並列化の利得が消える**。「渡すのはファイルパスやIDにして、読み込みは子側でやる」が定石
2. **pickle できないものは渡せない**：ラムダ、オープン済みのファイルハンドル、DB コネクション等はエラーになる。関数はモジュールのトップレベルに定義する
3. **グローバル変数の変更は親に反映されない**：子は親のコピー（または新規起動）なので、「子で更新したはずの dict が空」となる。共有が必要なら戻り値で返して親で集約するのが最も安全（`Manager` 等の共有機構はあるが、複雑さに見合う場面は少ない）

## 使いどころの判断

- **向いている**：件数×重い計算に分解できる処理（ログ解析、画像変換、ハッシュ計算、シミュレーション）
- **向いていない**：I/O 待ちが主体（スレッドか asyncio で足りる。プロセスは起動もメモリも高くつく）、タスク間で密に状態を共有する処理

なお「複数マシンに広げたい」規模になったら multiprocessing の守備範囲を超え、ジョブキュー（Celery/SQS）やデータ基盤（Spark 等）の領分になる。
