# 同期型＋非同期型（両対応）

「非同期にしたいエンドポイントは一部だけ。全部 async で書き直すのは無理」——現実のプロジェクトはこれが普通で、同期型（[12-07](12-07_同期型.md)）と非同期型（[12-08](12-08_非同期型.md)）の二者択一を迫られると困る。この間を埋めるのが**両対応**のフレームワークで、代表が FastAPI（正確にはその土台の Starlette）。Django も 3.x 以降 async ビューを段階的に取り込んでいる。

## 仕組み：def と async def を混ぜて書ける

```python
@app.get("/aggregate")
async def aggregate():                    # 非同期：並行I/Oの恩恵を受けたい
    async with httpx.AsyncClient() as c:
        a, b = await asyncio.gather(c.get(API_A), c.get(API_B))
    return merge(a, b)

@app.get("/legacy")
def legacy():                             # 同期：既存の同期ライブラリをそのまま使う
    return old_orm.query(...)             # requests や既存 ORM でOK
```

ポイントは同期関数の扱い。FastAPI は `def` のエンドポイントを**スレッドプールで実行**するので、同期処理がイベントループを凍結させない（[12-08](12-08_非同期型.md) の「うっかり同期」事故を仕組みで防いでいる）。つまり：

- `async def` + async ライブラリ → イベントループで高効率に
- `def` + 同期ライブラリ → スレッドプールで安全に

**「まず全部 def で書き、待ちが支配的なエンドポイントだけ async def に置き換える」**という段階的移行ができるのが、両対応の実務的な価値。

## 落とし穴：組み合わせを間違える

両対応は「何も考えなくていい」ではなく、**組み合わせの規律**が残る：

```python
@app.get("/trap")
async def trap():
    return requests.get(SLOW_API)   # async def の中で同期I/O ← ループ凍結（最悪の組み合わせ）
```

- `async def` の中では async ライブラリしか使わない（守れないならその関数は `def` に落とす）
- スレッドプールにも上限がある。`def` エンドポイントに大量の遅いリクエストが来ればプールが枯れる——「def なら無限に安全」ではない

「async def + 同期ライブラリ」だけが事故で、他の組み合わせは動く、と覚えるのが簡単。

## 選択の目安

新規の API サーバーでどれか迷ったら、両対応（FastAPI）から始めるのが現在の無難解：同期の書きやすさで始めて、必要になった箇所だけ非同期化する退路が確保されている。逆に「全編 async 前提で最高効率」が最初から確定しているなら、純非同期型（[12-06_Sanic](12-06_Sanic.md) や aiohttp）も選択肢になる。
