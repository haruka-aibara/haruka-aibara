# 非同期型フレームワーク

外部 API を3つ呼んで結果をまとめる BFF、数千クライアントが張りっぱなしの WebSocket、遅い上流を待つプロキシ——**処理時間の大半が「待ち」**というワークロードでは、同期型（[12-07](12-07_同期型.md)）のワーカーはほぼ全員が待機列に並んでいるだけになる。この無駄を回収するのが非同期型（Sanic、aiohttp、Tornado、FastAPI など）。

## モデル：待ちの間に別のリクエストを進める

非同期型は**イベントループ**という単一の実行者が、多数のリクエストを少しずつ進める。`await` は「ここで待ちに入るので、その間ほかの仕事をどうぞ」という譲り宣言：

```python
@app.get("/dashboard")
async def dashboard():
    async with httpx.AsyncClient() as client:
        users, orders, alerts = await asyncio.gather(   # 3つのAPIを並行で待つ
            client.get(USERS_API),
            client.get(ORDERS_API),
            client.get(ALERTS_API),
        )
    return build(users, orders, alerts)
```

同期型なら 100ms×3=300ms かかる集約が、並行に待てば約100msになる。1ワーカーで数千の同時接続を張れるのもこのモデルの得意技。標準側の対応が **ASGI**（WSGI の非同期版）で、サーバーは uvicorn 等を使う。

## 代償：「うっかり同期」がすべてを止める

非同期型の性能は「誰も実行者を長時間独占しない」という**紳士協定**の上に成り立つ。この協定を破るコードが1行あるだけで全リクエストが止まる：

```python
@app.get("/bad")
async def bad():
    data = requests.get(SLOW_API)   # awaitできない同期ライブラリ！
    # ↑ この 200ms、イベントループ全体が凍結＝全接続が待たされる
```

ここから実務上の掟が導かれる：

- **I/O ライブラリはすべて async 対応品で揃える**（requests→httpx、psycopg2→asyncpg 等）。「1個だけ同期のまま」が許されないので、移行はオール・オア・ナッシングになりがち
- CPU を食う処理・どうしても同期な処理は、スレッド/プロセスに逃がす（`asyncio.to_thread` 等）
- 「非同期にしたのに遅い」の調査は、まず**ループを止めている同期呼び出し探し**から

この「協定を守る難しさ」が、非同期型を「速いが規律を要する」選択肢にしている。asyncio 自体の書き方は [13_並行処理](../13_並行処理/) を参照。

## 選択の目安

- **待ちが支配的・同時接続が多い**（API 集約、WebSocket、ストリーミング）→ 非同期型の独壇場
- CPU バウンド → 非同期は無力（GIL と合わせて [13-03](../13_並行処理/13-03_GIL.md)）。プロセス分割の話になる
- 普通の CRUD → 同期型で十分なことが多い。FastAPI のような「両対応」（[12-09](12-09_同期型+非同期型.md)）で始めるのも手
