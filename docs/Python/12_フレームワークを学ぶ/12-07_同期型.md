# 同期型フレームワーク

Python の Web フレームワークを選ぶとき、個々の名前の前に知っておくべき分類が「同期型か非同期型か」。この違いは書き味の好みではなく、**1つのワーカーが同時に何件のリクエストを捌けるか**という処理モデルの違いで、フレームワーク・サーバー・ライブラリの選択すべてに波及する。

## モデル：1リクエスト＝1ワーカーを占有

同期型（Django、Flask、Pyramid など）では、リクエストを受けたワーカー（プロセス/スレッド）はレスポンスを返すまでそのリクエストに専念する。途中で DB やAPI の応答を待つ間も**ワーカーは待ちぼうけ**——他のリクエストは別のワーカーが受けるしかない。

```python
@app.route("/report")
def report():
    data = db.query(...)          # 100ms 待つ間、このワーカーは何もできない
    ext = requests.get(...)       # さらに 200ms 待つ
    return render(data, ext)
```

だから同期型の並行性は**ワーカー数で稼ぐ**。本番では WSGI サーバー（gunicorn 等）でプロセス／スレッドを並べる：

```bash
gunicorn --workers 4 --threads 2 myapp:app   # 同時処理は最大 4×2=8 リクエスト
```

この構成が **WSGI**（Web Server Gateway Interface）という標準の上に成り立っている。同期型＝WSGI の世界、と対応づけて覚えてよい。

## 弱点と、それでも主流であり続ける理由

弱点は明確で、**待ち時間の長い処理（遅い外部 API、大量の同時接続、WebSocket）でワーカーが枯渇する**。同時接続1万のチャットサーバーを同期型で書くのは筋が悪い。

それでも同期型が実務の多数派であり続けるのは：

- **コードが素直**：上から下に実行されるだけ。async/await の伝播や「うっかり同期処理を混ぜてイベントループを止める」事故（[12-08_非同期型](12-08_非同期型.md)）と無縁
- **エコシステムが枯れている**：Django/Flask の周辺ライブラリ・知見の蓄積は圧倒的
- **大半のアプリには十分**：社内ツールや通常の CRUD API のボトルネックは大抵 DB であって、ワーカーモデルではない

## 選択の目安

リクエストあたりの処理が「DB を1〜2回叩いて返す」型で、同時接続数が極端でないなら同期型で困らない。**「遅い I/O を大量に待つ」要件が見えたときだけ**非同期型（[12-08](12-08_非同期型.md)）を検討する、という順番が実務的。
