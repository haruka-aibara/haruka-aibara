# 二分探索木

Python を書いていて二分探索木（BST）を自作する日はほぼ来ない。それでも学ぶ価値があるのは、**データベースのインデックスがなぜ検索を速くするのか**、**「ソート済みを保ちながら挿入」に何を使うべきか**を説明する概念だから。

## 仕組み：大小で左右に振り分ける木

二分探索木は「左の子 < 親 < 右の子」というルールで値を配置した木構造。探すときは根から大小比較で左右に降りるだけなので、木がバランスしていれば**探索・挿入・削除が O(log n)**——100万件でも約20回の比較で届く。

```
        50
      /    \
    30      70
   /  \    /  \
  20  40  60  80
```

さらに、**中間順で辿るとソート順に列挙できる**・**範囲検索（30〜60のもの全部）が得意**という性質があり、これがハッシュテーブル（[02-02](02-02_ハッシュテーブル.md)）との決定的な違いになる。

## ハッシュテーブルとの使い分けが本質

| | ハッシュテーブル (dict/set) | 二分探索木（系） |
|---|---|---|
| 完全一致の検索 | **O(1)** | O(log n) |
| 範囲検索・順序の維持 | 不可能（全走査） | **得意** |

「id で1件引く」なら dict の圧勝。「スコアが80〜90のユーザー」「タイムスタンプ順に前後を見る」なら木の領分。**RDB の B-tree インデックス**（BST の多分木版）が範囲検索や ORDER BY に効くのは、まさにこの性質による。`WHERE score BETWEEN 80 AND 90` にインデックスが効く理由を一段深く言えるようになる。

## 「バランス」が崩れると台無しになる

素朴な BST にソート済みデータを挿入すると、木は一直線に伸びて実質リンクドリストになり O(n) に劣化する。実用の木はこれを防ぐため**自動でバランスを取り直す**（AVL 木、赤黒木など）。実務製品はすべてこの自己平衡版で、「BST は自作せず、枯れた実装を使う」の理由もここにある。

## Python での現実解

標準ライブラリに平衡二分探索木はない。順序付きの検索・挿入が欲しいときの現実解は：

```python
import bisect

scores = [20, 30, 40, 50, 60, 70, 80]           # ソート済み list を維持
idx = bisect.bisect_left(scores, 55)             # 二分探索 O(log n)
bisect.insort(scores, 55)                        # ソートを保って挿入（挿入自体は O(n)）
```

挿入が頻繁で件数が大きいなら `sortedcontainers`（サードパーティ、実務での定番）を使う。それ以上の規模・永続性が要るなら、それはもうデータベース（と B-tree インデックス）の仕事。
